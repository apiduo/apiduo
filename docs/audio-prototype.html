4. 两个必须先修的计费缺陷

  
都在现有代码里，与本次适配无关，但会决定适配值不值得做。

  

    
      
缺陷现状后果修法

    
    
      

        P1
STT 时长计量缺失

        STT 请求的 Input 是空串，GetTokenCountMeta() 算出 0 token；上游不返 usage 时回落到这个 0
        whisper-1 这类按秒计费的上游完全免费，且已发出的量收不回来
        RelayInfo.AudioSeconds，三级来源：上游 duration → 容器头解析 → 字节保守下限
      

      

        P1
音频 token 识别失败

        dto.Usage 的 tag 是 input_tokens_details，OpenAI 语音接口返的是 input_token_details，差一个 s
        音频输入按文本价结算，audio_ratio 配置形同虚设
        不靠 details 猜，直接按 RelayMode 三选一分派
      

    
  

  

    为什么排在适配之前：现在能出声的只有 4 个渠道，漏损面有限。一旦把 29 个渠道铺开，同一处缺陷会被放大 29 倍，而且按秒计费的账期已过，追不回来。
  






  
5. 实施顺序

  
按风险排，不按功能排。每步都可独立合入。

  

    
阶段内容为什么在这个位置

    
      
P1计量地基：AudioSeconds + 三级时长来源 + 按秒结算 + 计费分支改按 RelayMode 分派不修就先别接。已发出的量不可追

      
P2协议配置 + canonical 折叠 + 单测（纯函数，无网络无厂商）Enabled=false 时零行为变化，可安全合入

      
P3OpenAI 脚本 + 三类入口打通 + 能力声明挂进渠道选择器覆盖面最广，siliconflow 这类只需改 base_url

      
P4国内厂商逐家：先火山（含异步桥接），再阿里，再腾讯每家一套签名，一家一个失败面
