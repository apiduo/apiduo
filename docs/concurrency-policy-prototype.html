第一性原理：成本不在函数，在计量层
决策层（额度 → 上限）是纯函数，两条路线都简单；拒绝层（429 + 响应头 + i18n）可复用既有范式。 全部差异在计量层：速率计数只需 +1 与窗口过期，在途金额挂在已有预扣链路，二者都不需要知道请求何时结束；而在途请求条数必须严格配对每个请求的开始与结束，需覆盖正常返回、SSE 末帧、客户端断连、上游超时重试、进程崩溃五种形态，任一处漏释放都会把用户永久限死。 这正是 OpenRouter 选择「金额 hold」而非「条数计数」的工程原因。
原型边界：本页为静态设计评审稿，所有数值由浏览器本地计算，不调用任何后端接口，不构成产品实现。 曲线默认 B₀=10 / B₁=1000 / L=64，低额档文本 3、其他 1，非文本 = max(1, ⌊文本/3⌋)，B ≥ B₁ 为「解除用户级上限」且仍受全局软上限约束。
事实前提：OpenRouter 官方并无「按额度映射并发数」机制；其 402/403/429 三类限制、累计购买额分档、在途消费预算与 SSE 错误语义见 docs/concurrency-policy-design.md。 当前工作区为裁剪快照（无 go.mod、缺 controller/relay.go 与 i18n locales），难度评估按完整工程给出，本快照无法编译验证。
