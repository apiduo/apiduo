01这笔钱由三个数决定

一次请求的扣费只有一条式子：quota = tokens × model_ratio × group_ratio。tokens 是计量结果，不是决策；另外两个才是可调的旋钮。

改 model_ratio 影响全站所有人；改 group_ratio 影响整个分组的所有模型

两条旁路也都走不通。billing_expr 的可用变量只有 p / c / cr / img / hour / weekday 这一类，全是用法、请求内容和时间，没有任何用户维度——它在模型维度上是全局唯一真值，本来就不该认识用户。token.group 能换分组，但换不了「只对某个模型」。

02为什么不能给 group_ratio 加一根 model 轴

因为它是稠密的——每个分组都必须有一个值，那是兜底价。加 model 轴后每个格子都得填，可折扣天然是稀疏的：只有少数例外有值。

按 3 组 × 3 模型示意。真实规模下中栏是 20 × 100 = 2000 个格子

这不是假想。group_group_ratio（用户组 × 使用组）已经是这个教训的活标本——它的默认值里至今留着 "vip": {"edit_this": 0.9}，运营得先造一个叫 edit_this 的假分组才能用。

现有的 group_group_ratio 是 UserGroup × UsingGroup 的稠密二维表，没有 user 轴也没有 model 轴——它能给「vip 组所有人用 svip 时 0.9」，给不了「只给张伟，且只对 gpt-4o」。

于是真的有两个自由变量：UsingGroup × Model。但两者基数差三个数量级：分组只有几个，模型有几百个。低基数适合枚举成 key，高基数适合写模式规则——这也是仓库既有范式（group_ratio 是 map，model_ratio 走通配查表）。

不要做扁平的 groups + models 双通配字段。 那会撞上无解的排序歧义：vip 精确 + 模型 * 与 * 组 + gpt-4o 精确，vip 调 gpt-4o 该命中谁？两条具体度相同，怎么排都能举反例。组只做精确 key 分桶，通配只留给模型，歧义直接消失。

完整结构：apiduo_discounts 从数组改成 map[group][]rule。* 桶是「其他全部分组」的兜底。

05过期时间

要点做法不这么做的后果
until 是时刻now < until 才有效，0 = 永久存「30 天」要每次重算基准，跨时区/夏令时会错
判定在解析时until 随规则带到解析器，每请求实时比靠缓存 TTL 失效会晚 60 秒，且方向不可控
排序持久化写入时排好，解析只遍历热路径每请求都排序
日期粒度date picker 选「最后有效日」，落库转该日 23:59:59「到期 12/31」被理解成当天零点就失效，少一天
过期行不删灰显于「已过期」分组，可手动清理删掉后审计断链，查不出「曾经给过什么价」
过期是「跳过这一行，继续往下匹配」，不是整体失效。 vip 桶里 gpt-4o 的 7 折到期后，落到该桶 * 行的 0.80，而不是回到 group_ratio，更不会串到 svip 桶。勾选下面界面的「模拟到期」可以直接看到。
过期边界比改配置更容易撞上，因为它自动发生。 23:59:58 发起的流式请求 00:01 才结算，结算时若重算折扣就会用新价。折扣必须和 GroupRatioInfo 一起冻结进 PriceData / BillingSnapshot，结算读快照。多分组下这个坑更严重：auto_group 重试会真的换组（price.go:47 直接改 UsingGroup），重算就会串桶。

07存哪儿：决定能不能低成本落地

放进 users 表的新列会踩到一个暗坑：UserBase.cacheMAC() 对整个结构体做 HMAC 签名，加任何字段都会改变签名，存量 Redis 缓存全部校验失败，升级瞬间所有活跃用户同时回源数据库。这个变更的成本和一次全量缓存重建一样。

但 users.setting 本来就是 text，在 UserBase 里是 string。往这段 JSON 里加个 key，结构体类型没变，MAC 没变，而链路已经通了：

users.setting (text) → GetSetting() → dto.UserSetting → UserBase.Setting (string，随用户缓存进 Redis) → WriteContext → gin context → RelayInfo.UserSetting ← HandleGroupRatio 直接能读

一次 HGETALL 就把用户和折扣一起带下来了，零额外 IO。折扣数据从 UserSetting 读，分组从 RelayInfo.UsingGroup 读，两者在 HandleGroupRatio 里汇合——分桶不需要额外查库。写入走现成的 UpdateUserSetting，它自带 PublishUserAuthCache，下一次请求即生效；在途请求按开始时的快照结算。

09对抗审查

按「这个方案会在哪儿坏」写，不列优点。

  • 桶键必须是 UsingGroup，不是 UserGroup。 auto_group 跨分组重试时 price.go:47 直接改 relayInfo.UsingGroup；按 user.group 分桶会让「重试换到 svip」的请求仍按 vip 扣，且只在重试路径触发，常规测试碰不到。
  • 不给 token 指定 group，svip 桶永远命中不了。 auth.go:662,679：token.group 为空时 UsingGroup = user.group。配好了却所有请求都落 vip 桶，没有任何报错，界面上要先提示「这个人需要几个 token」。
  • 两个前置 403。 ContainsGroupRatio(tokenGroup)（auth.go:673）和 GetUserUsableGroups(userGroup)[tokenGroup]（auth.go:667）任一不过，token 直接被拒。组名要同时存在于 group_ratio 表和可用分组配置里，否则折扣配置形同虚设。
  • token.group = "auto" 是个特例。 它在 ContainsGroupRatio 里被放行，但真正的 UsingGroup 是重试后选中的组。UI 要明说 auto 不参与分桶，否则运营会以为配了个 auto 桶就生效。
  • 日志字段必须同步覆盖。 group_group_ratio 命中时会置 HasSpecialRatio=true，service/log_info_generate.go 与 service/task_billing.go 据此写 other.user_group_ratio = GroupSpecialRatio。折扣覆盖 GroupRatio 后若不改这两个字段，账单显示 0.90、实扣 0.80，对账查不出来。
  • 桶之间互斥，不能串。 桶内无命中就回落 group_ratio[UsingGroup]，不要再去 * 桶找。反过来 * 桶里放一条 * 模型行 = 全站所有组所有模型统一价，group_ratio 从此永不生效，保存时要二次确认。
  • 组名是字符串 key，删组会留下僵尸配置。 SubscriptionPlan.UpgradeGroup 还会直接改 user.group，进而改变默认 token 的 UsingGroup。分组不存在或已变更时，界面要列出「无请求会命中」的桶并高亮告警，不自动清理。
  • 不要用扁平的 groups + models 双通配。 二维 specificity 有真实歧义：vip 精确 + 模型 * 与 * 组 + gpt-4o 精确 具体度相同，vip 调 gpt-4o 命中谁都无法自圆其说。分桶是消歧手段，不是排版偏好。
  • 计算点有 5 个，散在三处独立实现里。 HandleGroupRatio 只覆盖主路径（文本/图像预扣、MJ/Task 预扣、relay_task、websocket）；service/quota.go:118 的音频计费自己又算了一遍 groupRatio；service/task_billing.go:409 的任务结算是第三遍。漏掉音频那处，语音请求永远按组价扣，且没有任何报错。
  • 折扣必须并入 GroupRatioInfo 并冻结。 pkg/billingexpr/types.go 的注释写死了：group 相关字段在 auto-group 重试和结算前会刷新。挂在 RelayInfo 外面，就会出现 A 组价格预扣、B 组价格结算；跨零点流式请求结算时重算折扣，还会用新价。结果进 PriceData / BillingSnapshot，结算只读快照。
  • 回滚会永久吃掉折扣。 UpdateUserSetting 是 Marshal(整个 setting) 全量覆写。回滚到旧版本后旧结构体不认识这个 key，任何人改这个用户的任何一项设置，折扣就被覆盖掉了。升级前备份 users.setting 是必须步骤，不是保险措施。
  • /api/pricing 必须同步。 controller/pricing.go:50 已经把 group_group_ratio 应用到展示价。个人折扣不在那里应用，用户在模型广场看到 0.90、实际被扣 0.80，反过来就是客诉。那段 pricingMap 是全局缓存，个人折扣必须走独立缓存键（含 user + group），否则会串用户、串分组。
  • 规则超过两行就没人看得懂最终价。「命中即停」是隐式的——运营看到 gpt-4o 和 gpt-* 都在，却看不出哪行生效。底部「实际生效」预览是正确性保障，不是装饰；分桶之后它还必须按组切换，否则预览的是另一个桶。
  • 每个桶的 * 模型行最多一条，规则总数限 50。 第二条 * 永远被第一条截住，是纯死配置，保存时拒绝。上限防止有人贴一大段 JSON 进 users.setting，把用户缓存撑爆。
  • 模型列表要去空格、去重。 "gpt-4o, claude-*" 里的空格若不 trim，会变成精确名 " claude-*" 而永不命中。claude-* 也不包含 claude 本身，想覆盖裸名要单独写。
  • 模型匹配不能复用现成函数。 FormatMatchingModelName 是单向归一化（把 gpt-4-gizmo-abc 变成 gpt-4-gizmo-*），不是 pattern 对 name 的匹配。折扣要自己写十几行：* 全匹配、前缀* 前缀匹配、否则精确相等。
  • 日期按运营本地时区解释，边界校验锁死。「12/31」必须在录入端就转成该时区 23:59:59，不能到服务端再按 UTC 转，否则差 8 小时。输入框填 8 而底层存 8 就是 8 倍价：0 < rate < 1，「折」与「0.8」的转换只在一个地方做；0 会触发 freeModel 预扣归零。
  • 模型名从哪来——已用零侵入方式解决。 不改 HandleGroupRatio 签名（那要动 6 个调用点、3 个上游文件），改为块内读 relayInfo.GetBillingModelName()：BillingModelName 为空时返回 OriginModelName，与各路径查价用的名字一致。代价是任务 action 模型（CoverTaskActionToModelName 兜底出来的名字）拿不到，折扣对它不生效——这类模型本来也没法定价名，可接受。
  • 传进去的必须是计费模型名，不是请求原始名。 info.GetBillingModelName() 才和定价表、映射后的模型名一致；用 OriginModelName 会让映射类模型（如 gpt-4-gizmo-xxx）匹配不上，折扣静默失效。
  • 是覆盖，不是相乘。 写成 GroupRatio * rate 就会和 group_group_ratio 叠加，用户实扣比配置更低。正确是直接 GroupRatioInfo.GroupRatio = rate，与现有 GetGroupGroupRatio 的「命中即覆盖」语义一致。
  • 三类计费都乘 GroupRatio，这点已核实。 按量 modelPrice * QuotaPerUnit * GroupRatio、图像 ImageQuotaBeforeGroup * GroupRatio、tiered_expr quotaBeforeGroup * snap.GroupRatio（pkg/billingexpr/settle.go:38）。所以覆盖 GroupRatio 三条路径都生效 —— 前提是那 6 个调用点都传了模型名。
  • 日志字段要同步。 命中 group_group_ratio 时会置 HasSpecialRatio=true，service/log_info_generate.go 与 service/task_billing.go 据此写 user_group_ratio。折扣覆盖后不改这两个字段，账单显示 0.90、实扣 0.70，对账查不出来。
  • 一个坏的折扣 JSON 会连累整份用户设置。 UserSetting 是整体 Unmarshal，折扣字段格式错会让语言、通知、侧栏配置一起变零值。要先 json.RawMessage 单独容错解析：折扣解析失败只丢折扣，不影响其余设置。
  • 回滚会吃掉折扣（已核实为唯一真实数据风险）。 EditWithTx 是白名单字段更新、不碰 setting；UpdateUserSetting 先读后改，都安全。但回滚到旧版本后，旧结构体不认识 apiduo_discounts，用户再改一次通知设置就会把它 marshal 掉。升级前备份 users.setting 是必须的。
  • 展示组与实扣组可能不是同一个。 GetPricing 用 user.Group 算，实扣用 relayInfo.UsingGroup（token 指定）。广场显示的是「默认组价」，用户拿 group=svip 的 token 请求时价不同。所以倍率表要按组返回（上面的 user_discount_ratios），让前端跟着选中的组走。
  • 到期存在最多 5 分钟的展示延迟。 前端 useQuery(['pricing']) 的 staleTime 是 5 分钟（use-pricing-data.ts:33），而后端 pricingMap 缓存 1 分钟。折扣到期后广场可能仍显示折后价，实扣已恢复原价。把折扣规则单独查询、或把 staleTime 降到 30 秒。

10今天就想用

多分组临时办法：group_group_ratio 填 {"vip":{"svip":0.9}}，但它对该用户组的所有人生效、没有 model 轴，也没法只给张伟。

完全不写代码的临时办法： 设置 → 分组倍率填 vip=0.8 / svip=0.9，设置 → 用户可用分组加 svip（默认只有 default/vip），渠道的可用分组加上这两个组，编辑用户 → 分组选 vip，再建一个 group=svip 的 token。代价：对该组所有人生效、无模型轴、要跨 3 个页面。

临时办法：新建分组 vip_gpt、group_ratio 设 0.8、把渠道的 group 字段加上这个组、把用户 group 改成它。

代价说清楚：这会让这个人所有模型都变 0.8，做不到只对 gpt-4o。每加一个「模型 × 折扣」组合就多一个永久分组，渠道也要跟着加组——你等于在手工模拟上面第 2 张图中间那一栏。
