## 8. 发现的问题（都不影响本次发布）

### P2 · schema 校验失败绕过了结构化错误

```
task.get 不传 task_id
→ isError:true, text="validating \"arguments\": validating root: required: missing properties: [\"task_id\"]"
→ 没有 structuredContent、没有 code

n 传字符串 "abc"
→ isError:true, text="validating \"arguments\": … type: abc has type \"string\", want one of \"null, integer\""
```

这是 SDK 在进 handler 之前就拦下了，`outputSchema` 声明了 `error{code,retryable}` 但这条路径拿不到，
且文案是 Go/英文。影响有限（agent 照着报错能改对），但这是**同一个服务端里第三套错误形态**。

可选做法：把 `task.get` 的 `task_id` 从 JS 层 `required` 里拿掉、在 handler 里判空；
`n` 不改类型，只在文档里说明这类错误来自 schema 层。都不算干净，建议**只记录不修**。

### ~~P2 · 重放在 structuredContent 里认不出来~~（2026-11-15 已修）

重放与首次生成的 `structuredContent` 完全一致（`status/model/outputs` 相同），
「未重复生成」只写在 text 前缀里。只读结构化字段的客户端会把它当成一次新生成。
修法：`generateOutput` 加 `replayed bool`（3 行）。已落地：重放结果带 `replayed: true`，
首次调用不带该字段。

### ~~P3 · 两条通道的 `n` 拒绝文案不一致~~（2026-11-15 已修）

顶层 `n=1000` → `n 最多 4，收到 1000；要更多请分多次调用`
`extra.n=1000` → `n 最多 4，收到 1000`（少了提示）

原因：`extra` 先被 `checkExtra → checkRange` 拦下，走不到 `checkBatchN` 的补充文案。
修法：`extra` 里的 `n` 在 `checkExtra` 之前先走 `checkBatchN`，两条通道共用同一句判定。

### P3 · 空能力列表也带了 5 分钟缓存

`resources/list` / `prompts/list` 现在返回 `ttlMs=300000, cacheScope=public`。当前无害
（永远是空），但将来真要加 `resources` 时，客户端可能把「空」缓存 5 分钟。

### 已知技术债 · 每次启动一条假 ERROR

```
[SYS] failed to migrate mcp protocols: Error 1054 (42S22): Unknown column 'protocol' in 'where clause'
```

`mcp_model_profiles.protocol` 列早已删除，迁移语句还在跑。修它要 +2 行 added、触顶合并预算，
上次已回退。不影响功能。

### 环境限制（不是服务端问题）

- 经 `127.0.0.1:8081`（mitm 反代）调 `subscriptions/listen`：**8 秒零字节**；
  直连 `apiduo.cn`：立刻收到 `notifications/subscriptions/acknowledged` 并保持打开。
  ⇒ 以后做推送必须把 `~/.workbuddy/mcp.json` 改成直连，或让反代不缓冲 SSE。

协议层（stateless、2026-07-28 握手、能力声明、缓存、限流）、工具层（结构化输出、错误分类、

## 11. 发现并修复

### 11.1 P0 · 同一个 `client_request_id` 配另一组参数，静默返回旧结果

```
首次：prompt="a red apple"        → 生成苹果
二次：prompt="a red sports car"  → replayed=true，返回的还是苹果
```

对 agent 来说就是「我要跑车，你给了苹果，还说成功了」。已修（`0.0.145`）：
幂等表新增 `request_hash`（工具 + `buildPayload` 之后的归一化载荷的 sha256），
键相同而指纹不同直接回 `IDEMPOTENCY_KEY_REUSED`，既不重放也不新发。
指纹取归一化后的载荷，所以「不传 duration」与「显式传 duration=5」仍算同一请求。
旧行 `request_hash` 为空，按「无法判定」放行，不做回溯校验。

### 11.2 P2 · `reference_images` 类型错误被判成 `INTERNAL_ERROR`

```
{"reference_images": {"a": 1}}      → INTERNAL_ERROR
{"reference_images": ["ok", 1]}     → INTERNAL_ERROR
```

这是调用方参数错，却告诉 agent「服务端故障」，它会重试同一个错误。已修（`0.0.145`）：
新增 `PARAM_INVALID`，并带上收到的类型（`map[string]interface {}` / `float64`）。

### 11.3 P2 · 视频模型的 `size` / `quality` 被静默丢弃

`video.generate` 传 `size="1920x1080"` 时，校验通过、参数被丢、产物仍是 720P，
没有任何提示。已修（`0.0.145`）：直接回 `PARAM_NOT_DECLARED`，并指出「画幅用 ratio，
清晰度用 resolution」。静默丢弃一个决定产物形状的参数，比拒绝更难查。

### 11.4 P3 · 观察快照漏掉模型声明的开关/枚举参数

线上样本：doubao `watermark="yes"` 被拒后，`param_snapshot` 是 `{}`、`failed_param` 为空 ——
白名单只有 `size/duration/n/resolution/aspect_ratio/quality/format`，于是
`watermark` / `ratio` / `generate_audio` 永远进不了快照，「声明是否收得太紧」的巡检
看不到它们。已修（`0.0.146`）：补进 `ratio` / `generate_audio` / `watermark` /
`sequential_image_generation`；数值型高基数参数（seed 之类）仍不进白名单。

修后同一条拒绝的样本：`failed_param=watermark`、`param_snapshot={"watermark":"yes"}`。

### 11.5 P0 · 同步生成超时 → 上游已计费，产物全丢

第一次 `qwen n=4`：

```
301s  →  "请求上游失败: Post "http://127.0.0.1:3000/v1/images/generations": context deadline exceeded"
账本  →  18:20:12  qwen-image-3.0  20000  Image count 4
```

即：**钱扣了 4 张，URL 一张都没拿到**。MCP 客户端超时是 300s，而上游这次用了 349s。
另外错误文本把内网地址原样回显给了调用方。

已修（`0.0.147`）：

- 上游客户端超时 5min → 8min（覆盖已观测到的最慢同步批量）；
- 网络错误包成 `errUpstreamTimeout`，分类为 `UPSTREAM_TIMEOUT`，
  `retryable=false`、`retry_action=check_console`，hint 明确写「可能已生成并计费，
  先查账单，不要直接重试」—— 之前落到 `INTERNAL_ERROR`，agent 会当服务端故障重试，
  那正好是第二次扣费；
- 错误文本抹掉 `scheme://host`，保留方法与路径用于定位。

复验：同样 `n=4` 这次 **349s 成功，4 个 URL**（产物 6.1 MB，HTTP 200）。

## 13. 未修（数据/配置问题，不是 MCP 代码）

### 13.1 happyhorse 的声明价与实扣差 5 倍

`models.list` 宣告 `$0.05/次起（720P 5s）`，配置 `ModelPrice["happyhorse1.1"]=0.05`，
但账本每次 5s 任务扣 **125000 quota**。按同批 qwen（$0.01 → 5000）换算，
125000 = **$0.25**，即实际是 **$0.05/秒 × 5 秒**。

两种可能：配置按秒计价、MCP 文案按次写错；或配置写错。需要业务确认。
我倾向把文案改成「$0.05/秒（720P 5s ≈ $0.25）」，但这是 `mcp_model_profiles.cost`
里的数据，**没有直接改生产库**。

### 13.2 gpt-image 只计了 38 quota

一次 `gpt-image-2.6-flare` 生成：上游 usage `total_tokens=223`（input 7 / output 216），
但账本记 `prompt_tokens=1, completion_tokens=0, quota=38`（≈$0.00008）。按倍率计费的
模型把图片输出 token 算成了 0 —— 这不是 MCP 层，属于 relay 的用量映射或渠道倍率配置。

### 13.3 doubao 的产物 URL 24 小时后过期

返回的是 TOS 预签名地址，`X-Tos-Expires=86400`。qwen / flux / gpt 的 `oss.s3ai.cn`
地址不带签名参数。同一份 `outputs` 里混着「永久」和「24 小时」两种有效期，
agent 若把 URL 存下来隔天再用会 403。

### 13.4 schema 层校验失败仍是纯文本（已知，决定不修）

`task.get` 不传 `task_id`、`n` 传字符串这类错误由 SDK 在进 handler 前拦下，
没有 `structuredContent`。要修得把 `required` 与类型检查从 schema 挪进 handler，
代价大于收益。
