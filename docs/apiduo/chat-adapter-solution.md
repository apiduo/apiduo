# Chat-adapter 解决方案（设计稿 v0.1）

> 来源：`remap-service`（v0.1.26，单文件 866 行 README + `internal/` 全量实现）蒸馏。
> 状态：**设计稿，未写代码**。文中「实测」均引自 remap 的既有验证记录，本次未新增任何请求。
> 原型：`design/chat-adapter.html`（只读演示台，不是管理后台）。

---

## 0. 结论

**一句话**：把「模型名」从**传输事实**降级为**标签**。网关是唯一知道上游真名的进程，客户端只能看到标签，且这个约束由出站字节的生成方式保证，不靠约定。

三条不可逆决定：

| # | 决定 | 理由 |
|---|---|---|
| D1 | **无状态**，不引入管理台 | 一旦能在线改配置，就出现第二份真相；灰度、回滚、审计都要重做。配置进 Git，改配置走发布 |
| D2 | **白名单式置换**，不做全文替换 | 全文替换会篡改模型生成内容（用户问「你是什么模型」、代码片段、搜索结果摘要）。实测火山 `/v1/responses` 438 个 SSE chunk 中，真名只出现在 `response.model` 一处 |
| D3 | **失败显性**：无法保证脱敏时拒绝转发 | 一次明确的 400 可观测、可复现；一次静默的泄漏不是 |

**不做什么**：负载均衡、准入鉴权、计费、协议转换、模型能力矩阵、管理后台。
**只做什么**：请求改名 + 响应归名 + 出站面收敛。

与 `image-adapter` / `video-adapter` 的本质差异：

> 那两个技能定义 **canonical 协议**（把方言折叠成一种形状）。
> Chat-adapter **不定义新协议**，canonical 就是入站协议本身 —— 它只替换**命名空间**。
> 因为 chat 的请求/响应形状各家已高度趋同，强行折叠会丢失 vendor extras，而 extras 恰恰是排障与能力的来源。

## 1. 问题：模型重定向是两段式

NewAPI 这类网关的「模型重定向」只改**去程**。回程原样透传，于是泄漏发生在四个位置：

| 位置 | 典型形态 | NewAPI 原生行为 |
|---|---|---|
| 响应体 | `"model":"deepseek-v4-flash-260425"` | 原样回给客户端 |
| 响应 ID | `"id":"chatcmpl-…-deepseek-v4"` | 原样 |
| 错误体 | `"message":"model deepseek-v4 not found"` | 原样 |
| 响应头 | `X-Tt-Logid`、`Server`、`x-ratelimit-*` | 原样 |

客户端只要读一次响应，就知道真实上游。**因此「重定向」必须由一对动作组成：请求改名 + 响应归名。** 缺任何一半都等于没做。

## 2. 威胁模型：谁能看到什么

| 角色 | 能看到 | 可信度 | 设计推论 |
|---|---|---|---|
| 终端用户 / 客户端 SDK | 网关出口的每一个字节 | **不可信** | 脱敏的判定点是「出站字节」，不是「业务字段」 |
| 渠道运营 | 渠道配置、`.env` | 可信 | 配置里可以写上游真名 |
| 网关进程 | 映射表、真实上游、凭据 | 唯一真相源 | 归名只在这里发生 |
| 上游 | 真实模型、客户端凭据 | 外部 | 不假设它会替我们保密 |
| 日志 / 看板 | 结构化字段、指标标签 | 内部 | 只允许对外名；真名进受控字段 |
| 网络中间件 | 头、时序、体积 | 半可信 | 头必须白名单，时序属于不可控残留 |

三条推论直接决定架构：

1. **不能有「客户端可选上游」的能力**。remap 支持 `X-Upstream-Base` / `X-Upstream-Proxy` 请求头 —— 这既是 SSRF 面，也把上游拓扑交给了客户端。Chat-adapter **移除**这两个头。
2. **映射头是控制面，不是数据面**。`X-Model-Map` 由 new-api 这类可信中间层注入；公网客户端直接携带时必须拒绝（否则可绕过渠道策略选到未授权模型）。
3. **看板不是脱敏的例外**。指标标签一旦写入真名，等于把泄漏面扩到内部系统与第三方 SaaS。

## 3. 不变量

| # | 不变量 | 破坏后的样子 |
|---|---|---|
| I1 | **单一改写点**：只有映射层能决定 `model`；其余层不得拼装模型字符串 | 出现第二处 `strings.Replace`，两处规则漂移 |
| I2 | **全量归名**：任何出站字节里的模型标识都属于「对外名」命名空间 | 漏一个字段就是一整条泄漏 |
| I3 | **失败显性**：无法保证脱敏时拒绝转发 | 静默直通，无人知晓 |
| I4 | **归名只用请求上下文，不做反向查表** | 多对一时 A 别名的响应会串成 B 别名 |
| I5 | **生成内容不改写**（T0 模式） | 篡改用户可见回答，比暴露型号更糟 |
| N1 | **内容自述与行为指纹不可保证**（见 §6.3） | 宣称「绝对无法识别」，然后在演示中被一句话问穿 |

I5 与需求「响应全部为新模型」存在张力，处理方式见 §6.3–6.4：把「标识级不暴露」与「身份级不暴露」分开承诺。

## 4. 协议面

### 4.1 入站路径 → 协议（无配置）

| 路径 | 协议 | 凭据头 | 网关补齐 |
|---|---|---|---|
| `/v1/chat/completions`、`/v1/completions`、`/v1/embeddings` | `openai` | `Authorization: Bearer` | — |
| `/v1/responses`、`/v1/responses/{id}` | `responses` | `Authorization: Bearer` | — |
| `/v1/messages`、`/v1/messages/count_tokens` | `anthropic` | `x-api-key`（无前缀） | `anthropic-version: 2023-06-01` |
| 其他 `/v1/*` | `other`（OpenAI 惯例兜底） | `Authorization: Bearer` | — |

按路径判定而非按配置：配置是第二份真相，且新增端点时不该需要改配置。

### 4.2 凭据：纯透传，重新注入

网关不持有任何 Key。客户端给什么，按目标协议的头名重新注入什么。这带来两个必须写清的代价：

- **无法做准入**：Key 是否有效由上游判定。要准入，就必须在网关前再加一层鉴权，或改为网关持 Key（那就变成另一种产品）。
- **错误归因随凭据归属变化**：Key 是客户端的，上游 401 就是客户端的错 → **保持 401**；若改成网关持 Key，同样情形必须译成 **502**（客户端没写错却被要求改请求）。这条判据写进错误表，避免照抄上游状态码。

### 4.3 映射语法

```
① 精确    acme-pro=deepseek-v4-flash-260425
② 通配    claude-3-5-*=claude-sonnet-4-5
③ 兜底    MODEL_MAP_FALLBACK=deepseek-v4-flash-260425
```

| 形态 | 写法 | 效果 |
|---|---|---|
| 一对一 | `pro:v3` | 标准 |
| 多对一 | `pro:v3;lite:v3` | 共用上游，**按请求上下文各自归名**（I4） |
| 一对多 | `pro:v3;pro:r1` | 等权随机 |
| 加权 | `pro:v3;pro:v3;pro:r1` | 2:1 |

通配支持前缀 / 后缀 / 中缀 / 包含 / 全匹配；多条命中取**最具体**（精确 > 字面量更长 > 锚点更多），与书写顺序无关。

**严格模式默认开启**（`MODEL_MAP_STRICT=true`）：未命中即 400。理由：静默透传会让「配置漏了一条」与「故意不配」在结果上完全同形，而这正是最该被发现的故障。

⚠️ **strict 与 `MODEL_MAP_FALLBACK` 互斥**：兜底本身就是一条命中规则，配了它就不存在「未命中」，strict 会退化成永远不触发的开关。strict 模式下启动即校验 fallback 为空（或显式 `ALLOW_FALLBACK_UNDER_STRICT=true`），否则拒绝启动。同理，`*` catch-all 规则也会让 strict 失效 —— 它是通配，不是兜底，必须在配置评审时单独拦。

### 4.4 为什么没有「反向映射表」

多对一时，`v3` 同时对应 `pro` 和 `lite`。若响应归名靠 `upstream → public` 反查，先注册者会赢，另一个别名的响应就会串味。**归名必须携带本次请求的对外名**，映射表只做去程。

### 4.5 多上游：地址随别名走，不随请求走（移除 `X-Upstream-Base` 的后果）

remap 用 `X-Upstream-Base` 让调用方逐请求指定上游。这在一个实例服务多个上游时很方便，但它把「去哪里」交给了请求方 —— 既是 SSRF 面，也让上游拓扑可被枚举。移除它之后，多上游只有三种解法：

| 方案 | 形态 | 代价 | 适用 |
|---|---|---|---|
| **A. 每上游一个实例** | 部署 N 份，各自 `UPSTREAM_BASE` | 部署与升级 ×N；实例间配置漂移 | 强隔离 / 每租户独立 |
| **B. 地址写进映射项**（推荐） | `acme-pro = https://ark.../api/v3 \| deepseek-v4-flash-260425` | 配置随模型增长；同一别名不能指向两个 base | 单实例、上游数 < 20 |
| **C. 签名控制头** | `X-Upstream-Base` + HMAC + 时间戳 | 引入密钥、重放防护、时钟同步 | 渠道动态且不可枚举 |

**P0 取 B**。理由是它仍是**纯查表**：一个别名解析出 `(base, model, protocol)`，没有健康检查、没有权重、没有重试 —— 因此不构成「路由」，不违反 D1。启动时必须校验「同一别名不得解析出两个 base」，否则运行期只能靠先到者获胜，那是最难排查的一类串味。

这条同时解释了职责边界：**选渠道、选 Key、记账都在 new-api；chat-adapter 只认「这个别名对应哪个 base + 哪个真名」。** 它不知道渠道 ID，也不该知道。

## 5. 响应置换规范

### 5.1 命名空间

```
public_model   客户端请求体里的 model，本次请求的唯一归名依据
upstream_model 映射后的真名，只存在于进程内与受控日志
public_id      出站 ID：默认透传上游 ID（见 5.6）
fingerprint    上游 system_fingerprint 的 HMAC 投影
```

### 5.2 字段处置矩阵（T0 默认）

| 字段 | 处置 | 说明 |
|---|---|---|
| `model` / `response.model` / `message.model` | **整体覆盖**为 public_model | 不看原值，直接写 |
| `id` / `message.id` / `response.id` | **默认不动**；仅当值内含真名时改写 | 见 5.6 |
| `system_fingerprint` | HMAC(secret, 原值) 取 12 hex，前缀 `fp_` | 保留「后端变了」的信号，不暴露是谁 |
| 错误体 `message` / `code` / `param` / `type` | 短值子串替换 | 4xx 保留可操作信息，5xx 泛化 |
| 其他短字符串（≤256 字节） | 子串替换 | 别名库长串优先 |
| `content` / `text` / `delta` / `reasoning_content` / `arguments` / `refusal` / `transcript` | **一律不动** | 生成内容白名单，按字段名判定，大小写折叠 |
| 任意 >256 字节的字符串 | 不动 | 视为生成内容 |
| 未知字段 | 递归扫描，短值替换 | 上游新增字段的默认安全 |

### 5.3 流式

- 逐事件处理：只解析 `data:` 行的 JSON 载荷，`[DONE]` 与注释心跳原样透传。
- 每个 chunk 独立脱敏；跨 chunk 不拼包（SSE 的事件边界就是语义边界）。
- 若开启「首字提前下发」，合成的首事件**必须走同一条脱敏管道**，不能旁路构造 —— 它是整条流里唯一由本进程生成、却能写进客户端响应的字节。
- 响应正文一旦开始下发，**绝不重试**（否则客户端会收到拼接的两段流）。

### 5.4 响应头：白名单，不是黑名单

| 保留 | 理由 |
|---|---|
| `Content-Type` | 客户端解析 |
| `Retry-After` | 退避信号，值本身不标识厂商 |
| `X-Request-Id`（**网关自己生成**） | 跨系统关联，不暴露上游 logid |

其余一律删除，包括 `Server`、`Via`、`X-Powered-By`、`X-Tt-Logid`、`CF-Ray`、`X-Amzn-Requestid`、`x-ratelimit-*`。

> 黑名单的失效方式是「上游新增一个头，静默漏过」；白名单的失效方式是「少转发一个头，立刻可见」。方向要选后者。

**注意**：正文被改写后，`Content-Length` 必须重算或改用 chunked。转发上游原值会截断响应 —— 这是「脱敏做对了但客户端解析失败」的典型。

### 5.5 错误：按「谁的错」翻，不照抄上游

| 上游 | 条件 | 出口 | body |
|---|---|---|---|
| 400 | 客户端字段错 | 400 | 保留字段名，真名/URL 替换 |
| 401 | 凭据透传（默认） | **401** | 泛化文案 |
| 401/403 | 网关持 Key（非本产品） | 502 | 泛化文案 |
| 403 | 模型未授权 | 403 | 泛化文案，不回显上游策略名 |
| 404 | 模型不存在 | 404 | **不转发上游原文**（常含真名与接入点） |
| 429 | 限流 | 429 + `Retry-After` | 泛化文案 |
| 5xx / 超时 | 上游故障 | 502 / 504 | 固定文案 |

`ERROR_DETAIL=generic|sanitized`：白标场景默认 `generic`（自造文案 + 自造 code），排障信息全部落到内部日志，用网关的 request id 关联。这是「可排障」与「不泄漏」之间唯一可接受的交换方式。

### 5.6 ID 与有状态协议（最容易被忽略的一处）

改写 ID 会破坏所有「客户端回传 ID」的续接能力：

- Responses API 的 `previous_response_id`
- 文件 / 批处理 / 微调任务的 `file_id`、`batch_id`
- 部分 SDK 的会话关联

**决策**：默认**不改写不透明 ID**。上游 ID 通常是 `chatcmpl-` / `msg_` / `resp_` 这类通用前缀 + 随机串，不含模型名，透传不构成泄漏。仅当 ID 中**实际出现了真名或别名**时才改写，并且：

1. 改写用 HMAC 生成稳定的 `ca_<12hex>`，同一上游 ID 恒等；
2. 该部署若同时启用 `previous_response_id`，**必须**建 TTL 双向映射表（有状态），否则显式拒绝该能力（400 `unsupported_stateful_continuation`）。

不要「改了 ID 但假装续接还能用」—— 那会在第二轮对话才 404，排障成本最高。

### 5.7 超限：拒绝，不直通

单响应超过 `MAX_SANITIZE_BYTES`（默认 16MB）时返回 400，绝不原文转发。理由：一次明确失败可观测，一次静默泄漏不可。状态码取 400 而非 5xx —— 上游是正常返回的，是网关基于策略拒绝，记成 5xx 会污染上游错误率。上游真实状态码与错误正文仍写入内部 span。

## 6. 泄漏面清单（对抗审查）

把「不暴露上游」拆成 6 类共 28 个通道，逐条给出处置。**标注「不可控 / 无法保证」的 7 条（22–28）是产品承诺的边界**，必须在文档与销售口径中写明。

### 6.1 结构与头

| # | 通道 | 处置 |
|---|---|---|
| 1 | 响应 `model` 字段 | 覆盖 |
| 2 | `response.model` / `message.model`（流式包裹） | 覆盖 |
| 3 | `id` 内的模型名 | 条件改写（5.6） |
| 4 | `system_fingerprint` | HMAC 投影 |
| 5 | `usage` 的厂商私有细分（`cache_creation_input_tokens`、`server_tool_use`） | **保留**（计费依据），承认是结构指纹 |
| 6 | 工具调用 ID 前缀（`call_` / `toolu_`） | 保留（协议差异，非模型差异） |
| 7 | 检索引用 URL（暴露检索后端） | 保留内容，**域名可替换**（可选） |
| 8 | 产物 URL（对象存储签名 / AK / bucket） | **必须处置**：rehost，或剥离签名改代理 URL |
| 9 | 响应头 `Server` / `Via` / `X-Powered-By` | 删除 |
| 10 | 上游 logid / request id 头 | 删除，换网关自生成 ID |
| 11 | `x-ratelimit-*` | 删除（暴露账号配额画像） |
| 12 | `Set-Cookie` | 删除 |
| 13 | `Content-Length` | 重算（否则截断） |

### 6.2 错误与请求面

| # | 通道 | 处置 |
|---|---|---|
| 14 | 错误 `message` 含真名 / 接入点 ID / URL | 替换 + 截断 |
| 15 | 错误 `code` / `type` 厂商私有枚举 | `generic` 模式重写 |
| 16 | 错误 `param` 含厂商私有字段（`thinking.budget_tokens`） | 保留（客户端要改的字段），承认协议指纹 |
| 17 | `/v1/models` 返回上游模型清单 | **网关自造**：只列对外别名；无映射则 404。**这是 remap 当前未覆盖的 P0 缺口** |
| 18 | `X-Model-Map` 来自公网客户端 | 拒绝（控制面头） |
| 19 | `X-Upstream-Base` / `X-Upstream-Proxy` | **移除**（SSRF + 拓扑泄漏） |
| 20 | 请求体中的 `file_id`（上游文件服务颁发，绑模型） | 透传但登记为已知指纹 |
| 21 | `tools` 里的厂商私有工具名（`web_search_20250305`） | 透传，属显式能力声明 |

### 6.3 内容与行为（不可控）

| # | 通道 | 结论 |
|---|---|---|
| 22 | 模型自述「我是 DeepSeek」 | **T0 不改写**；T1 可选改写（见 6.4）；无法保证 |
| 23 | 工具参数 / 代码 / 引用中出现真名 | 同上。`arguments` 是内容字段，改写会破坏工具调用 |
| 24 | 拒答模板、安全策略话术 | 不可控（行为指纹） |
| 25 | 语言风格、标点、emoji 习惯 | 不可控 |
| 26 | 知识截止、上下文窗口、能力边界 | 不可控（可通过探测推断） |
| 27 | 首 token 延迟、吞吐、限流阈值 | 不可控（旁路） |
| 28 | token 计数与缓存命中行为 | 不可控（`cached_tokens` 是强指纹） |

**产品承诺的准确表述**：

> Chat-adapter 保证**出站字节中不出现上游模型标识**（1–21）。
> 它**不保证**模型无法被识别 —— 内容自述与行为指纹属于推断层（22–28），任何网关都无法消除。

这句话必须写进 README 第一屏。把 N1 藏起来，第一次客户演示就会被问穿。

### 6.4 内容层的三档策略

| 档 | 行为 | 代价 | 适用 |
|---|---|---|---|
| **T0（默认）** | 内容一字不改 | 模型自述会泄漏 | 自有产品、可接受「上游是谁」 |
| **T1（白标）** | 仅对**短句中出现的确切别名**做替换，其余不动；每次改写计数并抽样审计 | 可能篡改引用/代码；漏掉「我是 DeepSeek」这类不带版本号的表述 | 对外白标、演示环境 |
| **T2（不建议）** | 全量替换 + 注入身份 system prompt | 破坏 prompt 缓存、改变模型行为、仍可被绕过 | 不做 |

T1 的判定必须与 T0 共用同一套别名库与长度阈值，**不允许**为内容层单开一条正则旁路。

## 7. 配置面（最小集）

| 变量 | 作用 | 默认 |
|---|---|---|
| `UPSTREAM_BASE` / `UPSTREAM_BASE_<PROTO>` | 上游地址（单上游部署，仅服务端） | 必填 |
| `MODEL_MAP` | 精确 / 通配映射；多上游时每项带 base（§4.5） | 空 |
| `MODEL_MAP_FALLBACK` | 兜底 | 空 |
| `MODEL_MAP_STRICT` | 未命中即 400 | **true** |
| `MODEL_MAP_FAILOVER` | 429/5xx 切兜底 | false |
| `SANITIZE_ALIASES` | 别名库（长串优先） | 空 |
| `SANITIZE_MAX_VALUE_LEN` | 短值阈值 | 256 |
| `MAX_SANITIZE_BYTES` | 超限拒绝 | 16MB（样例部署）· 32MB（代码兜底） |
| `HEADER_ALLOWLIST` | 出站头白名单 | 见 5.4 |
| `ERROR_DETAIL` | `generic` / `sanitized` | generic |
| `CONTENT_POLICY` | `T0` / `T1` | T0 |
| `MAX_INFLIGHT` | 并发闸门 | 1024（样例部署）· 4096（代码兜底） |
| `UPSTREAM_FIRST_BYTE_TIMEOUT` | 流式首字节 ≈ TTFT | 30s（样例 60s） |
| `UPSTREAM_FIRST_BYTE_TIMEOUT_NONSTREAM` | 非流式首字节 = 整段生成上限 | 300s |
| `UPSTREAM_TIMEOUT` / `UPSTREAM_STREAM_TIMEOUT` | 总时长 | 10min / 30min |

> 上表数值取自 remap v0.1.26 的 `internal/config/config.go` 与 `.env.example`。两处不一致时以「样例部署」为准 —— 代码里 `MAX_SANITIZE_BYTES` 兜底 32MB、`MAX_INFLIGHT` 兜底 4096，而样例部署分别钉在 16MB / 1024。这种「代码默认值 ≠ 部署值」的漂移本身就是配置管理问题，Chat-adapter 应只保留一份。

超时四项语义不同，不可合并：流式的首字节 ≈ TTFT，非流式的首字节 = 整段生成上限，差一个数量级。

## 8. 可观测性（不泄漏的前提下可排障）

| 出口 | 内容 | 约束 |
|---|---|---|
| 指标标签 | `route` / `public_model` / `outcome` / `status` | **基数封闭**：只有精确声明过的别名成序列，其余归 `other` |
| 结构化日志 | 可含 `upstream_model`，开关控制 | 不进 trace、不进看板 |
| Trace 属性 | 映射级别（`exact`/`wildcard`/`fallback`/`none`）、改写计数、上游耗时分解 | 不写上游名 |
| 关联键 | 网关自生成 `X-Request-Id` | 客户端可带，但出口一律替换为自生成值 |

三个必看指标：`sanitize_rewrites_total`（置换是否生效）、`requests_rejected_total`（闸门/超限）、`model_failover_total`（首选上游在报错，客户端无感）。

**别把「上游名」做成指标标签**。客户端可以每次填一个新 model 名，标签基数随即失控 —— 这是成本与查询性能问题，也是泄漏面。

## 9. 验收：对抗性用例

原则：**canary 模型名**（随机不可猜串）植入所有通道，断言出站字节 0 命中。每条断言都要做**变异自证**：删掉被保护的守卫，用例必须转红。

| # | 用例 | 断言 |
|---|---|---|
| 1 | 非流式 chat | 出站无 canary；`model` = 别名 |
| 2 | 流式 40 chunk | 每 chunk 无 canary；`[DONE]` 保留 |
| 3 | Anthropic `message_start` | `message.model` 已覆盖 |
| 4 | 错误体植入 canary + URL | 出站无 canary、无 host（`generic` 模式） |
| 5 | 响应头植入 `X-Tt-Logid` | 头不存在 |
| 6 | `id` 内含 canary | 已改写为 `ca_`，且同一上游 ID 稳定 |
| 7 | 生成内容含 canary | **内容完整保留**（T0），只计数不改写 |
| 8 | 工具 `arguments` 含 canary | 完整保留，登记为残留 |
| 9 | 多对一（pro/lite 同上游） | 各自回自己的别名，不串味 |
| 10 | 加权 2:1 | 分布近似 2:1（实测 262:138） |
| 11 | 未命中 + strict | 400，不转发 |
| 12 | 响应 > `MAX_SANITIZE_BYTES` | 400，无正文，span 记 `response_too_large` |
| 13 | 上游 429 | 429 + `Retry-After`，body 泛化 |
| 14 | 上游 401（凭据透传） | 401，body 泛化 |
| 15 | `GET /v1/models` | 只含别名；无映射 404 |
| 16 | 客户端自带 `X-Model-Map`（公网） | 400，不生效 |
| 17 | 客户端自带 `X-Upstream-Base` | 该头被忽略（不转发、不生效） |
| 18 | 结构完整性 | 直连 vs 网关：字段数、嵌套、未知字段一致 |
| 19 | 首字注入事件 | 也经过脱敏管道（T0 下 model 仍为别名） |
| 20 | 重复请求 1000 次不同 model 名 | 指标序列数收敛（1 + other） |

通过线：**1–17 全绿 + 18 字段级一致 + 20 序列数收敛**。只跑 1、2 两条不算验收。

## 11. 与 remap 的差异清单

| 项 | remap 现状 | Chat-adapter | 理由 |
|---|---|---|---|
| 响应头 | 黑名单删除 | **白名单保留** | 黑名单对新增头静默失效 |
| 上游地址头 | 客户端可指定 | **移除** | SSRF + 拓扑泄漏 |
| 映射头来源 | 未鉴权 | **仅可信跳** | 控制面不能由数据面决定 |
| `/v1/models` | 透传（缺口） | **自造** | 会列出全部上游模型 |
| ID 改写 | 子串替换 | **默认不改** | 破坏 stateful 续接 |
| 严格模式 | 默认关 | **默认开** | 漏配与不配不同形 |
| 错误文案 | 脱敏后透传 | **默认泛化** | 厂商话术本身是指纹 |

| 验收 | 30 项功能用例 | **canary + 变异自证** | 功能用例不覆盖泄漏 |
| 管理台 | 无 | 无（+ 只读演示台） | 保持无状态 |

## 附录 B：进程内落地方案（渠道开关）

前置判断：**如果 apiduo 是唯一出口**（客户端只打 apiduo），进程内比独立网关少一跳、少一份配置，而且 `/v1/models` 本来就只列公开模型。代码成本与独立网关同量级，运维面更小。

### B.1 挂载点：一个 Writer 包装，不是 47 个适配器

apiduo 已有三处 `c.Writer = wrapper`（`middleware/audit.go:119`、`relay/requestplugin/reply.go:111`、`relay/helper/common.go:93`），包装是既有模式，不是新机制。

- 入口：`controller/relay.go` 的 `Relay()`，在分发前包一层，覆盖 OpenAI / Claude / Gemini / Responses 四种格式。
- 归名依据：`relaycommon.RelayInfo.OriginModelName`（请求对外名），不需要反查映射表。
- SSE：包装器维护 carry buffer，按行切 `data:`；跨 `Write` 的不完整行暂存；`Flush` 原样透传，不得延迟首字。
- 非流式：整段在内存改写后一次写出，重算 `Content-Length` 或强制 chunked。

### B.2 覆盖缺口：Realtime

`RelayFormatOpenAIRealtime` 走 `upgrader.Upgrade(c.Writer, …)`，帧不经过 Writer。要么在 realtime 事件序列上单独改写，要么在配置里明确「该端点不支持身份隔离」并拒绝开启。**不要假装覆盖** —— 这是唯一一个包装器结构性到不了的地方。

### B.3 粒度：全局默认开，渠道只能「关」

渠道级开关如果做成「默认关、手动开」，新渠道就是默认泄漏，而且没人会发现。正确形态是三态：

| 层 | 配置 | 默认 |
|---|---|---|
| 全局 | `IDENTITY_MASK=on` | 开 |
| 模型 | `models.identity_mode = inherit \| mask \| pass` | inherit |
| 渠道 | `settings.allow_upstream_identity`（仅内网调试渠道可开） | false |

回显名默认取本次请求的 `OriginModelName`。只有要「强制显示成另一个名字」时才需要模型字段，而且那个名字应该是自己的别名 —— 冒用厂商官方名是另一类问题（商标 / 虚假宣传 / 客户端按名路由会错）。

### B.4 能力路由不是渠道开关

「tools 请求改走官方 DeepSeek」通常意味着**换渠道**，而渠道是在模型选定之后才由分发器选的。渠道级配置无法表达「去另一个渠道」。正确粒度是模型级：

```
model: acme-pro
capability_routes: { tools: deepseek-chat, vision: qwen-vl-max }
```

它在分发前决策（`middleware/distributor.go` 之前），并写 `cap_route` 日志。

**三个必须一起决定的点**：

1. **判定条件不是「带没带 `tools`」**。工具调用是多轮闭环：第二轮客户端回传的是 `messages[].role == "tool"` 与 `tool_calls`，通常不再带 `tools` 数组。只按 `tools` 判断，第二轮就切回原模型，轻则风格跳变，重则工具结果解析失败。条件至少要覆盖 `tools` / `role == "tool"` / `tool_calls` 三者。
2. **Responses API 的 `previous_response_id` 跨模型会断**：新模型的上游不认识上一个 response，第二轮直接 404。这条链路要么不切，要么按 response id 粘住（有状态），不能按「本次有没有工具」判断。
3. **计费口径二选一**：客户看到 A、实际用 B。按 A 收费就吃差价，按 B 收费则账单与 `model` 名不一致。无论选哪个，日志必须同时记 `client_model`、`upstream_model`、`billed_model`，否则对账时无法解释。

**不要为它再拆一个「脱敏开关」**：路由开了、回显没开，就是半开状态，而且没人会发现。开关本身的语义应是「路由 + 回显」联合生效。


### B.5 成本（修正）

| 方案 | 代码 | 运维 | 主要风险 |
|---|---|---|---|
| 进程内 · 身份隔离 | 6–8 人日 | 无新增部署 | 流式分片、Realtime 缺口 |
| 进程内 · 能力路由 | 3–4 人日 | 计费解释成本 | 双上游调用 |
| 独立网关 · P0 | 5.5–7.5 人日 | 1 个新服务 + 模型清单对账 | 多一跳、两份配置 |

上一轮「3–6 周」是按逐适配器改 130 处 `"model":` 估的；Writer 包装这条路径把成本降到与独立网关同量级。这是修正，不是口径漂移。

### B.6 结论

- **apiduo 是唯一出口** → 进程内，先做身份隔离，再做能力路由。
- **多租户 / 多上游 / 需要独立灰度** → 独立网关（正文方案）。
- 两者不要同时上。先用一种把 canary 验收跑通，再谈第二种。
