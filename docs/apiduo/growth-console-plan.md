# 增长运营模块 · 实施计划

> 状态：排期稿。基于 `docs/apiduo/growth-console.md`（v0.2 设计稿）与 `design/growth-console.html`。
> 估算口径：单人、含测试与联调、不含评审与等待。
> 前置事实已核对本仓库代码，见第 1 节。

---

## 0. 结论

**26 人天，约 7 周单人节奏。第 1 周末即产生可归因收益，不需要等到全部做完。**

首次上线点定在 P0 结束——不是因为它简单，而是因为「余额耗尽预警」是唯一能在第一周就量出挽回率的功能，
而它只需要 `quota_data` 的近 7 天消耗，不依赖分层、不依赖工作台。

| 任务 | 人天 | 依赖 | 交付物 |

## 3. 五个必须提前处理的技术坑

### 坑 1（最严重）：事故型流失完全隐形

`quota_data` 只记录成功消费（F2）。一个客户错误率 100% 时消耗为 0，
按「消耗分位」和「最后调用时间」都会判成沉默或 B 层，**而实际情况是我方故障把客户打走的**。

对策：P0 的 A1 必须同时产出「近期失败请求数」。判定条件为
`有请求 ∧ 无消耗` → 事故型，优先级高于普通沉默。数据源用 `logs` 按天增量统计 `type != consume`，
不做按用户的时间范围查询（规避 F3）。

这条如果漏掉，整个系统的第一批预警就会把最该救的客户静默掉。

### 坑 2：`logs` 缺复合索引，查询模式必须反向设计

不能写「查某用户近 7 天错误」，只能写「扫某一天所有错误，按用户聚合」。
日任务按 `created_at` 单日范围扫描，与现有 `idx_created_at_type` 匹配，成本可控。
加索引属独立变更，不进本计划。

### 坑 3：时区不统一会让日环比永远算错

`quota_data.created_at` 是 Unix 时间戳。若任务按 UTC 切天、界面按本地时区展示，
「昨天」会偏 8 小时，环比数据长期失真且不易察觉。
必须在配置里显式固定时区（建议 `Asia/Shanghai`），写入聚合表时按该时区对齐。

### 坑 4：`DataExportEnabled` 被关掉时指标静默归零

开关关闭后 `quota_data` 停止写入，界面照常渲染，只是所有数字归零——不会报错。
对策：每个页面显示「数据新鲜度」（最后一次写入时间），超过 2 个导出周期（10 分钟）即置灰并提示。

### 坑 5：首周分层不稳

新系统没有 30 天历史时，分位切点会随数据补入而漂移。
对策：前两周只计算、只观察，不展示动作按钮；第三周起启用。

## 4. 关键路径

```
P0 ──► P1 ──► P2
 └──────────► P3 ──► P4
```

- P2 依赖 P0（预警数据），不依赖 P1。
- P3 依赖 P0（聚合数据），可与 P1/P2 并行。
- P4 依赖 P3（触达记录是归因的载体）。

若只有一个人：P0 → P3 → P1 → P2 → P4。把 P3 提前的理由是它产生的是**资产**（历史记录），
越早开始积累越值钱；P1/P2 产生的是**视图**，晚做不影响数据完整性。

| 项 | 判断 |
|---|---|
| 拉新漏斗 | 可延后。它解释问题但不解决问题，且需要按来源埋点 |
| 留存曲线 | 可延后。看一次就够，属复盘工具 |
| 触达模板 | 可砍。先手工发，跑通再模板化 |
| 批次 ROI | 保留，但可以先用表格人工核算，不急着做系统 |
| 毛利 | 必做，但独立排期 |

## 6. 一句话提醒

这份计划里唯一不能砍的是 P0 的「失败请求聚合」。
其余功能做慢了，损失是可估的；这一项漏了，系统会在最该报警的时候保持沉默。
