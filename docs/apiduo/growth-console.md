# 增长运营 · 集成方案与产品原型

> 状态：设计稿 v0.2，未落代码。配套可交互原型：`design/growth-console.html`
> 目标读者：后端 / 产品 / 运营
> 前置阅读：`docs/apiduo/pricing-and-group-design.md`（`group` 六重语义的技术债）

---

## 0. 一句话定位

这一层不改动任何计费与鉴权路径，只在日志之上加一层**只读派生视图 + 一张人工动作记录表**，
把运营从「看数据」推到「做完一件事并留下痕迹」。

v0.1 只解决了观察面。v0.2 的核心变化是把首屏从看板换成工作台——理由见下一节。

硬边界三条：

1. **不碰 `user.group`。** 运营分层独立存储，与计费分组完全解耦。
2. **不改 `users` 表结构。** 只读，避免与上游同步产生冲突面。
3. **不参与请求路径。** 所有计算离线完成，失败不影响转发。

---

## 1. 为什么从看板改成工作台

这是本次迭代最需要解释的判断。

看板类产品的价值**在第一次打开时就已经交付完毕**。运营看完分布、漏斗、留存曲线，就理解了用户结构；
第二天再打开，看到的是同样的形状。边际价值迅速衰减到接近零。

工作台类产品的价值**随使用累积**。每记录一次触达、每关闭一条预警、每结算一个批次，
下一个人（或三个月后的自己）能拿到的信息就更多。它的价值曲线是上升的，不是衰减的。

运营的真实时间分布也支持这个判断：绝大部分时间在「判断谁要跑、联系他、给方案、记结果」，
而不是在「看图表」。图表只在做月度复盘时才被真正需要。

所以页签顺序是：**今日（做什么）→ 分层（谁）→ 客户档案（为什么）→ 触达（怎么干预、有没有用）→ 规则（标准）**。

---

## 2. 五个页签的职责边界

| 页签 | 回答的问题 | 不许做的事 |
|---|---|---|
| 今日 | 现在做什么，按什么顺序 | 不放趋势图，不做分析 |
| 分层 | 谁重要，结构长什么样 | 不分配动作，不按层级派活 |
| 客户档案 | 这个客户为什么是现在这样 | 不做批量操作 |
| 触达与归因 | 干预花了多少、赚回多少 | 不做无批次记录的发放 |
| 规则 | 判定标准是什么 | 不放任何业务数据 |

三条容易做错的边界：

1. **动作排序不按层级，按损失。** 一个 A 层客户的余额即将耗尽，优先级高于 K 层的季度回访。
   层级决定投入强度，不决定先后顺序。
2. **档案是记忆，不是看板。** 客户档案的唯一价值是「换个人也不丢历史」。若它只显示指标，
   和一个筛选过的用户详情页没有区别。
3. **发放必须有批次。** 没有批次号的权益发放是成本；有批次号才能算 ROI，才是投资。

## 3. 四个接入点

| # | 位置 | 形态 | 解决什么 |
|---|---|---|---|
| A | 一级菜单「增长运营」`/growth` | 新增页面，五个页签 | 群体视角与执行闭环 |
| B | `/users` 列表 | 加 3 列 + 1 个筛选 | 账户视角 |
| C | 用户详情抽屉 | 加「健康度」区块 + 档案入口 | 决策依据 |
| D | 系统设置 → 运营 | 阈值、模板、覆盖名单 | 运营自助调整 |

### A. 一级菜单「增长运营」

菜单项通过后端动态菜单配置注册，与 `docs/new-api动态菜单配置方案-第一性原理.md` 的机制一致，
不硬编码进前端路由表。

### B. `/users` 列表新增列

| 新列 | 类型 | 说明 |
|---|---|---|
| 30 天消耗 | 金额 | 与余额分离。余额是存量，消耗是流量 |
| 趋势 | 图标 | 近 7 天 vs 前 7 天 |
| 层级 | 徽章 | K / A / B / 沉默，可点筛选 |

现状证据：`web/src/features/users/components/users-columns.tsx` 的列只有
`id · username · status · quota · group · role · created_at`，**没有任何一列反映近期行为**。
`used_quota` 是累计值，一个三个月前用满额度的账户数字依然漂亮，实际早已流失。

### C. 用户详情「健康度」区块

近 30 天消耗 sparkline、成功率与主要错误码、首调与末调日期、连续活跃周数、
当前层级与建议动作，以及「查看完整档案」入口。

### D. 系统设置 → 运营

分层切点（分位）、沉默判定、预警阈值、触达模板、人工覆盖名单。配置存 `options` 表，沿用现有设置项读写方式。

## 4. 数据来源与缺口

| 界面字段 | 现有来源 | 状态 |
|---|---|---|
| 30 天消耗 | `logs` 按 `user_id` 聚合 `quota` | 可用 |
| 请求数 / 成功率 | `logs` 按 `user_id` 聚合 | 可用 |
| 首调 / 末调时间 | `logs` `min/max(created_at)` | 可用 |
| 余额 | `users.quota` | 可用 |
| 趋势 | 两段窗口对比 | 派生 |
| 层级 | 分位切点 + 趋势 | 派生 |
| 集中度 | Top N 消耗占比 | 派生 |
| 触达记录 | 本项目新增 | 需新建表 |
| 批次 ROI | `logs` + 批次表 | 需新建表 |
| **毛利** | **无** | **缺失** |

结论：除毛利外，界面上的每个数字都能从现有日志表算出，不需要新增埋点。

唯一缺口是渠道成本——`model/channel.go` 没有 `cost` 字段，系统知道收了多少，不知道赚了多少。
处理方式：毛利列显示「待接入」，不显示估算值。错的毛利比没有毛利更危险，它会让人做出错误的分层判断，
而且没人会去验证。同理，批次 ROI 当前只能用营收近似毛利，界面必须标注「会系统性高估」。

## 5. 存储形态

### 5.1 只有三张表

| 表 | 性质 | 为什么必须有 |
|---|---|---|
| `growth_user_board` | 每用户一行的宽表 | `quota_data` 按小时分桶，跨 30 天 `GROUP BY` 要扫百万行，不能放在请求路径上 |
| `growth_touches` | 业务事实 | 触达记录无法从任何既有数据重建，删了就没了 |
| `growth_batches` | 业务事实 | 批次与归因无法重建 |

判据只有一条：**派生数据不建表，业务事实才建表。**

### 5.2 复用了什么

| 需求 | 复用 | 说明 |
|---|---|---|
| 消耗 / 请求数 / token | `quota_data` | 现成的按用户聚合表，粒度到小时 |
| 失败请求数 | `logs` | `quota_data` 只记 `LogTypeConsume`，失败必须回明细 |
| 余额 / 注册时间 / 状态 | `users` | 只读 |
| 累计充值 | `topups` | 只读 |

### 5.3 被否掉的三张表

- `user_growth_daily`（用户×天）：`quota_data` 是它的超集，再建一张就是第二份事实来源。
- `user_segments`：几千行排序是毫秒级，实时算即可。
- `growth_alerts`：预警是规则输出，人工状态挂在 board 行的 `alert_state` 上。

也没有塞进 `audit_logs`（语义是审计）、`redemption`（语义是额度凭证）或 `logs`（会被清理归档）。

### 5.4 三条硬约束

1. **粒度是用户级，不是用户×天级。** 选了后者，行数等于用户数乘 365，两年后自己就是瓶颈，且改粒度等于重建。
2. **宽表只能派生，永远可以整表覆盖重算。** 一旦有人在上面手改数据，它就和 `quota_data` 打架，而且没人分得清哪个对。
3. **时间序列不进宽表。** 方向用两个窗口标量表达；要看逐日曲线请查明细。

### 5.5 刷新方式

日任务取三个窗口（7 / 14 / 30 天）的 `quota_data` 累加量，用减法得到「前 7 天」；
失败数从 `logs` 按天取；整表 upsert，保留 `manual_tier` / `manual_reason` / `alert_state`。

`data_export` 被关闭时不写新行，界面据 `computed_at` 提示数据不新鲜，而不是静默归零。

## 6. 分期

| 阶段 | 内容 | 依赖 | 可独立交付 |
|---|---|---|---|
| P0 | `/users` 三列 + 今日工作台（只读队列） | `logs` 聚合 | 是 |
| P1 | 分层计算 + 分层页 + 人工覆盖 | P0 聚合结果 | 是 |
| P2 | `growth_touch` + 客户档案 + 触达记录 | 无 | 是 |
| P3 | `growth_batch` + 批次归因 + 自动停投 | P2 | 是 |
| P4 | 渠道成本字段 + 毛利 + 毛利预警 | 需改 `channel` 模型 | 否 |

排序理由：P0 改动最小、依赖最少、收益最直接（运营立刻能看到谁在用）。
P2 是唯一让系统「越用越值钱」的一期，优先级应高于 P3 的自动化。
P4 是分层正确性的前提，但在它落地前，界面应持续显示缺口，不先用营收替代。

## 7. 验收判据

不是「功能上线」，而是四个可测的结果：

1. 运营能在 10 秒内回答「本月最可能流失的三个客户是谁」，且答案与事后事实吻合
2. 任一 K 层客户的关键承诺（如「本周给结论」）不会被遗漏——待办由系统生成，不靠记忆
3. 能指出至少一个应该停投的批次，并给出 ROI 依据
4. 分层人数落在可操作区间（K 层 5–20 人）

第 1 条与第 2 条是核心。如果三周后运营依然靠印象判断、靠脑子记承诺，这套系统就没有解决问题。

---

## 8. 已知限制

- 毛利与真实 ROI 在 P4 之前不可用，所有涉及利润的判断都应推迟或标注为近似。
- 客户档案的质量取决于运营是否真的记录。功能可以做，习惯不能强制——这需要配合「不记录则不算处理完」的产品约束。
- 分层对季节性业务、POC 阶段客户会误判，必须依赖人工覆盖，不能全自动。

## 9. 运营可配置项

存在 `options` 表的 `growth.settings`，键值是一段 JSON。运营在「规则」页改，
下一次重算或手动点「立即重算」后生效。越界值会被夹回安全区间，不会把分层算崩。

| 项 | 默认 | 作用 |
|---|---|---|
| `tier_key_percent` | 3 | K 层分位切点 |
| `tier_active_percent` | 15 | A 层累计分位切点 |
| `tier_key_cap` | 20 | K 层人数硬上限 |
| `silent_days` | 30 | 无成功调用多少天判为沉默 |
| `balance_warn_days` | 3 | 余额可用天数低于此值触发预警 |
| `incident_rate_pct` | 20 | 失败占比高于此值判为事故型 |
| `decline_pct` | 10 | 周环比降幅超过此值视为下滑 |
| `dormant_days` | 14 | 注册后多少天无调用判为未激活 |

为什么要有上限：`tier_key_cap` 防止平台用户暴增后 K 层膨胀到几百人。
K 层的定义是「运营能叫出名字的账户」，超过 20 人这个定义就失效了。

## 11. 布局与加载契约（2026-11-23）

这一页和 `/service-health` 都曾用 `SectionPageLayout fixedContent`。那个 prop 的含义是
「内容区不滚动、页面自己管理滚动容器」，只适合单块自适应高度的表格（如使用日志）。
这两个页面是堆叠卡片，实测内容 1272 / 2429px 被裁到 673 / 665px，滚动条根本不存在——
用户看到的症状是「不支持滚动」「页面卡死」，实际每一次渲染都是正常的。

- 堆叠卡片一律用默认布局（内容区 `overflow-auto`）；`fixedContent` 只能给
  「单块 `h-full min-h-0 flex-col` + 自滚表体」的页面用。
- 页签列表在滚动容器里 `sticky top-0`，滚到页面中段仍可切页签。

加载侧的三条：

1. **分页必须在渲染层做**。`/api/data/user-balances` 一次返回全部有消耗的客户
   （每人 14 天序列），留存看板曾经一行一个 `<tr>` 全量挂载；客户上千时主线程被
   DOM 锁死。现在与下钻表、客户列表统一走 `ListPager`（20 行/页，可选 50/100）。
2. **搜索必须防抖且与页码解耦**。原先每个按键发两个全量聚合，且「改筛选 → 回第一页」
   靠 effect 补，会先按旧页码发一次再按新页码发一次。现在页码与筛选同在一个 state 里，
   防抖后只发一次。
3. **读数缓存 + 重算互斥**。概览/预警/模型构成走 `service.CachedGrowthOverview` 等
   （复用 ops 缓存池，30 秒 TTL，写接口按 `growth:` 前缀失效）；手动重算用
   `TryStartGrowthRefresh` 抢占，连点返回 `{started:false, already_running:true}`。
