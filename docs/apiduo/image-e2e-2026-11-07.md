## 本轮发现并修复的两个计费 bug

端到端查 `logs.quota`，同模型同一次生成，从 chat 入口调用比 images 入口**贵一倍**：

| 阶段 | images | chat |
|---|---|---|
| 修复前 | 38 | **75** |
| 修复后 | 38 | **38** |

根因与修法：

1. **`usage` 与 ImageHelper 不一致**。`finishImageChatResponse` 原返回
   `PromptTokens:1, CompletionTokens:1`；`ImageHelper` 是 `1/0`。TextHelper 按 token 计价，
   多一个 completion token 正好翻倍。改为 `1/0`（`TotalTokens>0` 仍满足 `hasBillableUsage`，不漏计费）。
2. **乘子口径错**。原用 `len(response.data)`，而 ImageHelper 用请求 n，且非 `UsePrice` 时
   `PrepareImageBillingForRequest` 把 quantity 固定为 1。skill §2.2 也明确 `data` 长度不保证等于 n。
   改为把 canonical 的请求 n 缓存到 `a.imageRequestCount`，回包时只调 `UpdateImageCount()`
   （内部已按 UsePrice / tiered 分支处理），不再无条件 `AddOtherRatio`。

修复后受控对比：images n=1 / n=2 与 chat n=1 / n=2 / 图生图，5 个请求全部 `quota=38`，完全一致。

## 追加：chat 回包改 Markdown + stream 拼 SSE（21:47）

需求：`chat 返回图片 用 md 包装返回`，并追问 `stream:true` 是不是也该「拼装为 chat」。
答案：是。上一轮用 400 打发 `stream:true` 与「入口只负责拼装形状」的口径矛盾，撤销。

### 回包形状

| 入口 | `content` | 说明 |
|---|---|---|
| chat 非流式 | `image_url` parts 数组（**不用 md**，最终口径见末节） | 每张图一个 part，附加字段跟各自 part |
| chat `stream:true` | SSE 三帧：`delta.content` 是 md → `finish_reason=stop` → `[DONE]` | `Content-Type: text/event-stream` |
| chat 上游空 `data[]` | `content: []` | 字段仍在，不升格 5xx（§9.7 口径） |

上游附加字段（`usage` / `revised_prompt` / `size`）仍 carry over 到 envelope 顶层。
服务端计费是 `finishImageChatResponse` 返回的另一份 `*dto.Usage`，与响应体里的 usage 互不影响。

⚠️ 流式用 md 是有意偏离 skill §2.2（skill 只定义了非流式 parts）；非流式在
21:55 已恢复为 parts，最终口径见末节。

### 实现要点

- `chatImageMarkdown()` 生成 md；`wrapChatCompletion()` / `wrapChatCompletionStream()`
  共用同一份 md，避免非流式与流式内容漂移。
- SSE 写回**不能**用 `service.IOCopyBytesGracefully`：它会把上游的
  `application/json` 复制回来覆盖 `Content-Type`，SSE 客户端会按 JSON 解析。
  这里自己 `Header().Set + WriteHeader + Write + Flush`。
- `TextHelper` 在 stream 下没有特殊分支（仍调 `DoResponse`、仍强转 usage 计费），
  所以**不用改上游分发**；`a.imageStream` 缓存 `request.Stream`，与 `info.IsStream` 取或。
- 计费：非流式 / 流式 / images 三入口实测 `quota=38` 一致。

### 对抗审查留下的风险 / 易踩坑

1. **`clear` 是置 `null`，不是删键**：响应里 `b64_json: null` 与 `url` 并存。
   客户端用 `.get()` 没问题，用 `"b64_json" in item` 会拿到 null。
   与 skill §2.2「url / b64_json 互斥」略有偏差。属既有实现，未擅自改。
2. **内联 base64 有 ≥1024 字符阈值**：短 base64 被当标识符跳过。第一次测 `b64_json`
   「没转存」就是这个原因，不是 `rewrite_paths` 没生效——排障时容易误判。
3. `b64_json` 默认不选，必须显式 `rewrite_paths`；`url` / `data:` / `base64` 等才在默认表。
4. **已是可访问的 http(s) URL 不会跳过**，会下载再转存；本地/私网被 SSRF 拒，
   所以端到端只覆盖了 data URI / 内联 base64 两条路径。
5. `public_base_url` 必须与 bucket 对齐（`<base>/<prefix>/<key>`），配错会得到 404 链接。
6. 失败有 15s→5min 翻倍冷却，排障时会以为「配置没生效」。
7. 同一内容 key 相同但每次仍 PUT，省的是对象数不是带宽。
