00一页纸结论

这五项职责不是五个工程模块，而是同一条成本曲线的五个切面。先定义目标函数，再谈架构，否则每个子系统都会局部最优、整体亏损。

01

成本的第一杠杆是利用率，不是采购价。卡价降 25% 只让单百万 Token 成本降 25%；利用率从 0.30 提到 0.55 降 45%；单卡吞吐翻倍再降 50%。采购谈判是最后才动的旋钮。

02

计费是产品功能，不是财务功能。流式中断、多模态非标、缓存命中、内部重试四个场景决定了毛利能否被解释。必须在事件模型层解决，事后补账一定错。

03

多租户的难点不在权限，在 KV Cache。它是实例内不可切分的共享显存。租户隔离的真实单位是「实例」，不是「角色」。

04

SLA 的前提是口径统一。连接成功、首 token 成功、完整完成是三个指标。混用会让 SLO 失去约束力，也会让赔付条款无法执行。

05

售前承诺需要工程签字。「承诺—能力」映射表是唯一能挡住过度承诺的闸门；口头承诺的 P99 最终都由架构组偿还。

01第一性原理：一个恒等式

Token 工厂的本质，是把「GPU 小时」这个刚性成本，转换成「可计费 Token」这个柔性产出。转换效率由三个变量决定，其余一切架构都是这三个变量的实现手段。

单百万 Token 成本 C = P × 10⁶ / ( R × 3600 × U × B )

P　单卡小时成本（折旧＋电力＋机房分摊，元/卡时）
R　单卡有效输出吞吐（tokens/s，按计费口径而非裸生成口径）
U　有效利用率（实际出 token 的时长 ÷ 挂载时长）
B　有效计费比（计费 Token ÷ 实际生成 Token，含缓存折扣、失败豁免、免费额度）

这个式子的价值不在于算出一个数，而在于它把五个看似独立的子系统钉在了同一根因果链上：R 由推理平台决定，U 由调度决定，B 由计费模型决定，P 由采购与混部决定。任何一项技术决策，如果说不清它影响哪个变量、影响多少，就不该进入路线图。

1.1敏感性：钱从哪里省出来

以 70B FP8、H100、P=12 元/卡时为基准，逐项做单变量扰动。结论是反直觉的：成本对卡价的弹性只有 1，对利用率和吞吐的弹性是 1.7–2.0。

02总体架构与子系统映射

五层结构，纵向是请求路径，横向是控制面。关键设计是控制面与数据面彻底分离：计费、配额、路由决策都不允许出现在 Token 生成的临界路径上。

图 1 · 赭红标记的是本方案的主要改造点；其余为既有能力或增量较小的部分。

三条贯穿性原则，用来裁决后续所有设计争议：

  • 临界路径只做加法和查表。生成路径上的每个决策（扣费、限流、路由）都必须能在微秒级完成，任何需要 RPC 或锁的操作一律前置或异步化。
  • 事实只存一次。usage 事件是计费、监控、成本核算的唯一事实源。三处各算一遍是账单与看板打架的根因。
  • 降级要有序。失败顺序是：换上游 → 降规格 → 排队 → 明确拒绝。绝不静默失败，也绝不无限重试放大成本。

03推理平台与资源调度

这一项要交付的不是「能跑 vLLM」，而是在给定 GPU 预算下最大化有效吞吐，且不让任何租户的抖动外溢。前者靠引擎，后者靠隔离，两者经常互相矛盾，必须显式取舍。

3.1资源切分：三种隔离强度，对应三种生意

GPU 隔离没有银弹，只有成本与确定性的交换。实践中应把集群按隔离强度分成三个池，而不是追求一种方案通吃。

节点侧统一由 GPU Operator 管理驱动、device plugin 与 DCGM exporter，避免「驱动版本不一致」成为长期故障源。这一层不承载任何业务逻辑，只保证 GPU 资源能被正确声明、切分与观测。

3.4调度：把「闲时」变成钱

利用率的提升只有三条路，必须同时做，单做任何一条都不够：

  1. 流量整形：把可延迟的请求（批量推理、评测、离线生成）识别出来，放进低优先级队列。这是唯一不花钱就能提升 U 的手段。
  2. 混部：在线池在显存水位低于阈值时接受批处理任务，高水位时抢占。抢占必须能在一个 batch 周期内完成，否则会拖垮在线 P99。
  3. 分时复用：白天在线、夜间批处理，用 Kueue 之类的队列配额在时间维度上切分，避免为峰值长期付费。

调度器层面，K8s 原生调度器不理解 GPU 拓扑与显存碎片，需要引入 gang scheduling 与队列配额（Kueue / Volcano 一类）。不要自研调度器——这是典型的投入产出倒挂项。

04计量计费与账务闭环

这是整个平台的「收银台」，也是唯一一处错误不可被用户容忍的模块。设计目标不是「算得准」，而是「在任何异常下都能证明自己算得准」——两者需要完全不同的工程手段。

4.1事件模型：一次请求只产生一条事实

usage_event（不可变，追加写） request_id · billing_group_id · tenant / project / key
model · endpoint · provider · stream · finish_reason
in_tokens · cached_tokens · out_tokens · unit · unit_qty
usage_source: upstream | estimated | mixed
price_version · in_price · out_price · cached_price · fx_rate
amount · currency · status: ok | client_abort | upstream_error | policy_blocked

三个字段值得单独说明，它们决定了后面所有争议能否被裁决：

  • billing_group_id：一次用户语义上的请求。网关内部因上游失败重试 3 次，只归入同一组，只结算一次。没有这个字段，重试会变成重复计费。
  • usage_source：计量数据来自上游返回、本地估算还是混合。对账时按来源分层比对，能立刻区分「模型差异」与「实现 bug」。
  • price_version：结算当时的价格快照。价格表可变，已结算事实不可变。所有退款、重算、审计都基于快照，而不是当前价格。

4.2流式计费：四种情况，四套口径

流式是计费最容易出错的地方，因为「请求结束」有四种互不相同的含义。必须为每种情况定义清晰的计费归属，否则每一次都是人工仲裁。

工程细节 不要对每个 chunk 单独做 tokenize。BPE 合并与多字节 UTF-8 会跨 chunk 边界，逐块编码必然多算或少算。正确做法是维持滑动窗口缓冲（保留尾部若干字节的重叠区），用「累计编码长度差」计算增量，并在 finish_reason 到达时以完整文本重算收敛。所有增量计数只用于过程中的预扣校验，最终结算以完整文本为准。

4.3非标计量：统一到「成本当量」

文本、图片、音频、视频的计量单位不同，但成本都来自 GPU 秒。因此内部需要一个归一化单位（下称 credit），把所有模态折算成同一把尺子，再对外用各自习惯的单位报价。

4.4账务正确性：三条不变式

账务系统的可信度不来自「写得对」，而来自「任何时候都能验证」。为此只允许三条不变式存在，所有实现必须围绕它们：

  1. 余额只能由流水推导。禁止直接 UPDATE balance。任何余额变动必须同时产生一条 ledger 分录，余额是物化视图。退款用反向分录，不改历史。
  2. 预扣恒大于实扣。请求开始按 prompt × in_price + max_tokens × out_price 冻结额度，结束时按实际用量结算并释放差额。这保证超支不会发生，也天然容忍结算延迟。
  3. 日终对账必须收敛。Σledger、渠道实收、客户账单三方差异不得超过 0.1%。差异分类为漏单 / 重单 / 金额差 / 汇率差，各自有自动处置策略。

预付与后付共用同一套 ledger，差异只在结算时点与信用敞口：预付按钱包余额实时扣减，余额不足在请求入口直接返回 402，不允许「先跑后欠」；后付按月结账期出账，需要押金或信用额度，额度用尽自动降级为预付，逾期则冻结调用。两种模式不能靠开关在运行时混用，必须绑定在租户合同上，否则财务无法判断应收。

05多租户、安全与权限

B 端客户买的不是「账号」，是可审计的边界。因此租户模型的设计起点不是角色表，而是「哪些资源必须被证明隔离」——数据、算力、预算、审计，四条各自独立。

5.1三层租户模型

层级与职责 Organization（合同主体 · 结算单位 · 数据边界）
　└─ Team / Project（成本中心 · 配额单位 · 权限范围）
　　　└─ API Key（调用凭证 · 最小授权 · 可轮换）
任意一层都可独立设置预算、模型白名单、IP 白名单与速率上限；子层约束不得超过父层。

把「结算单位」放在 Organization 而不是 Key，是因为发票、账期、信用额度天然属于合同主体。把「配额单位」放在 Project，是因为内部团队的成本归集发生在这个粒度。这两件事混在一起，会导致财务与研发互相不认账。

5.2权限：RBAC 定功能，ABAC 定范围

纯 RBAC 无法表达「这个开发者只能调用白名单内的模型、且只能在办公网段」这类约束。实际需要两层叠加：

  • RBAC：角色 = 一组功能权限（owner / admin / developer / billing / viewer）。解决「能不能做这个动作」。
  • ABAC：策略 = 对资源与条件的约束（project、model、时段、来源 IP、预算余量）。解决「能对哪些对象、在什么条件下做」。

实现上复用现成的策略引擎（Casbin / OPA），不要自研表达式解释器。策略变更必须留审计，且支持灰度：先 dry-run 记录「本会被拒绝」的请求，观察一周无异常再真正生效。

5.3API Key 的六条硬规则

  1. 只存哈希，不存明文；展示时仅显示前缀与后四位。
  2. 支持 scope：模型白名单、端点白名单、额度上限、速率上限、过期时间。
  3. 支持轮换：新旧 Key 并行有效期可配（默认 24h），到期自动失效。
  4. 支持绑定来源：IP / CIDR / 来源标签，越界直接 401 而非 429。
  5. 异常检测：用量突增、跨地域调用、公开仓库泄漏扫描，命中即告警并可一键吊销。
  6. 禁用即失效：吊销走缓存失效广播，收敛时间目标 < 5s，不依赖 TTL 自然过期。

6.4链路追踪与降级链

一条 trace 必须能回答「这 800ms 花在哪」：网关排队 → 路由选择 → 上游 TTFT → Token 传输 → 客户端。采样策略为错误全采、慢请求全采、正常 1% 采样。Prompt 内容默认不进 span，只带长度、模型、租户哈希。

降级链需预先定义并做成可配置，而不是故障时临场决定：

降级顺序（逐级放宽，逐级通知） 同模型备用上游 → 同规格替代模型 → 降规格模型（明示降级）
→ 排队等待（返回预估时长） → 明确拒绝（附重试建议）

6.5弹性扩缩容：扩容靠预热，缩容靠耐心

推理实例冷启动以分钟计（拉镜像、加载权重、图捕获与显存预分配），因此扩容不能靠临时拉起，只能靠预热池。策略分三层：

  • 预留池：常驻 15–20% 空闲实例覆盖日常波动，这部分成本已计入基线利用率，不能算作浪费。
  • 指标驱动扩容：以队列等待 P95 与 TTFT P99 为主指标，而不是 GPU 利用率。利用率是滞后信号，看到 90% 时用户已经在排队。
  • 缩容滞后：缩容窗口不短于 10 分钟，且只在队列为空、活跃会话低于阈值时执行。过早缩容会引发抖动式扩缩，实际成本高于不缩。

跨集群切换是最后一道防线：同城双活吸收单集群故障（RTO < 1 min），异地冷备应对区域性故障（RTO < 30 min）。切换必须支持按租户灰度与一键回滚——整体切流是事故放大器，不是容灾手段。

07售前与客户交付

这一项的本质是把工程能力翻译成客户能审计的承诺。做得好，技术溢价被认可；做得差，每一份标书都是一次未来的赔付。

7.1Sizing：先算并发，再算卡

客户给的是 QPS 和场景，不是并发数。中间需要一步换算，而这一步几乎总被跳过，导致「资源报多了丢标、报少了亏钱」。

容量换算三步 ① 并发会话 N = QPS × 平均会话时长（含排队与生成）
② 显存上限 N_kv = 可用显存 ÷ 单会话 KV 占用
　　单会话 KV ≈ 2 × 层数 × KV 头数 × head_dim × 序列长度 × 精度字节
③ 算力上限 N_c = 集群有效吞吐 ÷ 单会话 Token 速率

实际可承载并发 = min(N_kv, N_c)

举例：Llama-3-8B FP8 部署于单张 48GB 卡，序列 4K、FP16 KV。
单 Token KV ≈ 2 × 32 × 8 × 128 × 2B ≈ 131 KB，4K 序列约 512 MB/会话，可用显存约 36 GB ⇒ N_kv ≈ 70。
该卡实测总吞吐约 3000 Token/s，单会话按 40 Token/s 计 ⇒ N_c ≈ 75。
两者接近时才是平衡配置；若 N_c 远小于 N_kv，问题在算力（应换卡型或量化），反之问题在显存（应加卡或缩短上下文）。

交付纪律 Sizing 必须给出区间与假设，不能给单点数字。「按 4K 上下文、40 Token/s 输出估算，单卡支持 60–75 并发」是可信的；「支持 100 并发」是不可交付的。

7.3交付物清单

  1. 技术方案书：逻辑架构、部署架构、数据流三张图 + 容量与成本测算。
  2. 压测报告：混合负载（长短 prompt、多租户、突发），给 P50/P95/P99 与吞吐曲线，而非单点延迟。
  3. 成本测算表：可复算的 Excel，输入 QPS 与模型即可输出卡数与月成本。
  4. SLA 条款：与承诺矩阵一一对应，含统计口径、排除条款、赔付计算方式。
  5. 私有化清单：离线镜像、License 机制、升级通道、运维移交文档。

其中成本测算表是最容易被低估的交付物。它同时是售前工具和内部定价依据，一旦两边用同一份模型，报价与成本就不会脱节。

08落地路线与验收

顺序由「错了以后最难补救」决定，而不是由「技术上最想做的」决定。计费错误会直接摧毁客户信任且无法追溯，因此排第一；引擎优化可以随时补，排后面。

P00–2 月计费可信 + 看得见。usage 事件模型、流式四场景计数、双分录 ledger、指标字典与 L3 口径。验收：对账差异 < 0.1%，任一请求可逐条下钻到成本。
P13–5 月多租户可卖。Org/Project/Key 三层模型、配额树、价格版本与快照、L2 隔离。验收：单租户无法影响他人 P99（同池抖动 < 1.2×）。
P26–9 月成本可优化。分层队列、抢占式批处理、MIG 池化、Top 5 模型换 SGLang 专项调优。验收：在线池 U ≥ 0.45，混部池 ≥ 0.65。
P310–12 月规模化交付。多集群容灾、私有化交付流水线、Sizing 计算器与承诺矩阵进销售流程。验收：标准项目交付周期缩短 50%。

8.1为什么 P/D 分离排在 P2 之后

它需要稳定的流量结构、可靠的 KV 传输层、以及能承受更大故障面的运维能力。在 P0/P1 阶段引入，会把「计费不准」和「推理不稳」两类问题混在一起，导致故障归因失效。工程上，先让系统可解释，再让它更快。

09对抗审查：这套方案的脆弱假设

任何架构方案都是一组假设的集合。有价值的不是证明它对，而是提前说清它在什么条件下会错，并为每个假设配一个可观测的证伪指标。

9.2本方案主动放弃的东西

  • 不做统一推理抽象层。试图用一个接口屏蔽 vLLM / SGLang / TRT-LLM 的全部差异，会让每家的特性都用不上。改为：网关层统一协议，引擎层各自最优。
  • 不做自研 tokenizer。多模态与多模型的 tokenizer 差异是长期债，一律用官方实现 + 版本锁定，升级走回归测试。
  • 不做实时毛利计算。成本核算按小时批量，实时性对经营决策没有价值，却会拖垮结算链路。
