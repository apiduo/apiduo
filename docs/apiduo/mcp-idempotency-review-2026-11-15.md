# MCP 幂等与异步任务：对抗审查（2026-11-15）

针对三个问题：同步任务要不要幂等？要不要存图片？异步视频那条链路有什么问题？
结论都建立在线上实测上，`0.0.147` 之后、`0.0.148` 之前。

---

## 0. 一句话结论

| 问题 | 结论 |
|---|---|
| 同步任务要幂等吗 | **要，但不是为了防重复扣费** —— 它是「客户端断开后还能把结果取回来」的唯一通道。实测：断开 5 秒，服务端照常跑完、扣费、存结果；同键重放拿回那张图，0 计费 |
| 要存图片吗 | **不存**。原来的代码允许 `b64_json` 进表（上限 256 KB），已改成只存 URL |
| 异步视频 | 句柄设计是对的（自包含、零状态），但**超时后释放幂等键会直接导致二次扣费**，已修；另有 3 处建议 |

---

## 1. 同步：为什么幂等是承重的

### 1.1 先看它到底是不是「纯透传」

不是。MCP 在 apiduo 同步 API 之上加的东西：

| 层 | 做的事 |
|---|---|
| 前 | 能力目录挑选默认模型、参数归一（size→比例、extra 展开）、本地校验（越界参数直接拒绝，不出站） |
| 中 | 用调用方的 sk 调 `/v1/images/generations`（计费完全复用 sk，MCP 不碰钱） |
| 后 | 产物解析、text 渲染、观察样本、幂等结果 |

所以「本质是调用 apiduo 的同步 API」是对的，但**它不是无状态转发**：一次生成 30–350 秒，这期间连接随时可能断。

### 1.2 断线实验（决定性的那个）

```
18:42:52  发起 image.generate（qwen，client_request_id=e2e-cancel-1），第 5 秒主动断开
18:42:55  幂等行：pending
18:44:12  账本出现 5000（这张图确实生成了）
18:44:12  幂等行：done，result 321 字节
18:45:xx  同键重试 → replayed=true，同一个 URL，账本没有第二条
```

关键点：**客户端走了，MCP 没走**。它把生成跑完、把 URL 存下来。

没有这张表会怎样：同样的断线，结果只剩一条账单，URL 找不回来（relay 的 logs 里只有计费参数，
没有产物地址）。所以「同步不需要幂等」不成立 —— 它恰恰是断线后唯一的找回路径。

> 这个行为依赖部署：当前 apiduo.cn 前面有反代，客户端断开没有传播到 MCP 的请求上下文。
> 换成直连 + 支持取消的传输层，行为可能变成「断线即取消」，那时幂等行会停在 pending。
> **不要把「断开后还能跑完」当成协议保证**，它只是当前部署的事实。

### 1.3 但它存的东西不对（已修）

`completeIdempotency` 存的是整个 `generateOutput`，其中 `outputs[].b64_json` 是**图片字节**。
虽然我们发的是 `response_format=url`，但有些渠道会忽略它照旧回 base64 —— 那就会把几 MB
的图片塞进 MySQL，24 小时，重放时再塞回上下文。

现在的行为：

- 只存 `url`；`b64_json` 一律剥掉；
- 全是 b64、没有 URL 的产物直接丢弃，并在 text 里注明「其中 N 个以 base64 内联返回，未缓存」；
- 剥的时候**新开切片**，不原地裁剪 —— `out.Outputs` 和返回给调用方的是同一个底层数组，
  原地改会把本次响应的图片也一起清掉（这个坑写测试时踩到了，已有用例守住）。

### 1.4 真正的洞：超时后把键释放了（已修，P0）

原代码：

```go
if err != nil {
    if in.ClientRequestID != "" {
        releaseIdempotency(...)   // 任何上游错误都释放
    }
    return d.fail(m.ID, err)
}
```

超时的时候，请求已经在路上、上游很可能已经受理并计费。**释放键 = 放行下一次重试 = 第二次扣费**。
我们之前看到的 `n=4` 那次（301s 超时、账本 20000、URL 全丢）如果换了同一把键重试，就会再扣一次。

现在的判定不是「有没有错误」，而是「**这次调用到底发生没发生**」：

| 情形 | 处置 | 理由 |
|---|---|---|
| 编码/构造请求失败 | 释放 | 请求没离开进程 |
| 拨号超时 | 释放 | 连接都没建立 |
| 上游返回 4xx/5xx | 释放 | 有状态码，结论已知 |
| **等响应超时** | **不释放，标记 done** | 可能已计费；重放时明确说「结果未取回，去后台确认，不再重新生成」 |
| 200 但响应体解析失败 | 不释放 | 结论未知，宁可让调用方查后台 |

宁可多一次「去后台看看」，也不要悄悄生成第二次。

### 1.5 顺带修的：查询类调用的超时

原来所有上游调用共用一个 8 分钟的 http.Client。`task.get`（纯读）和 `models.list` 也被这个
8 分钟罩着 —— 一次轮询卡住 8 分钟，agent 的整个循环就停在那里。现在：

| 调用 | 超时 |
|---|---|
| 生成（同步图 / 异步提交） | 8 分钟（客户端级） |
| `task.get` | 30 秒 |
| `models.list` | 15 秒 |

## 2. 异步视频：句柄这条线是对的

### 2.1 设计对照

| 关注点 | 现状 | 评价 |
|---|---|---|
| 句柄 | HMAC 自包含 `{model, upstream, kind, uid, t, e}`，服务端零状态 | ✅ 重启、换副本都能查 |
| 归属 | 句柄里绑 `UserId`；查询时 relay 的 `GetByTaskId(c.GetInt("id"), taskID)` 再按用户过滤一次 | ✅ 两道锁 |
| 过期 | 7 天，`TASK_ID_EXPIRED` 明确指到后台 | ✅ |
| 伪造 | 无密钥不可签 | ✅ |
| 查询成本 | relay 只读本地 `task.Data` 快照，不调上游、不写日志 | ✅ |
| 幂等 | 存的是「提交结果」（task_id），重放返回同一个句柄 | ✅ 有价值（同断线场景） |

### 2.2 仍然存在的三个问题

**P2 · `upstream` 全量回显，占响应体 46%**

一次 `task.get` 共 1012 字节，其中 `structuredContent.upstream` 465 字节、text 123 字节。
轮询 30 次就是 30 份同样的上游对象，里面还有 `model: "happyhorse11"`（provider 模型名）
与 `id: cgt-...`（provider 任务号）。

agent 真正需要的只有 `status / outputs / error / poll_after_ms`。建议 `task.get` 不再回
`upstream`（`generate` 保留，首包有排障价值）。

**P2 · `task.get` 没有限流**

`models.list` 有 60 次/分钟的 per-token 窗口，`task.get` 没有。虽然它只是 DB 读，
但轮询是所有工具里频率最高的那个：一个 agent 同时盯 10 个任务、5 秒一轮就是 120 次/分钟。
建议同一套窗口，阈值放宽到 120 次/分钟。

**P3 · 任务失败一律标「不可重试」**

```go
out.Error = &toolError{Code: CodeTaskFailed, Retryable: false, RetryAction: "none",
    Hint: "不要用同样参数重试；先确认参数或换模型"}
```

但 `fail_reason` 可能是 `upstream reported failure` 这种瞬时错误（我们自己就复现过 502）。
对 `upstream error` 类原因建议走 `matchErrorRule`，给出可重试 + 退避；内容违规类保持不可重试。

### 2.3 幂等解决不了的那个洞

MCP 在「relay 已经建了任务」和「签发句柄并返回」之间崩溃 → 幂等行停在 pending，
10 分钟后被当作陈旧占位接管 → 重试**又建一个任务**（再扣一次），而第一个任务还在跑。
用户会在后台看到两个任务。

这不是幂等表能修的：它需要 relay 在**建任务时**按 `(token, client_key)` 去重。
当前的幂等表只是把这个窗口从「立刻重复」推迟到「10 分钟后重复」。

### 2.4 重放拿到的是「提交时」的文本（P3）

`video.generate` 的重放返回 `已提交（模型 …），任务 … 进行中`，即使任务早就完成了。
agent 会照着这句话去 poll 一次，多一次往返。可以在重放时按 `task_id` 查一次当前状态再渲染
（查询是本地读，代价很小），或者至少在文本里注明「这是提交时的结果」。

## 3. 这轮改了什么

| 文件 | 改动 |
|---|---|
| `mcp/protocol_upstream.go` | `errNotSent` / `errUpstreamTimeout.BeforeSend`；生成 8 分钟、查询 30 秒、`/models` 15 秒；网络错误抹掉内网地址 |
| `mcp/protocol_tools.go` | `shouldReleaseIdempotency`：只有「确定没发生」才释放键；等响应超时标记 done |
| `mcp/idempotency.go` | 幂等结果只存 URL，剥掉 b64；不原地改调用方的切片 |

测试：`TestShouldReleaseIdempotency`（6 种错误）、`TestCompleteIdempotencyDropsInlineButKeepsResponse`
（表里没有 b64、调用方的对象没被改）。

## 4. 没做，留给你决定

1. `task.get` 去掉 `upstream`（省 46% 响应体）。
2. `task.get` 加 per-token 限流。
3. 失败任务按 `fail_reason` 分类可重试性。
4. 重放时刷新异步任务的当前状态。
5. relay 侧按 `(token, client_key)` 在建任务处去重 —— 这是 2.3 的唯一正解，但属于 relay，不是 MCP。
