00一页纸结论

不拥有 GPU，就等于不拥有成本曲线的分母。网关能动的只剩分子——采购价、重试浪费、计费覆盖。因此本方案的目标函数不是「更便宜」，而是让「赚了多少、漏在哪」成为一个可以每天回答的问题。

01

薄毛利生意的弹性全在成本侧。售价 10、上游 7、放大 1.10 时毛利约 18%。上游成本基数是售价的 70%，所以重试放大 10 个百分点，等于吃掉 39% 的利润；而固定成本砍 20%，只换来 6%。

02

计费精度的价值不在那 2%，在它是否可信。漏计的直接损失有限，但它会让「上游成本对不对、重试有没有放大」失去基准。所有优化都建立在同一份事实上，否则连赚没赚钱都判断不了。

03

收入与成本必须分账核算，不能强行对齐。上游按自己的 tokenizer 计费，本地按自己的估算收费，2–8% 的偏差是常态。强行对齐会让两边都不准；正确做法是各自成账，在批次层算毛利。

04

SLA 等级 = 冗余等级。不拥有算力时，可用性只能靠「异构上游 + 独立账号池」堆出来。同一供应商多开账号不是冗余。

05

fallback 有静默降质风险。不同上游对 tool-calling、长上下文、结构化输出的支持不一致，切换成功但能力缺失，比直接报错更难被发现。

01第一性原理：薄毛利的三个漏点

网关的毛利等于「售价减上游成本」，而成本基数占售价七成以上。这个结构决定了：任何作用在成本侧的比例损耗，都会被毛利的小分母放大。这就是为什么网关的运营重点永远是「堵漏」，而不是「省固定开销」。

单位毛利（每百万 Token） m = Price × B − Pup × A − F

Price　对外售价　　　　B　计费覆盖率（已结算 ÷ 实际消耗）
Pup　上游单价（按 Token 或按次折算）　　A　重试放大系数（上游计费量 ÷ 已结算量）
F　　固定成本分摊（带宽、存储、日志、人力）

A 这个指标值得单独定义，因为它是网关特有、且几乎没人放在看板上的量。A = 上游实际计费 Token ÷ 平台已结算 Token，理想值 1.00。它把四类浪费合并成一个可比数字：上游失败后重试、流式中断后的重发、客户断连后服务端继续生成、以及对冲请求（hedging）。

1.1敏感性：利润被什么吃掉

基准取值：售价 10 元/百万、上游 7 元/百万、A=1.10、固定成本 0.5 元/百万，利润 1.8 元/百万（毛利率 18%）。逐项单变量扰动：

重试放大 1.10 → 1.20−0.70
售价 +5%（分层定价，量不变）+0.50
重试放大 1.10 → 1.03+0.49
上游采购价 −5%+0.39
漏计率 2% → 0.5%+0.15
固定成本 −20%+0.10

图 1 · 各动作对单位利润的绝对影响（元/百万 Token），基准利润 1.8 元。

这个算例仍然偏乐观：它没有计入支付通道费（约 0.6%）、发票税负、免费额度消耗与退款。补齐之后，真实毛利率通常再低 2–4 个百分点。18% 应理解为上限估计，而非经营现状——这也是后文结论一律用「相对变化」表述、不依赖绝对值的原因。

判断 优先级由此确定：重试治理 > 采购议价 > 定价分层 > 计费精度 > 固定成本优化。把效率工程放在前面是典型误判——省下的运维开销在利润表上几乎看不见，而一次上游批量 5xx 引发的重试风暴可以在几小时内抹掉一个月的利润。

1.2计费精度为什么仍要排进第一梯队

从图 1 看，把漏计从 2% 压到 0.5% 只值 0.15 元。这个数字不足以支撑「计费是核心」的说法，但漏计还有一个二阶效应：它同时污染了判断其它一切的基准。

  • 漏计与「上游成本偏高」在账面上长得一模一样，都会表现为毛利偏低。分不清是哪一种，就无法决定该去谈判还是该去修 bug。
  • 漏计通常不均匀：流式、长上下文、多模态是重灾区。整体 2% 的偏差，在这些场景可能到 10%，导致单模型毛利被严重误判。
  • B 端客户会审计账单。一次「说不清为什么是这个数」的争议，损失的是续约，不是那 0.15 元。

所以计费的定位不是「多赚钱」，而是让所有其它决策有一个可信的度量基。这也是路线图把它排进 P0 的唯一理由。

1.3A 不是一个数，是五项浪费的合计

把 A 当成一个可以直接「优化」的指标是危险的：它只会引出「加强重试管理」这一条对策，而重试通常只占三分之一。必须先拆到可归因的分项，才能决定该改哪一段代码。

损耗分解 A = 1 + ( W₁ + W₂ + W₃ + W₄ + W₅ ) ÷ 已结算量

W₁ 重试重复　上游失败后重发，前一次已产生的消耗
W₂ 中断残值　上游中途断开，已计费但未交付
W₃ 断连继续　客户端断开后服务端未及时停止生成
W₄ 对冲请求　同一请求并发发往两家
W₅ 计量缺口　上游已计费，本地未记录
表 1 · 损耗分项：占比、采集与治理
分项典型占比采集方式治理手段见效周期
W₁ 重试重复30–50%attempt 序号 + 每次 attempt 的用量不可重试判定、重试预算周
W₂ 中断残值15–30%失败原因 + 已接收长度熔断、降级链月

占比为经验区间，须以自测数据替换；长上下文场景的 W₂ 会显著高于表中值。

归因陷阱 W₅ 会同时让 B 下降、A 上升——同一个漏记事件在两个指标里各出现一次。做损耗分析时只能选一个口径归因，否则会把同一个漏洞算两遍，得出「漏损比实际严重一倍」的结论。

另一条容易被忽略：A 的目标值必须按模型分档。长上下文模型的 W₂ 占比高（一次中断的绝对损失大），短请求模型由 W₁ 主导。全局设 1.08，会掩盖某个模型其实已经 1.30 的事实——应按「模型 × 渠道」双维度看。

2.1上游三契约：不拥有算力时唯一能拿到的控制权

把 GPU 移出范围之后，网关的很多能力会退化成猜测。避免退化的唯一办法是：把需要上游提供的信息写成契约，作为接入的准入条件。

这三条的价值在于：每一份缺失的契约，都会在账上变成一笔看不见的成本。接入评审时把「是否满足三契约」列为必填项，比事后调优便宜一个数量级。

2.2三条贯穿原则

  • 临界路径只做加法和查表。扣费、限流、路由判定必须在微秒级完成，任何跨服务调用一律前置或异步。
  • 事实只存一次。usage 事件是计费、监控、成本核算的唯一源。三处各算一遍，必然出现两套数字。
  • 失败要有序且不可放大。换上游 → 降规格 → 排队 → 明确拒绝。任何一层都不得「重试到底」。

03计量计费与账务闭环

现有实现已经解决了「算得出来」：按次、按秒、按 token 三种模式可以共存，预扣与结算也跑得通。本方案要补的是「算得过去」——流式、缓存、重试、改价四种情况同时出现时，账仍然对得上、且能逐条解释。

3.1三个口径，三本账

网关最容易犯的结构性错误，是试图用一个数字同时承担三件事。正确做法是明确分开，再在对账层收口：

表 3 · 三本账的定义与关系
账本计量口径数据来源用途
收入账本地 tokenizer（或上游回传）usage 事件 × 价格快照客户账单、余额
成本账上游计费口径上游账单 / usage 回传毛利核算、采购决策
损耗账差异量（A 的分解）两侧差额按失败类型归因重试治理、稳定性投入

不要在单请求层算毛利。单请求的两个口径必然不等，强行对齐只会得到一个既不准也无法审计的数。正确粒度是「模型 × 日」，两侧各自汇总后相减，差异再按失败类型分解。

3.2流式计费：四种结束方式，四套口径

流式的计费难点不是计数，而是「请求什么时候算结束」。四种结束方式必须各自定义，否则每次异常都要人工仲裁：

表 4 · 流式场景的计费归属

工程细节 不要对每个 chunk 单独 tokenize。BPE 合并与多字节 UTF-8 会跨 chunk 边界，逐块编码必然多算或少算。做法是维持滑动窗口缓冲（保留尾部重叠区），用「累计编码长度差」算增量，最终以完整文本重算收敛。增量计数只服务于过程中的预扣校验，结算一律以完整文本为准。

3.3预扣：现有半量预扣的透支风险

当前实现对按 token 计费的模型按 ratio / 2 × QuotaPerUnit 预扣，即预扣约等于「半个价格单位」的额度。这在短输出下够用，但存在两个边界：

  • 长输出透支：输出 4K Token 的请求，实际消耗远超预扣量，高并发下会出现「余额已为负但请求仍在跑」。
  • 预扣与 max_tokens 脱钩：请求里声明的 max_tokens 是最坏情况上界，预扣却按常量给，两者没有关系。

建议改为按请求上界预扣：hold = 输入估算 × 输入价 + min(max_tokens, 模型上限) × 输出价，结束时按实际结算并释放差额。代价是并发请求的冻结额度变高，需要同时把「冻结额度」纳入余额展示，否则用户会误以为被多扣。

3.4非标计量：统一到成本当量

文本、图片、音频、视频的计量单位不同，但成本都来自上游的计费口径。内部需要一个归一单位（credit），把所有模态折算成同一把尺子，对外再用各自习惯的单位报价。

3.5改价与缓存：两个最容易被忽略的漏点

改价。当前的价格由 ModelRatio / ModelPrice 与分组倍率相乘得到，都是全局可改的配置。请求结算后若没有价格快照，一旦运营调整倍率，历史账就无法重算，退款与审计都失去依据。解决方式很轻：结算时把实际生效的倍率写进 usage 事件，价格表可变，已结算事实不可变。

缓存。上游的 prompt caching 有独立的计费口径（cache write 与 cache read 单价不同）。如果网关只透传 cache_control 而不区分计量，就会出现「按全价卖、按折扣价买」的额外收益；一旦上游调整策略或反向涨价，这笔收益会瞬间变成亏损，而账面上看不出来。要求是：usage 事件必须区分 cached 与 uncached 的输入 Token，定价表也必须能对两者分别定价。

3.6账务三条不变式

  1. 余额只能由流水推导。禁止直接改写余额字段，任何变动必须同时产生一条 ledger 分录，余额是物化视图。退款用反向分录，不改历史。
  2. 预扣恒大于实扣。预扣按请求上界冻结，结算按实际用量多退少补。这保证超支不发生，也天然容忍结算延迟。
  3. 日终对账必须收敛。Σledger、支付渠道实收、客户账单三方差异不超过 0.1%，差异分类为漏单 / 重单 / 金额差 / 汇率差，各自有自动处置策略。

3.7预付与后付

两者共用同一套 ledger，差异只在结算时点与信用敞口：预付按余额实时扣减，余额不足在入口直接返回 402；后付按月结账期出账，需要押金或信用额度，额度用尽自动降级为预付，逾期冻结调用。两种模式不能靠开关在运行时混用，必须绑定在租户合同上，否则财务无法判断应收。

3.8计费异常补偿

对账负责发现问题，补偿决定问题会不会演变成事故。这里的原则与常规财务相反：多收必退，少收不追。理由不是慷慨，而是两类错误的代价不对称——多收一次，客户会重新审计你所有的历史账单；少收一次，只是一笔可计入损耗的成本。

少计（大额）差额 ≥ 阈值商务沟通后分期调整不得在下一期账单突然补扣
服务未达标未达承诺矩阵档位按条款赔付，优先赔付额度附统计口径与原始数据

三条执行约束：

  • 补偿走反向分录与独立科目，不改历史账单。直接改数会让审计链断裂，也会让「这个月为什么和上个月对不上」变成永久的解释成本。
  • 少计不自动追缴。突然补扣是信任事件，不是财务事件。大额差异宁可谈成折扣，也不要出现在账单里。
  • 赔付优先用额度而非现金。保留收入、降低现金流压力，且额度最终会被消费掉。

04多租户、配额与权限

网关的租户隔离比推理平台简单——没有显存这类不可切分的资源。但它有另一个难点：流式请求的长连接特性，让「按 QPS 限流」失去意义。一个 30 秒的流式请求占用的不是一次调用，而是一段持续的上游配额。

4.1三层模型

层级与职责 Organization（合同主体 · 结算单位 · 数据边界）
　└─ Project（成本中心 · 配额单位 · 权限范围）
　　　└─ API Key（调用凭证 · 最小授权 · 可轮换）
任意层可独立设置预算、模型白名单、IP 白名单与速率上限；子层约束不得超过父层。

把「结算单位」放在 Organization 而非 Key，是因为发票、账期、信用额度天然属于合同主体；把「配额单位」放在 Project，是因为成本归集发生在团队粒度。这两件事混在一起，会导致财务与研发互相不认账。

4.2配额：三个维度，缺一不可

表 8 · 配额维度与失效后果
维度单位为什么必须有典型取值
金额预算元 / 周期最终兜底，防止账单超预期按合同，80% 预警
并发请求数在途请求流式长连接的真实资源占用按档位 5 / 50 / 500
Token 速率TPM / RPM与上游配额对齐，防单租户打满渠道按档位阶梯

只做 RPM 限制是常见的错误：100 个 RPM 的租户若每个请求都跑 60 秒，等效于 100 个常驻连接，足以耗尽一个渠道的并发。并发数才是与上游能力对齐的那个量。

4.3权限：RBAC 定功能，ABAC 定范围

  • RBAC：角色 = 一组功能权限（owner / admin / developer / billing / viewer），回答「能不能做这个动作」。
  • ABAC：策略 = 对资源与条件的约束（Project、模型、时段、来源 IP、预算余量），回答「能对哪些对象、在什么条件下做」。

实现上复用既有策略引擎，不自研表达式解释器。策略变更必须留审计，且支持 dry-run：先记录「本会被拒绝」的请求，观察一周无异常再真正生效。

4.4模型权限：三层交集与状态码语义

模型黑白名单不是一张表，而是三层的交集：合同允许集（Org 上，来自签约）→ Key 白名单（子集，最小授权）→ 请求级条件（时段、IP、预算余量）。任何一层拒绝即拒绝，且内部拒绝原因不回传给调用方。

表 9 · 拒绝语义：状态码本身是信息
情形返回理由

4.5API Key 的六条硬规则

  1. 只存哈希不存明文，展示时仅给前缀与后四位。
  2. 支持 scope：模型白名单、端点白名单、额度上限、速率上限、过期时间。
  3. 支持轮换：新旧 Key 并行有效期可配（默认 24h）。
  4. 支持绑定来源：IP / CIDR 越界直接 401，而非 429。
  5. 异常检测：用量突增、跨地域调用、公开仓库泄漏扫描，命中可一键吊销。
  6. 吊销即失效：走缓存失效广播，收敛目标 < 5s，不依赖 TTL 自然过期。

05可观测性与 SLA

不拥有上游时，可观测性的作用从「调优」变成「举证」：既要向客户证明服务达标，也要向自己证明成本没有漏。所以指标必须同时覆盖体验、健康、成本三类，且都与计费同源。

不拥有算力，可用性只能靠冗余堆出来。这决定了 SLA 不是「服务水平」的表述，而是一个采购决策：承诺几个 9，就要买几份冗余。

5.6渠道调权与自动摘除

这是「自动扩缩容」在网关侧的实际形态：不扩机器，只调流量分配。判据不能只看成功率——成功率对慢渠道不敏感，用户早就走了它仍然是 100%。

健康分与权重 H = w₁ × 成功率 + w₂ × ( 1 − TTFT_p95 ÷ 基准 ) − w₃ × 429率
权重 = H × 成本系数　　（成本系数仅在 H 达标时参与排序）
建议 w₁=0.5、w₂=0.3、w₃=0.2；权重每 60s 重算，按业务调。

三条防震荡约束，缺一条都会得到「权重来回跳、流量打摆」的结果：

  • 最小驻留：单渠道权重调整后 5 分钟内不再变动。
  • 幅度限制：单次调整不超过当前权重的 20%；严重异常直接摘除，不走降权。
  • 半开恢复：摘除后按指数退避放 1% 流量探测，连续成功 3 次恢复，而不是等定时器。
与成本的关系 成本系数只能在健康度达标后参与排序。若把「便宜」并进健康分，结果必然是「便宜渠道一直有量，即使它已经在超时」——成本优化必须建立在可用性约束之上，不能与之并列。

06售前：容量、承诺与报价

这一项要把工程能力翻译成客户可审计的承诺。没有 GPU 之后，售前最关键的三个数字变成：要几个渠道、要不要签承诺量、能承诺几个 9。三者互相约束。

6.1容量规划：从 QPS 到渠道数

四步换算 ① Token 需求　TPM = QPS × 60 × (输入 + 输出 Token 均值)
② 并发需求　　N = QPS × 平均请求时长（流式按时长算，不是按次）
③ 单渠道上限　取实测 TPM 与实测并发的小值（不用标称值）
④ 渠道数　　　= ceil(峰值 × 1.3 ÷ 单渠道上限) × 冗余等级系数

第 ③ 步的「实测」是整条链路上最容易被跳过、也最容易出事的一步。供应商标称的 TPM 通常标注了「共享池」前提，实际可用额度取决于同池其他租户。做法是：接入后跑 72 小时基线，取 P95 的实际吞吐作为单渠道上限，而不是产品文档上的数字。

6.2承诺用量：什么时候该签

预留折扣看起来总是划算，但它把「按量付」变成了「固定成本」，风险从供应商转移到自己身上。盈亏平衡点很简单：

承诺量决策 设按量单价 p，预留折扣 d，承诺量 Qc，实际用量 Q

Q ≥ Qc　→　节省 ＝ p × d × Qc
Q < Qc　→　多付 ＝ p × [(1−d)Qc − Q]

盈亏平衡：Q* = (1 − d) × Qc

算例：折扣 20%、承诺 1000 万 Token/月，则月用量低于 800 万时，按量反而更便宜。决策规则应写进售前流程：只有过去 3 个月用量的 P10 分位不低于 (1−d)Qc 时，才签承诺量。这条规则能挡掉大部分「为了拿折扣而承诺、结果闲置」的浪费。

6.4交付物

  1. 技术方案书：逻辑架构、请求链路、上游冗余拓扑三张图。
  2. 压测报告：混合负载（长短 prompt、多租户、突发），给 P50/P95/P99 与吞吐曲线，而非单点延迟。
  3. 成本测算表：输入 QPS 与模型分布即输出月成本与毛利，可复算。
  4. SLA 条款：与承诺矩阵一一对应，含统计口径、排除条款、赔付计算方式。
  5. 私有化清单：离线镜像、License、升级通道、运维移交文档。

其中成本测算表最容易被低估：它同时是售前工具与内部定价依据，两边共用同一份模型，报价与成本才不会脱节。

07落地路线与验收

排序依据是「错了以后最难补救」。账错了无法追溯，重试放大无法回滚，所以前两期都在修漏水；能随时补的能力往后排。

P00–2 月把事实立起来。usage 事件模型（含 billing_group、price_version、usage_source）、流式四场景计数、ledger、A 与漏计率上线。验收：对账差异 < 0.1%，任一请求可逐条下钻。
P13–5 月把漏水堵住。重试治理（不可重试判定、重试预算、全局过载信号）、预扣改上界、缓存分账。验收：A ≤ 1.08 且成功率不降。
P26–9 月把租户做厚。Org / Project / Key 三层、配额三维度、价格版本、预算告警。验收：单租户无法影响他人 P99（同档抖动 < 1.2×）。
P310–12 月把交付标准化。异构冗余与切流演练、SLA 分级、容量计算器进销售流程。验收：标准项目交付周期缩短 50%。

7.1为什么重试治理排在多租户之前

多租户影响的是「能不能卖给企业」，重试放大影响的是「每一笔交易赚不赚钱」。前者是增长问题，后者是存活问题——在毛利 18% 的结构下，A 从 1.10 恶化到 1.20 会让利润腰斩，而多租户晚三个月上线只是少签几单。

7.2先测量：七天拿到 A 的真实值

整套方案依赖一个前提——A 现在到底是多少。这个数不需要等账务系统建好才能知道：一张埋点表加一周真实流量就够。建议在任何代码改造之前先做，因为它同时给出「值不值得做」的答案。

表 15 · 七天测量计划

SLA 达标，fallback 率高冗余起了作用主上游能力不足，指标靠降质维持
毛利稳定，客单价下降业务健康高价值客户在流失，留下的是低毛利流量
收入增长，单租户毛利转负规模效应定价低于成本，在用增长掩盖亏损

8.2主动放弃的东西

  • 不做语义缓存。跨租户的语义命中存在串话与数据泄漏风险，收益远小于责任。只做上游 prompt cache 的透传。
  • 不做统一 tokenizer 对齐。上游按自己的口径计费，本地按自己的口径收费，强行统一只会两边都不准。分账核算即可。
  • 不做实时毛利。成本以账单为准，必然是 T+1。实时只能给「估算毛利」，且必须明确标注，否则会与财务报表打架。
  • 不做对冲请求（hedging）默认开启。它用成本换长尾延迟，只在明确付费的高价值场景按租户开启。

09与现有代码的差距清单

本方案不以重写为前提。现有多数能力可以复用，缺口集中在「事实模型」与「成本可见性」两处，且都能以增量方式接入。

按此映射，P0 的真实工作量是事件模型 + 账务层两块，不涉及网关主链路重写。这正是把「计费可信」放第一位的可行性依据：它不是一个大工程，而是一个必须先做的小工程。

待核实项 表中「重试」一行标记为待核对：流式响应已经开始向客户端输出后，若上游中断，当前实现是否会重新发起上游请求。若会，则每一次这类重试都会产生整段重复成本，是 A 的最大单一来源。这条应在 P0 期间用日志验证，而不是靠代码推断。
