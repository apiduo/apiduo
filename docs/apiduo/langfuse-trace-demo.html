日志页接入 Langfuse Trace

请求体、流式帧、非流式响应全采，含 agent 的 messages 与 tool_calls。主链路只多一次 memcpy —— SSE 不需要 tee，因为 dataHandler 拿到的已经是帧明文。日志页只多一个链接，且仅管理员可见。

旁路新增 既有链路 主链路不改 I/O 形态：不读 body、不 tee 响应、不序列化

关联键不落库

OTEL 要 32 位 hex，NewAPI 的 request_id 是 39 位。取 sha256(request_id)[:16] 派生，写进 other.admin_info，不动 ClickHouse 表结构。

collector 状态机 + 唯一上报点

各挂接点只向 collector 写状态（帧 append、usage 填充），relay defer 统一 finalize——成功、失败、panic 全覆盖，失败请求也有 trace。异步任务结算无 defer，走 RecordConsumeLog 兜底快照。

权限两道闸

SetAdmin 让普通用户拿不到 trace_id；链接由 props.isAdmin 门控。Langfuse 没有行级隔离，这道闸不能省。

第一原则 · 不影响原有系统性能

三档方案的开销

数字来自本机实测（M1 Max / go1.26），不是估算。三档差的不是实现难度，是同一件事：这段数据要不要跨出请求的生命周期。

条形按线性刻度绘制。差距只有 32 倍，不需要对数压缩——A 档短到看不见，正是它真实的样子。

C 档 · 全内容采集（推荐）

请求体 + 流式帧 + 非流式响应全采。关键在于 SSE 不需要 tee——StreamScannerHandler 的 dataHandler 已经拿到去掉 data: 前缀的帧明文，包一层即可，每个 chunk 零额外系统调用。

截断是真正的分水岭

全量 500 KB 要 +11.6 μs、512 MB 千并发；截成头 32 K + 尾 16 K 只要 +0.6 μs、48 MB。开销降 20 倍，内存降 10 倍，代价是长回答标 truncated。

我之前算错了一百倍

上一版把 SSE tee 估成「每 chunk 1 μs、1000 chunk ≈ 1 ms」，于是判定 C 档违反第一原则。错在把本来就要发生的 write 算成了新增成本。实测是 11.6 μs，不是 1 ms。

C 档还在第一原则之内吗

全量 11.6 μs 是 A 档的 32 倍，但这个倍数没意义，要看绝对值：摊到一次 3–8 秒的流式请求上是 0.0002%。真正的成本不是 CPU，是 buffer 内存——512 MB 千并发。所以默认截断到头 32 K + 尾 16 K，把内存压到 48 MB，CPU 顺手降到 0.6 μs。这不是性能妥协，是内存账。
