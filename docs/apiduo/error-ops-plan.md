## 六、执行中的判断修正（2026-11-16）

原计划有一项「把 dashboard 的 flow / models / capacity 迁到 quality 台」。实际读代码后**取消**。

### 原因

| 组件 | 实际内容 | 与 quality 台的关系 |
|---|---|---|
| `flow` | **桑基图**：用户 → 节点 → 模型的流量分配，带节点过滤与宽度指标 | quality 台只有错误率/延迟时间线，**完全没有流向拓扑** |
| `models` | 调用次数、平均延迟、成功率、吞吐、消费分布、目录健康度与字段覆盖率 | quality 台只有请求/失败/p50/p95，**没有消费与元数据视角** |
| `capacity` | 容量预测：95% 区间、实际 vs 基线、按渠道/模型日均 | quality 台**没有预测能力** |

三者都不是重复实现，是不同的问题域。强行迁进 quality 台，会让它从「服务质量」变成「什么都放一点的杂货铺」。

### 修正后的职责

```
/dashboard   平台分析   流向拓扑、消费分布、容量预测、模型目录
             └ 普通用户看 overview / my-keys / sk；管理员额外看 models / flow / capacity / users
/growth      客户运营   分层、余额健康、预警、触达、批次
/service-health  服务质量   错误率、延迟、聚类、变更、值班
```

`sk` 下放已经完成（普通用户可用），`models`/`flow`/`capacity`/`users` 保持管理员专属是**正确状态**，不是遗留。

### 教训

判断「两个功能是否重复」，只能看内容和数据源，不能看名字。
`Flow` 这个名字让人以为它是「流量曲线」，实际是一张流向图。

## 七、更正：第三节第六项「取消迁移」是错的（2026-11-16 晚）

上一节用 `git log --author` 判断组件归属，得出「retention 是 new-api 原生」的结论。**这个判断方法本身是错的。**

`apiduo` 是 `QuantumNous/new-api` 的 fork，两条提交线是同一个作者（Betterme）。作者名无法区分「上游原生」和「apiduo 新增」。

正确方法：`git diff upstream/main -- <path>`。

### 实测结果

| Section | 归属 |
|---|---|
| `overview` / `models` / `flow` / `users` | **new-api 原生** |
| `my-keys` / `sk` / `capacity` / `retention` | **apiduo 新增** |

### 因此

- `retention` 是 apiduo 新加的，**可以迁**。已迁到 `/growth` 客户页。
- 上一节的「三者都属平台分析、取消迁移」对 `models`/`flow` 成立（它们确实是原生的），对 `retention` 不成立。
- `capacity` 同样是 apiduo 新增，可迁，但暂缓——`quality` 台目前没有「容量预测」的位置，需要先设计。

### 方法论教训

**判断代码归属只能对照上游 diff，不能看提交作者、也不能看文件名。**
这次连续错了两次：第一次按名字猜（以为 Flow 是错误率曲线），第二次按作者猜（以为 Betterme 的提交都是上游的）。
