# 令牌级在途并发 · 一期（仅同步，上限可配）

> 状态：设计稿，未落代码
> 日期：2026-11-21（v4：上限改为可配 1..N，范围仍为「只做同步在途」）
> 口径：约束对象 = 令牌（`token_id`）；同步请求从准入到响应写完占用 1 个槽位；异步任务一期不占槽。

---

## 0. 结论先行

1. **上限设为可配 1..N 后，判据必须是「租约集合」，不是单槽位的 `SET NX`。** 单槽只能表达「有没有人」，表达不了「现在有几个人、还剩几个」。
2. **N 的代价不是性能，是公平性。** 槽位先到先得，没有排队。一个 key 配 N=3 分发给 3 个人，其中一个人开 3 个客户端就能占满，另外两人全部 429。要公平只有两条路：一人一 key（推荐），或者做排队（成本不成比例）。
3. 一期仍然只做同步：挡住「同一 key 的并发请求」，**挡不住串行提交后并行跑的异步任务**。提交请求只占几百毫秒。
4. 改动面：`Token` 加一个字段、一个中间件（内含一段原子脚本）、三处挂载、一个前端输入框。不改 `Task` 表、不查 DB、不需要对账。

## 1. 判据

```
key = concurrency:token:{token_id}

准入（一段脚本内原子完成）：
  1) ZREMRANGEBYSCORE key -inf now      // 回收过期成员
  2) n = ZCARD key
  3) n < limit ? ZADD key now+ttl request_id → 放行 : 拒绝

释放：ZREM key request_id               // 幂等，删不存在的成员无副作用
续租：ZADD key XX now+ttl request_id    // 只更新已存在的成员，不新插入
```

为什么必须原子：三步分开执行时，并发请求会读到同一个 `n`。`limit = 1` 时两个请求同时通过；`limit = 3` 时最坏可以通过 6 个。单 key 单脚本即可，不涉及跨槽。

### 1.1 时间源用 Redis 的 `TIME`，不用应用时钟

多副本下各机器的时钟会有漂移。用应用时间写 `score`，一台慢 2 秒的机器写入的租约会被另一台提前判定为过期，`limit = 1` 时会出现「明明有人占着却放行」。

单机时钟漂移不会报错，只会让闸门偶尔失效 —— 这是最难排查的一类问题。脚本内取 `redis.call('TIME')` 统一时间源。

### 1.2 `limit = 1` 时不建议退回 `SET NX`

单槽位用 `SET key request_id NX PX ttl` 确实更简单，但代码会分叉成两套：`limit = 1` 走 String，`limit > 1` 走 ZSET。配置从 1 改成 2 就换实现，边界最难测。

**统一用 ZSET**，`limit = 1` 只是集合大小上限为 1 的特例。代价是每次准入一次 `ZREMRANGEBYSCORE`，O(log N)，N 是上限，可忽略。

## 2. N 的语义与公平性

### 2.1 不同 N 的实际吞吐

按「单请求 10 秒」估算：

| limit | 理论小时上限 | 说明 |
|---|---|---|
| 1 | 360 次 | 严格串行 |
| 3 | 1,080 次 | 只对长请求有区分度 |
| 10 | 3,600 次 | 短请求（<1s）时基本不构成约束 |

**N 只在「请求时长 × N」超过用户真实节奏时才有意义。** 文本请求 2 秒、N=10，用户几乎撞不到上限；图片 20 秒、N=10，才真正限制在 10 张并行。

### 2.2 先到先得，没有排队

| | 行为 |
|---|---|
| 槽位满 | 立即 429，不排队、不等待 |
| 释放顺序 | 谁先结束谁先让位，无优先级 |
| 一个人占满 | 可能，且没有机制阻止 |

**这是分发范式必须写进文档的原因**：一个 key 配 N=3 分给 3 个人，不等于「每人 1 个」。它等于「3 个人抢 3 个槽，手快的占满」。

若要求「每人独立的 1 个」，只能在 key 层解决：**发 3 个 key，每个配 1**。这不是方案缺陷，是「并发上限」这个机制本身的边界 —— 它管总量，不管分配。

### 2.3 上限要有天花板

配置必须限制最大值（建议 1,000）：

- 防止误填 `999999` 导致 ZSET 无界增长；
- 上限越大，`ZREMRANGEBYSCORE` 的清理成本越高；
- 超过 100 的并发限制，对单 key 场景基本没有实际约束意义，说明该拆 key 了。

## 3. 效果边界（一期范围）

| 使用形态 | 一期是否挡住 | 说明 |
|---|---|---|
| 同一 key 10 个并行 chat（limit=1） | **挡住** | 第 2 个起 429 |
| 同一 key 10 个并行 chat（limit=3） | 挡住第 4 个起 | 前 3 个放行 |
| 同一 key 并行图片（同步渠道，limit=3） | **挡住第 4 个起** | 图片 10–30s，占用明显，N 有效 |
| 同一 key 并行视频提交 | 只挡同时提交 | 提交间隔 >200ms 就都能进 |
| 串行提交 20 个异步任务 | **挡不住** | 每次提交都释放，任务各自跑 |
| 一人在跑任务时另一人用同一 key 发文本 | **不挡**（一期） | 任务不占槽；二期才挡 |
| 轮询任务进度 | **不挡，也不该挡** | GET 不计入 |
| 换一个 key 继续打 | 挡不住 | 分发的固有属性 |

**一句话**：一期把「同一时刻的 HTTP 请求数」压到 N，不把「同一时刻的任务数」压到 N。

### 3.1 时间线

**同步请求 —— 有效（limit=2）：**

```
t=0.0s  A 请求进来 → 占槽（1/2）
t=0.1s  B 请求进来 → 占槽（2/2）
t=0.2s  C 请求进来 → 429
t=10.0s A 结束 → 释放（1/2）
t=10.1s C 重试 → 占槽（2/2）
```

**异步任务 —— 只约束提交动作：**

```
t=0.0s  POST /v1/videos → 占槽 → 0.2s 返回 202 → 释放（任务 A 在跑）
t=0.2s  POST /v1/videos → 占槽 → 0.4s 返回 202 → 释放（任务 B 在跑）
...
20 秒内可以提交 100 个任务，全部并行跑
```

## 4. 实现要点

### 4.1 挂载点（三处，否则可绕过）

| 路由树 | 位置 | 备注 |
|---|---|---|
| relay `/v1/*` | `router/relay-router.go`，`TokenAuth()` 之后、`Distribute()` 之前 | 与 `ModelRequestRateLimit()` 相邻 |
| video `/v1/video/*`、`/v1/videos/*` | `router/video-router.go` 两个 group 各一次 | 该树当前无任何限速 |
| MCP `/mcp` | `mcp/router.go:42`，`captureCaller()` 之后 | 已有 `token_id` 上下文（`middleware/auth.go:565-567`） |

同一个中间件函数三处引用。实测：video 与 MCP 两条树目前完全不经过 `ModelRequestRateLimit`，只挂 relay 会被绕过。

### 4.2 关闭条件早于一切

`limit == 0` → 直接 `c.Next()`，不碰 Redis。绝大多数 key 走这条路径，不能有额外开销。

### 4.3 TTL 与续租

- TTL = `max(60s, 该模型 P99 × 2)`，上限 15 分钟。
- 超过 TTL 一半续租一次。不续租时，30 秒的流式请求会在中途被回收，实际并发短暂超过 N。
- **续租失败的处理**：`ZADD XX` 返回 0 说明成员已被清理（请求超时了 TTL 还没结束）。此时应重新插入并记一条日志，而不是放弃 —— 请求确实还在跑，不占位比占位更糟。这会产生短暂的 N+1，属于可接受的偏差，但要能被观测到。
- TTL 同时是崩溃兜底：进程被 kill 后，最坏一个 TTL 后自动释放。

### 4.4 空集合的清理

所有成员都过期后，ZSET 会成为空 key 残留。数量级等于「配了限制的 key 数」，可以接受；若在意，给 ZSET 设一个较长 TTL（如 1 小时）并在每次写入时刷新，长期不用的 key 自动消失。

### 4.5 无 Redis / Redis 故障：fail-open

| 情况 | 行为 |
|---|---|
| 单副本无 Redis | 进程内 `map[request_id]deadline` + 互斥锁，计数 = `len(map)`，定期清理过期项 |
| 多副本无 Redis | 启动时 WARN，面板显示「单副本模式」，实际上限 = limit × 副本数 |
| Redis 运行中故障 | **放行** + 错误日志 + 计数告警 |

限流器故障必须放行。这与预扣相反：预扣 fail-closed 是保护资金，限流 fail-closed 会让整个网关在 Redis 抖动时全量 503。**保护性设施不能成为新的单点。**

### 4.6 释放路径

| 路径 | 是否释放 |
|---|---|
| 正常返回 | 是（`defer`） |
| SSE 正常结束 | 是（handler 返回后） |
| 客户端断连 | 是（context 取消，handler 返回） |
| 跨渠道重试 | 是（同一 handler，不重复占位） |
| panic | 是（defer 展开时执行） |
| 进程 OOM / kill -9 | 否 → TTL 回收 |

### 4.7 性能开销

**结论：可忽略，但有三个硬前提。** 新增开销低于现有的 `ModelRequestRateLimit`。

| 场景 | 客户端感知的增量 | 说明 |
|---|---|---|
| `limit = 0`（未配置） | **0** | 分支在最前面，不碰 Redis |
| 单副本内存模式 | < 1 μs | map + mutex，无网络 |
| Redis 同机 / 同 VPC | **0.2–0.5 ms** | 只有准入那 1 次往返在关键路径上 |
| Redis 跨机房（RTT 3 ms） | 3 ms | 不应出现 |
| Redis 卡住且未设短超时 | +1～3 s | 灾难，必须避免 |

关键点：**只有「准入」的 1 次往返计入首字节延迟**。释放的 `ZREM` 发生在响应写完之后（非流式）或流结束后（SSE），客户端通常感知不到，也不影响 TTFT。

参照现有实现：`ModelRequestRateLimit` 每个成功请求最多 6 次 Redis 往返（`LLen`、可能的 `LIndex`、令牌桶 `EvalSha`，成功后 `LPush` + `LTrim` + `Expire` 三次独立调用）。本方案是 **2 次**（准入 1 + 释放 1），更轻。

**三个硬前提，缺一个就会变成性能问题：**

1. **`limit == 0` 必须在最前面短路**，不读 Redis、不取时间。绝大多数 key 走这条路径。
2. **Redis 客户端必须设短超时（10–20 ms）并 fail-open**。默认超时是秒级，Redis 抖动会把每个请求变成秒级延迟 —— 这是限流器最常见的自伤方式。
3. **Redis 与网关同机房/同 VPC**。跨机房 3 ms 的 RTT 对文本首字节是 1% 量级，对短请求更高。

**两个放大风险，需要监控：**

- `ZREMRANGEBYSCORE` 的复杂度是 O(log N + M)，M 是被清理的过期成员数。正常请求的租约分散在不同时刻过期，M 很小；但**进程崩溃后重启，一批租约同时过期**，一次清理可能删除近千个成员（约 100 μs）。Redis 单线程，这会短暂阻塞其他 key。量级可接受，但要知道它存在。
- 同一 key 被高频使用（如 1000 QPS 全打一个 key），所有准入落到同一个 ZSET，Redis 单分片处理。1000 次 Lua/s 约为单核 5% 占用，可接受；若预期远超此量级，说明该 key 应拆分。

另外，限流本身会**降低上游并发**，通常减少上游 429 与超时，对整体成功率是正收益 —— 这部分收益不在延迟指标里体现。

## 5. 拒绝契约

| 项 | 内容 |
|---|---|
| HTTP | `429 Too Many Requests` |
| 错误码 | `concurrency_limit_exceeded` |
| 响应头 | `X-RateLimit-Limit: {limit}`、`X-RateLimit-Remaining: 0`、`Retry-After` |
| `Retry-After` | 当前**最早到期**那个租约的剩余时间（`ZRANGE ... WITHSCORES LIMIT 0 1`），不是固定值 |
| body | 沿用 `abortWithOpenAiMessage` 的 OpenAI 兼容格式 |

要点：

1. 闸门永远在响应开始前，不存在「流式已开始再限流」的 SSE 错误形态。
2. `Retry-After` 给真实剩余时间。给固定 1 秒会让客户端在 30 秒的请求上疯狂重试，把闸门变成放大器。
3. 与「余额不足」严格分开：并发超限是 429，余额不足走既有 402/403。客户端对这两者的正确反应完全不同。
4. 429 文案里带出 `limit` 与当前占用数，否则用户无法判断是自己并发太高还是别人占着。

## 6. 配置

`Token` 表新增一个字段：

| 字段 | 语义 | 默认 | 范围 |
|---|---|---|---|
| `ConcurrencyLimit` | 在途上限，0 = 不限制 | 0 | 0 – 1000 |

面板落在令牌创建/编辑页，一个数字输入框。分发流程不需要新 UI：管理员建 key 时填 1/3/10，把 key 给下游。

**不要用 option JSON 映射 token_id**：key 会持续增长，JSON 不可维护且无面板入口。

**三态用指针**：若以后加「用户级默认 + key 覆盖」，覆盖值必须是 `*int`（`nil` = 跟随，`0` = 不限，`n` = 固定）。本项目已有教训：`bool + omitempty` 会把显式关闭吃掉。

## 7. 观测

| 指标 | 用途 |
|---|---|
| `inflight_current{token_id}` | 当前占用量，回答「这个 key 为什么 429」 |
| `inflight_limit{token_id}` | 上限，与上面一起看才有意义 |
| `limit_rejected_total` | 拒绝量 |
| `lease_expired_total` | 到期回收次数。持续 > 0 说明有请求没走完释放路径，或者 TTL 太短 |
| `lease_revived_total` | 续租失败后重新占位的次数（§4.3）。这是实际并发会超过 N 的唯一来源 |
| `lease_held_seconds` | 占用时长分布，用于校准 TTL |

**面板要显示「当前在途 / 上限」**。key 分发后下游只看到 429，管理员在后台看不到原因会反复来问。

灰度：`shadow` 只记录不拒绝 → 指定 key 白名单 enforce → 全量。回滚是 `ConcurrencyLimit = 0`，即时生效。

## 8. 二期（异步）要补什么，一期不必做

一期与二期的差别只在判据多一项：

```
一期：ZSET 在途数 ≥ limit                                  → 429
二期：ZSET 在途数 + 该 token 的未终态任务数 ≥ limit          → 429
```

二期需要：

1. `Task` 表加 `TokenId` 列 + `(token_id, status)` 联合索引（`token_id` 现在只在 `PrivateData` 的 JSON 里，无法索引）；
2. 回填未终态的历史任务（通常几十行；已终态的 `token_id = 0` 不影响判定）；
3. 提交瞬间用 5 秒 Redis 短锁防 `count-then-insert` 竞态；
4. 闸门自带任务年龄上限（`TASK_TIMEOUT_MINUTES` 默认 72 小时，不能直接信任状态）。

**一期代码要为二期留位置**：把判定抽成「同步部分 + 异步部分」，二期只填异步那一段，不动中间件骨架。

## 9. 待确认

1. **N 的使用方式**。若打算让多人共享一个 N=3 的 key，需要接受「先到先得、可能被一人占满」；不接受就改成一人一 key。
2. **N 的上限值**。建议 1000，可按实际需要下调。
3. **一期的效果是否够用**。若痛点是「一个 key 只能串行跑任务」，一期不够，需要直接上二期。
4. **多副本部署现状**。若线上多副本且 Redis 不是必配，需先确认 Redis 可用，否则实际上限会乘以副本数。
