01

调用链与归属

谁改、改在哪

一次兑换码请求要穿过四层。关键不是层次本身，而是哪些文件是本方案要动的—— 上游文件每改一行都记入合并面预算，所以新逻辑全部下沉到新文件，上游只留一行委托。

为什么把审计画成旁路而不是一步：它写的是 LOG_DB，不是业务主库。 这意味着「码改了但审计没落」是可能的。所以审计只能作为追责线索， 真正的一致性靠 CAS 条件更新——这一点决定了下面状态机的画法。
02

状态机：把「改回去」这条边删掉

核心决策

兑换码的全部正确性问题都收敛到一条边：used → enabled。 它看起来只是改个状态，实际是把一笔已经兑付的负债重新变成负债。删掉它，账才对得上。

现有实现里这条边是通的。更要紧的是它会「自动」发生： Update() 的 Select 包含 status， 而它写的是上一步读出来的快照。管理员改名字的几百毫秒里如果有人兑换， 旧快照的 status=1 就会被写回去——不需要任何人有意操作。
03

事务边界：100 次提交 vs 1 次

P0

批量生成要解决的不是「慢」，而是失败之后库里到底有几张。 旧实现每条一条 INSERT 且各自提交，失败点之前的全部留下。

04

检索分流：一个输入框，四条路

P1

运营拿到的是用户贴来的一串字符，形态不确定：带横线、带空格、大小写混杂、只记得前几位。 先把输入归一化，再按形状决定走哪条 SQL——而不是把所有情况都塞进一个 OR。

05

导出链路：一份文件等于现金

P1

兑换码导出和别处不同：它输出的是可直接兑换的凭据。 所以这条链路上有四道闸，任何一道都不能省。

这一套不是新造的。导出的并发锁、流式写、no-store 三条都照 controller/log.go:98-168 与 service/log_export.go:33 的既有模式，只把 NDJSON 换成 CSV、把 key 换成 redemption_export: 前缀。
