# 多 key 粘性路由（sticky）

## 为什么需要

上游 prompt cache 按 **API key / organization** 归属。`random` / `polling` 会把同一个客户端的请求打散到 N 个 key 上，缓存命中率约 `1/N`，等于把缓存折扣按 key 数量摊薄。

渠道亲和（channel affinity）解决不了这个问题：它粘的是 `channelID`，粘住渠道之后 `SetupContextForSelectedChannel` 仍然会重新选 key。

`sticky` 把「一个下游令牌」固定到「一个上游 key」，让该 key 上的缓存条目持续命中。

## 三种策略之外：未配置

`multi_key_mode` 有三种取值，但实际会遇到第四种状态——**空值**：升级前创建的渠道没有这个字段，通过 API 建的渠道可能压根没传。

上游原来的处理是落到 `default` 分支返回 `keys[enabledIdx[0]]`，也就是**固定第一个 key**。而控制台对空值的回显是 `random`（`multi_key_mode || 'random'`）——界面说在分散，实际全压一个 key 上。

现在 `default` 分支按 random 处理，覆盖四种情况：空值、未知值、`sticky` 但请求没有种子（任务轮询、余额查询、渠道测试）。

影响：那些一直固定打第一个 key 的历史渠道，流量会真正分散开。如果某个渠道依赖「固定一个 key」的行为（例如上游按 key 做额度），把它显式设成 `sticky` 才是对的语义。

## polling 的两个坑（已修）

### 游标写在了调用方自己的副本上

`GetNextEnabledKey` 读游标用 `CacheGetChannelInfo`（缓存里的对象），写却写 `channel.ChannelInfo`（调用方传进来的那个对象）。两者在 relay 主链路上是同一个指针，所以看不出问题；但 `relay_task.go` 是 `GetChannelById` 拿的数据库副本——写进去的游标下一轮就丢了。

后果不是「稍微不均」，而是**任务类请求 8 次全部命中同一个 key**（有测试固定这一行为）。表现出来就是某些 key 被打爆、另一些闲着。

修法：写回时两处都写——`channelInfo` 给缓存，`channel.ChannelInfo` 给无缓存模式下的 `SaveChannelInfo` 落库。

### 任务和 key 是绑定的，但系统从来不记这把 key

上游的异步任务（视频、Gemini / Vertex 的 operation）是**按凭据隔离**的：key A 提交的任务，用 key B 去查会返回 404 —— B 的账号根本看不见它。所以「任务用哪把 key」必须在提交时记下来。

原来的代码没有记：

- `tryRealtimeFetch` 直接把 `channelModel.Key` 塞进 Authorization 头。多 key 渠道的这个字段是**所有 key 用换行拼起来的**，于是必然 401；单 key 渠道碰巧是对的，所以这个问题一直没暴露。
- `lockOriginChannel` 用 `GetNextEnabledKey()` 轮换一把 key 去操作原渠道的任务 —— 轮到谁全看运气，大概率是错的账号。

修法：**记身份，不记位置**。

1. `TaskPrivateData` 同时记录 `MultiKeyIndex`（提示）和 `MultiKeyFingerprint`（身份）。只记 index 是错的——key 列表是人手编辑的，在中间插一行，后面所有 key 的编号全变，任务就漂到别人的凭据上了。只记指纹则无法 O(1) 命中。两者配合：位置对上就直接返回，对不上就按指纹扫描。
2. 指纹是 `长度-hash`（如 `51-9f2a…`），不存明文，长度前缀还能让扫描先做一次整数比较，跳过所有长度不符的 key。
3. `GetKeyByFingerprint` **不推进游标**：状态查询是幂等 GET，不该消耗轮次，否则真正服务生成的请求会跳过被轮询的那个 key。
4. 指纹找不到（key 被删、被替换、被禁用）才回退第一个可用 key —— 至少还有凭据，能把上游的真实错误报出来，而不是发一个空头。

老任务没有指纹字段，直接走回退分支，与修复前的行为一致。

### 凭据短期留存：解决「存量任务查不到」

指纹只能找到**还存在于列表里**的 key。如果运维把任务用的那把 key 删了或换了，渠道里再也没有它的痕迹，任务就变成孤儿——上游明明还认这个任务，网关却拿不出对应凭据。

所以任务落库时额外存一份**明文凭据 + 写入时间**（`UpstreamKey` / `UpstreamKeyAt`），有效期 24 小时。读取顺序变成：

1. 留存凭据（24h 内）→ 直接用，**不检查禁用状态**：一把因为欠费被标记的 key 仍然是唯一能看见这个任务的凭据，拒绝它等于把计费问题变成任务丢失
2. 指纹 → 位置命中或扫描
3. 第一个可用 key → 兜底

只在**多 key 渠道**写这份副本：单 key 渠道的 key 本来就在 `channels.key` 里，多存一份只是多一处泄露面。

关于暴露面，说清楚：`private_data` 是 `json:"-"`，不会出现在任何 API 响应里；但它在数据库里是明文，与 `channels.key` 同级。备份文件、慢查询日志、DBA 都能看到。24 小时之后不再使用，但字段仍在，物理清除依赖任务表本身的清理策略（历史任务本来就要清）。

性能（3000 key 渠道，生产形态下 `Keys` 已预解析）：

| 场景 | 耗时 |
| --- | --- |
| 列表没动，index 命中 | 75 ns |
| 位置变了，按指纹扫描 3000 个 | 1.3 μs |
| 扫描 10000 个 | 3.7 μs |
| 指纹已不存在（key 被删） | 20 μs |
| 老任务无指纹 | 11 ns |

扫描之所以快，是因为比对的是 `stickyKeyPlan` 里缓存的 key 哈希（一次整数比较），命中后再用实时 key 校验一次——过期的计划只可能「找不到」，不可能返回错误的凭据。

### 多副本下顺序仍是交错的

游标存在进程内（`MemoryCacheEnabled=true` 时），多副本各轮各的。整体流量仍然均匀，但上游看到的是 N 条独立序列交错，不是一条严格顺序的序列。要严格全局顺序得把游标放进 Redis，那是另一件事。

## 同时最多用几个 key（min_active_keys）

一个渠道可以囤很多 key，但只想让其中一部分同时跑。配 `min_active_keys = 10`、挂 100 个 key，就是「同时在跑 10 个，90 个待命」。

**没有新增状态。** 待命的 key 状态仍然是「启用」，只是排在上限之外、不被选到。这么设计带来三个直接后果：

- **补位是自动的**：可用集合每次请求都从实时状态重建，某个 key 被禁用（401、欠费、手动停用）后它自动离开窗口，后面那个 key 顺势补进来。不需要 rebalance 扫描，不需要在禁用路径上挂任何代码。
- **所有既有语义不变**：计数器、筛选、徽标、`禁用所有`、`删除自动禁用` 都不用改，因为它们看到的状态 1/2/3 含义没变。
- **挂接点只剩 2 个**：`GetNextEnabledKey` 里把可用索引裁到上限，粘性计划构建时同样裁一次。保存渠道、自动禁用、手动禁用、全部启用这几条路径一概不碰——上一版为此在 `controller/channel.go` 和 `model/channel.go` 挂了 5 处。

代价是**「哪些 key 在跑」由列表顺序决定**：想换一批，调整顺序即可，不能单个勾选。这是刻意的——单个勾选要多一套状态和 UI，而顺序已经足够表达。

| 配置 | 行为 |
| --- | --- |
| `min_active_keys = 0` | 不限制，所有可用 key 参与选路（默认，行为与上游一致） |
| N < 可用数 | 前 N 个可用 key 参与，其余待命 |
| N ≥ 可用数 | 等于不限制（降级但不报错） |
| 可用数降到 0 | **渠道被禁用**（`auto_disabled` + 原因 `all_keys_disabled`），请求不再落到它 |

与选择策略正交：上限决定「几个 key 能用」，sticky / polling / random 决定「这 N 个里用哪个」。

### 耗尽与降级的边界

这三条线必须分清，混起来很容易做出「本来还能服务却整条下线」的决定：

| 可用 key 数 | 渠道状态 | 行为 |
| --- | --- | --- |
| 0 | **自动禁用** | `status_reason = all_keys_disabled`；重新启用任意一个 key 会自动恢复 |
| 1 ~ N-1 | 启用 | **照常服务**，只是窄于配置的宽度。窗口填不满不是故障 |
| ≥ N | 启用 | 按配置宽度服务 |

这里「0 就禁用」不是我的实现，是上游既有逻辑（`model/channel.go` 的 `handlerMultiKeyUpdate` 与管理端的 `disableMultiKeyChannelIfUnavailable` 两条路径都会做）。我做的事只是保证上限不会把这条线挪走：上限只收窄候选，`可用数 == 0` 仍然意味着一个都选不出来。

如果你希望「可用数 < N 就禁用」，那是另一个决定，代价要说清楚：3 个 key 挂了 1 个、batch 配 5 的渠道，会从「用 2 个 key 继续服务」变成「整条下线、零容量」。多数场景下这是净损失，所以我没做。

### 对抗审查改掉的三处

**① 轮询根本没走上限。** 上限最初只作用在「裁剪后的 `enabledIdx`」上，而随机分支读这个列表、轮询分支却自己遍历原始 key 环。实测上限 2、6 个 key，轮询把 6 个全用了。根因不是漏了一个判断，而是**「可用」被定义了两次**。现在 `enabledIdx` 是唯一的定义，轮询每命中一个候选就向它求证（`isActiveIndex`）。

**② 上限生效后轮询会退化成全表扫描。** 游标是「下一个 key 的下标」，每轮 `(idx+1) % len(keys)`。上限 10、3000 个 key 时，服务完第 10 个，游标就落到第 11 个——一个待命 key，于是下一轮要扫过剩下 2990 个才绕回窗口。实测 **1.67 μs/请求**。改成游标指向**下一个可用 key**（`nextActiveIndex`）后降到 **155 ns**。

**③ 上限生效时才值得短路。** 循环在收满窗口后立即 `break`，切片容量也按上限预分配：

| 3000 个 key、随机模式 | 改前 | 改后 |
| --- | --- | --- |
| 无上限 | 8.5 μs / 24 KB | 8.9 μs / 24 KB（不变） |
| 上限 10 | 8.5 μs / 24 KB | **101 ns / 80 B** |

无上限那条**故意不优化**：给 3000 个 key 逐个 `TrimSpace` 会让它慢 2.2 倍，而它换来的只是「中间的空行不再偶尔被试一次」——上游本来就这样，一次失败重试就过去了。所以空行检查和提前退出都只在 `limit > 0` 时执行。

一个附带的结论：**上限不只是省额度，也把这条路径的高速化了**。没有上限时，3000 个 key 的渠道每请求都要分配一个 24 KB 的索引切片；配上上限后是 80 B。

### 模式 × batch 的完整行为

| 模式 | 无 batch（0） | 有 batch（N） |
| --- | --- | --- |
| `random` | 全部可用 key 里随机 | 窗口内随机 |
| `polling` | 全量顺序轮转 | 窗口内顺序轮转，游标指向**下一个可用 key** |
| `sticky` + 有种子 | 全量 rendezvous，令牌恒等一把 key | 只在前 N 个可用 key 里 rendezvous |
| `sticky` + 无种子（任务轮询、余额、渠道测试） | 分散（不钉 `keys[0]`） | 窗口内分散 |
| 未配置 / 未知值 | 分散 | 窗口内分散 |

两条必须成立的不变量，都有测试固定：

1. **任何模式、任何配置下，返回的 key 一定是「当前列表里的、未禁用的、窗口内的」**。key 数据被改写（追加、中间插入、原位替换、删除、整表覆盖）后，下一个请求立刻生效，不会返回上一版的 key。
2. **给粘性渠道开启 batch 不会重排窗口内的令牌**。收窄候选集不可能击败已经胜出的那把 key，所以原本就在前 N 个里的令牌保持不动——这是「加个 batch 结果整个渠道 prompt cache 全冷」的反例保护。

反过来说，**关掉 batch 是会重排的**：候选集变大，某个原本排第二的 key 可能翻盘。这是数学事实，不是实现缺陷，文档里写清楚比事后解释便宜。

上限可以随时改，包括从 N 改回 0。`PUT /api/channel/` 收的是 `*int`，而 `ChannelInfo`
实现了 `driver.Valuer`（整体写 JSON 列），所以 0 不会被 GORM「struct Updates 跳过零值」
吃掉。这条有 e2e 固定：上限 2 的 polling 渠道改成 0 后，紧接着的 10 次请求覆盖了全部
5 把可用 key（`e2e/live/suites/multi_key_sticky.py` 第 6b 段）。同一段还验了上限对轮询
生效、窗口外的 key 从不参与、摘掉活跃 key 后窗口只右移一格。

## 算法

rendezvous（最高随机权重）哈希，不是 `hash(seed) % len(keys)`：

- 取模的缺陷：任何一个 key 被禁用，**所有** seed 的归属整体重排，缓存全冷
- rendezvous：key 增删只重排原本落在该 key 上的那 `1/N` 个 seed

打分函数是 `mix64(fnv1a(seed) ^ fnv1a(key))`，其中 `mix64` 是 MurmurHash3 的 64 位 finalizer。少了这一步分布会明显偏斜（实测 4 个 key 时有一个吃掉 50% 流量），因为「取最大值」比较整个字，而 FNV 的高位对短输入扩散不足。

哈希只吃 seed 和 **key 内容**，不吃索引：运维在 key 列表中间插一行，其他 key 的归属不能跟着变。

### 几千个 key 时的开销

关键不在于「哈希快」，而在于**请求路径上不该出现只随配置变化的东西**。`stickyKeyPlan` 在 key 列表或 key 状态变化时构建一次，里面同时放着：

- 每个 key 的哈希（`hashes`）
- **当前可用的 key 索引**（`eligible`：排除空行、排除已禁用）

请求只遍历 `eligible`，每个候选一次 `mix64`。因此开销与**可用 key 数**成正比，而不是总 key 数——禁用的 key 不再被「查一下状态然后跳过」，而是从一开始就不在列表里。

| key 数 | 优化前 | 现在 |
| --- | --- | --- |
| 4 | — | 185 ns |
| 3000 | 220 μs | **4.4 μs** |
| 10000 | 625 μs | **14.2 μs** |
| 3000（半数禁用） | 114 μs | **2.4 μs** |

注意最后两行：半禁用比全可用**更快**（2.4 vs 4.4 μs），因为可用集合只剩一半。旧实现恰好相反——禁用越多越慢，因为它每次都要遍历全集再逐个查状态。

### 状态变化怎么被发现

`MultiKeyStatusList` 没有版本号，所以靠三条互补的判据，都不需要遍历状态表：

1. **条目数**（每次请求一次 `len()`）：启用 key 会删掉条目、禁用会新增条目，任一变化都会让计划重建。
2. **惰性校验**（每次请求一次 map 查询）：只查**选中的那个** key。如果它已被禁用，说明计划过期，删掉重建再选一次。
3. **老化**（每次请求一次读时钟）：计划超过 30 秒强制重建。

前两条加起来仍然漏一种情况：**同时禁用 A、启用 B** 时条目数不变，而 B 根本不在计划的候选列表里，惰性校验永远查不到它——渠道越闲，B 越可能一直分不到流量。第 3 条是兜底：不管状态是怎么变的，最多 30 秒后一定生效。

用老化而不是版本号，是因为版本号要求每个写状态的地方都自增一次（`controller` / `model` 里六七处，且都是上游常改的文件），而老化只在我们自己的代码里，代价是一次读时钟。3000 key 的重建约 45 μs，每渠道每 30 秒最多一次，可以忽略。

代价是状态变化后的第一个请求多做一次 O(n) 重建，之后恢复正常。漏检的最坏后果是某个 seed 多一次失败重试，`tried` 集合会立刻把它跳过。

### 为什么不做分桶

试过把 key 分成固定 128 桶，先选桶再桶内 rendezvous，能压到 426 ns。否决的原因有两条，都是实测出来的：

1. **桶大小不均**：桶里装多少 key 服从泊松分布，10000 key 时最热的 key 拿到平均值的 **2.05 倍**流量。渠道的限流是由最热的 key 决定的，2 倍偏差等于砍掉一半可用容量。
2. **按桶大小加权可以修正份额，但代价是重排**：加权需要 `seed % 总key数`，只要增删一个 key，余数整体变化，实测 **99.45%** 的 seed 会换 key —— 整个渠道的 prompt cache 一次全冷，正好和这个功能的目的相反。

均匀和重排小，两者都要，就只能付 O(n)。6.3 μs 相对一次请求的几百毫秒是 0.001%，这个交换是划算的。

## 种子

`token_id` 优先，回退 `user_id`，都没有则退回普通轮询（不报错）。

一个令牌固定一个 key。比用户级更细：同一账号的不同令牌可以落在不同 key 上，分散单 key 的速率压力。

## 失败与重试

同一次请求内，`tried` 集合记录用过的 key 索引，重试取次高分位——**立即换 key**。`tried` 按 channelID 隔离（索引跨渠道没有意义）。全部 key 都试过之后回落为「忽略 tried」，不让粘性把请求打死。

「选 key」和「记进 tried」必须在同一把锁里完成：websocket 连接会复用同一个 gin context 处理多帧，两者分开会让两个并发帧选到同一个 key，正好是这套机制要避免的碰撞。`apiduoTried` 的 get-or-create 另有一把包级锁，否则两个并发帧会各建一份 `tried`，各自的锁保护不了对方。

空白行不是 key，会被跳过：轮询模式下它只是让一部分请求打空一次然后重试，粘性模式下会把同一个令牌**永久**钉在这个空 key 上。

`GetStickyEnabledKey` 出错或上游已经报错时，`overrideStickyChannelKey` 原样返回上游结果：粘性不允许制造上游本来不会有的失败。

`distributor.go` 的写法是刻意的：把 `GetNextEnabledKey()` 换成我们的函数会让上游那一行变成「被改过的」，rebase 必冲突；先调用上游、再覆盖结果，上游那行保持原样。

那次调用也不是白做：`GetNextEnabledKey` 对 `sticky` 走 **random** 分支（`model/channel.go` 的 switch），返回一个可用的随机 key，正好作为粘性选路失败时的兜底；它不推进 polling 游标。

### 没有请求种子的调用方

任务轮询（`relay_task.go`）、余额查询、渠道测试、模型列表拉取都直接调 `GetNextEnabledKey()`，拿不到 `token_id`。它们走 random 分支，保持粘性引入之前的分散度——如果落到 `default` 分支，这些路径会全部钉在 `keys[0]` 上，把缓存优化变成单 key 限流。

## 已知边界

- 粘性只在单实例内一致，但**纯函数哈希与实例无关**，多副本天然一致，不需要 Redis
- 渠道测试只测一个 key：sticky 模式下点一次测试只会命中该管理员会话对应的那个 key
- key 内容变化（运维替换某一行）会让落在该 key 上的 seed 重新分配，这是预期行为
- **Windows 粘贴带来的 `\r`**：`GetKeys()` 只按 `\n` 切，行尾会留下 `\r`，拼进 `Bearer` 后上游 401。这里不做 trim——trim 之后 `handlerMultiKeyUpdate` 用 `usingKey` 反查索引会匹配失败，key 级自动禁用会静默失效。粘性会让这个坏 key 从「1/N 概率」变成「该令牌 100% 失败」，粘贴后请检查行尾
- `MultiKeyStatusList` 用索引记账，管理员删除中间某行后索引会前移，禁用记录会错位到别的 key 上。这是上游 `handlerMultiKeyUpdate` 的设计，sticky 只是让它显形
