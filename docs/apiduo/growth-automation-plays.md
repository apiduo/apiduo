# 用户运营自动化机制

> 前置：`user-tier-operations.md`（分层）、`growth-console.md`（看板）。本文只回答"怎么从人盯变成触发式"。

**核心判断：最高 ROI 的动作不在运营侧，在额度错误响应体里。** trial 24h 内 19 条错误有 13 条 `insufficient_user_quota`——用户是撞到墙才知道有墙。加额度不解决，让墙可见可跨才解决。这也是 `quota_wall` 排在所有运营动作之前的理由。

## 一、L1 生命周期：全部用现有字段，不加表

`growth_user_board` 已有 `created_at / first_active_at / last_active_at / topup_total`，六态可直接判定，只加一列派生字符串：

| 状态 | 判定 |
|---|---|
| N0 未激活 | age ≤ 7d 且 `first_active_at` = 0 |
| N1 已激活 | age ≤ 7d 且 `first_active_at` > 0 |
| G 成长 | 8 ≤ age ≤ 30d 且 7d 内有调用 |
| M 成熟 | age > 30d 且 7d 内有调用 |
| D 沉默 | 30d 无成功调用 |
| L 流失 | 60d 无调用 **且 `topup_total` > 0** |

三处纠正：**①「流失」必须是付过费的人**（否则无效注册稀释挽回预算）；`churn_exit` 按充值额分档（≥$100 电话、$10–100 邮件、<$10 不发）。**② 30 天沉默与 60 天流失不共用一个词**——前者是领先指标，后者是结果。**③ 新客期用"线索"替代 L2**——新客没消耗，分位是噪声；改看企业邮箱/推荐人/主动咨询。

## 二、运营矩阵

| | K（≤20，人工） | A（人工+半自动） | B（全自动） |
|---|---|---|---|
| N0/N1 | 用"线索"判，不用 L2 | 同左 | D0/D2/D6 邮件链 |
| G | 双周 1v1 + 用量报告 | 自动报告 + 人工批注 | 产品内模型推荐 |
| M | 月度 1v1（触发式，非固定日） | 月度简报 | 月度账单 |
| D | 人工电话一次 | 两封邮件后停 | 两封后停 |
| L | 迁移协助，不挽留 | 停投 | 停投 |

## 三、触发表（核心）

渠道只两条：**站内信**（零成本可关）与**邮件**（复用 `NotifyUser`，已有 email/webhook/bark/gotify 与 `CheckNotificationLimit` 限流）。短信不做——贵且开发者反感。

| play_key | 触发 | 延迟 | 渠道 | 说什么 | 成本 | 执行 |
|---|---|---|---|---|---|---|
| `inact_d0` | 注册 | 即时 | 站内+邮件 | 三条可粘贴 curl + 真实模型 + 余额条 | 0 | 自动 |
| `inact_2h` | 注册 2h 无请求 | +2h | 站内 | 「Playground 点一下就能跑」，不放代码 | 0 | 自动 |
| `inact_d2` | `first_active_at`=0 | +2d | 邮件 | 首次失败 90% 是这三件事：缺 Bearer、base_url 少 `/v1`、模型名不存在 | 0 | 自动 |
| `inact_d6` | 仍为 0 | +6d | 邮件 | 3 行 SDK 示例 + 体验额度到期日（不催充） | 0 | 自动 |
| `quota_wall` | 首次 `insufficient_user_quota` | 实时 | 响应体 | 错误 JSON 附 `topup_url` + 剩余可用天数 | 0 | **产品侧** |
| `grow_report` | G 层 7d 环比 > +20% | 周一 | 邮件 | 他自己的用量：Top3 模型、P95、失败率、更便宜替代 | 0 | 自动 |
| `mature_brief` | K/A 且（环比 < -10% 或**用户感知**失败率 > 20%） | 触发即发 | 邮件 | 余额可用天数 + 下月预估账单 | 0 | 自动+批注 |
| `topup_nudge` | 曾充值 且（`balance`≤0 或 `balance/max(q3d/3, q7d/7)` < 3）且 `last_active_at` ≥ now−7d | 每日 | 邮件 | 「还剩 X 元，按当前速率可用 4 天」——只报账不打折 | 0 | 自动 |
| `silent_w1` | D 第 0 天 | — | 邮件 | 「90 天新增了什么」：模型、降价、新端点，**不带券** | 0 | 审批发 |
| `silent_w2` | D 第 14 天仍沉默 | +14d | 邮件 | 最后一封，含退订按钮，之后静默 90 天 | ≤50 元 | 审批发 |
| `churn_exit` | L 层 | — | 邮件 | 「密钥/账单/用量可随时导出，要我打包吗」 | 0 | 人工 |
| `k_review` | K 层，周轮换 5 家 | 每周 | 电话/企微 | 用量结构、限流失败、下月扩容 | 返额 | 人工 |

**放弃条件写死**：`silent_w2` 后静默 90 天；某人群连续两轮唤醒率 < 8% 则整体停投，只留产品内公告。

`quota_wall` 的效果度量：`wall_recovery_rate` = 撞墙后 48h 内有成功调用的人数 ÷ 撞墙人数。没有这个数，这个改动就永远只能凭感觉说"提示余额有用"。

## 四、渠道路由：同一件事只走一条通道

| 情形 | 走哪 | 不走哪 |
|---|---|---|
| 未付费 + 额度耗尽 | `quota_wall`（响应体） | 队列、邮件 |
| 已付费 + 额度耗尽 | 队列 P0 人工 + `topup_nudge` | — |
| 已付费 + 余量 < 3d | `topup_nudge` 邮件 | 队列 |
| 7 天无调用 + 余量低 | **什么都不发** | 全部 |
| `status != 1` | **什么都不发** | 全部 |

两条原则：**邮件只碰付过费的人**——未付费的耗尽由 `quota_wall` 接住，那一刻他在等响应，不在等邮件。**对已停用的账户报账等于催充**——所以 `topup_nudge` 必须带 `last_active_at ≥ now−7d`，否则一个 10 天前停用、余额还剩两天的账户会收到"余额将耗尽"，既制造无效队列项，也违反 §九.2。

**实现前必须先修的三条**：

1. **失败率不能用 `Failures7d / Requests7d`——这个比值会超 100%。** 分子是尝试级行数、分母只记成功请求，"第 3 次才成功"会算成 `2/1=200%`；另一头看量级，虚高是 2–4 倍。改用 **用户感知失败率 = 可见失败 request_id ÷（成功 + 可见失败 request_id）**，或等 `logs.is_final` 落库直读。`Failures7d ÷ (Requests7d + Failures7d)` 只能用于渠道健康。事故判定仍用 `isIncident`（`Requests7d>0 && Quota7d==0`）。
2. **余额可用天数用 `max(q3d/3, q7d/7)`，并单独判 `balance`≤0。** 现公式对刚放量的账户低估风险（报「还有 5 天」其实明天断）。但因果别写错：**这只影响"我们来得及救的比例"，不决定"客户撞不撞墙"**——撞墙那刻无论队列怎么排他都已被拦住，改预警不会让 trial 撞墙数下降。
3. **耗尽型不进队列，走响应体**（见上表第一行）。队列侧的判据（两个 kind 的拆分、非沉默的写法、`blocked_3d` 的失明面、`switch` 顺序与防回归测试）已单独成文 `growth-alert-diagnostics.md` 交 analytics——那是 `BuildGrowthAlerts` 的范围。运营侧只需要一条结论：**未付费的额度耗尽永远不发邮件、不进队列**，否则每个烧完试用的 trial 用户都会变成 P0，把 K 层挤下去。

## 五、自动化与人工的边界

不用"重要/不重要"，用三条全满足才算可全自动：**① 可逆且代价低**（发错≈0 成本，不是误发折扣）；**② 不读意图**（只依赖事实，不依赖解读「他为什么降量」——那可能他自己业务下滑，也可能我们模型变差）；**③ 一句话对 100 个客户都成立**。

再叠频率门槛：**月触发 < 10 次不值得建流程**；**> 30 次/月必须自动化**，否则一定漏。

结论：必须人做的只有三类——打电话、判读降量原因、承诺资源。必须自动的：报账类（余额/用量/失败率）与一次性教学类（怎么跑通）。

## 六、技术形态：四个部件，一个函数

1. **一张表 `growth_plays`**：`(user_id, play_key)` 唯一，字段 `state / due_at / channel / batch_id / sent_at / result`；状态机 `pending → approved → sent / skipped`。存在理由不是调度，是**抑制与审计**。
2. **一个函数 `MaterializeGrowthPlays()`**，挂在 `service/growth.go` 现有 `StartGrowthTaskLoop` 里、紧跟 `RefreshGrowthStats()`。日批幂等 upsert，不新建调度器；阈值进已有 `growth.settings`。
3. **抑制规则，先判抑制再判触发**：`status != 1` 不进任何 play；同用户 7 天内触达 ≤ 1 次（硬抑制）；有未解 P0 事故则抑制全部营销类；有 open 的人工跟进则抑制自动触达；已关渠道或 `(user_id, play_key)` 已 sent 则抑制。
4. **一个发送适配层**：`play → NotifyUser()`，发送后写 `growth_touches`，`method="auto:email"`、`operator="system"`。**客户档案时间线不改**——自动与人工落在同一条线上，这是"触达全靠人记"这个断层消失的唯一办法。**队列里点"已处理"也必须写一条 `method="manual:*"` 的 touch**，否则 7 天硬抑制失效，客户第二天照样收到邮件。

**新增 `quota_3d` 列**：三处依赖——`topup_nudge` 的速率、§四 的余额与耗尽两个分支、`mature_brief` 的剩余天数。`ScanQuotaRollup` 本就一次扫 90 天算 7/14/30/90，加一个 `CASE WHEN` 零成本。

## 七、预算与 ROI

**总权益预算 = 上月平台消耗 × 3%（硬顶 5%）**，按额度面值计；现金成本 ≈ 面值 × 上游成本率 ≈ 2%。

| 层 | 占比 | 理由 |
|---|---|---|
| K | 50% | 但只对增量返 |
| A | 20% | 培养下一批 K |
| 新客 | 20% | 现方案给新客 0 预算，恰是最该投的人群 |
| 风险/唤醒 | 10% | 止血，不求回报 |

**① 返额只对增量。** 「K 返月消耗 5–10%」与「总预算 3%」冲突——K+A 常占消耗 70–80%，光 K 返 5% 就吃掉全平台 3.5–4%。改为「环比增量 × 10%，上限=账户月消耗 5%」：只为增长付钱。

**② ROI 门槛 = `增量消耗 ÷ 已消耗赠送面值 ≥ 1/m`（毛利 30% 即 3.3）。** 由 `Δ利润 = m·I − C` 得 `I/C = 1/m`，与替代率无关——替代率已被"增量"这个分子吸收。此前设过的 1.5 与 [2.3, 3.3] 灰区均作废，后者把替代损失扣了两次。m 未知期偏严比偏松安全。**推论：送 10 元须换回 33 元增量，故小额定向远优于大额普发。**

**三个易错点**：

- **`C` 用已消耗面值**（发放面值只进预算表控敞口）；**分子必须是增量**——用"窗口总消耗 ÷ C"会多算一份 C，门槛漂成 `B/C + 1/m`，等于没有门槛。
- **新客不套 ROI**：从未付费者赠送用完也无收入回流（`I≤C` 时恒亏），那是获客成本不是 ROI 低；改看**首充转化率**（30/60 天）与**回本周期**（首充 ÷ 人均 `c·C`）。混进 ROI 表会让这块预算永远显示亏损、第一个被砍。
- **基线 = 前 4 周周消耗中位数 × 4 × (1 + 除本批外的大盘增速)**；结算窗 28 天，第 7/14/21 天给中期读数（超过前 4 周周环比 MAD 才判方向）。

停投三线（任一命中）：唤醒率连续两轮 < 8%；批次 ROI < 3.3（新客看首充转化率）；权益成本 > 该人群增量消耗 30%。未结算的锁是**同人群 × 同 play**，不是全局——否则一个 K 层返额批次在跑，28 天内所有新客批次都开不了。

## 八、<500 用户时不值得建

- **拖拽式旅程编辑器**：旅程不超 6 条，硬编码一天改一版；编辑器要两周。
- **A/B 测试与发送时机优化**：100 人分两组测不出显著性，只测"发 vs 不发"。
- **多渠道矩阵**：只保留邮件 + 站内。
- **实时事件流**：日批足够；唯一例外 `quota_wall`，它在请求路径上。
- **无审批全自动发送**：先待发队列 + 每日批准，某类 play 连续 4 周零误报再放开。

## 九、五条不能做

1. **故障窗口内不发任何营销触达。** 有未解 P0 时唯一允许的沟通是事故说明——此时发券 = 承认"我知道你坏了，但我只关心你充值"。
2. **不把"余额不足"写成催充。** 只报账，不打折。开发者不反感自己的账，反感被催。
3. **K 层不发模板。** 每封带一条只有他能看到的信息。一封群发毁掉的关系，十次 1v1 补不回来。
4. **不用"我们想你了"唤醒。** 沉默 30 天不是想你了，是项目结束或换了供应商。内容只能是"新增了什么"和"可随时导出"。
5. **不给未验证身份的账户自动发权益。** 只发给 `topup_total > 0` 或已验证企业邮箱的。
