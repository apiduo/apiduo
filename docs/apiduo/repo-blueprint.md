# 仓库整体规划：把 apiduo 做成 Agent 接入层

> 2026-11-16。承接 `merge-cost-forecast.md`（成本模型）、`module-isolation-plan.md`（挂接点分档）、
> `upstream-sync.md`（同步规范）。本文是**总纲**：定归属、定契约、定顺序。
> 三份前文的结论仍然有效，本文只修正其中已被实测推翻的部分（见 §7.1）。

## 0. 一页结论

**主张：apiduo 的产品是「Agent 的接入契约」，new-api 是它下面的引擎。**

这不是定位口号，是降本手段。契约一旦是对外接口，实现就必然落在接口层；接口层是新文件；
新文件零合并成本。**越 Agent-first，越不需要改上游。** 反过来，凡是"必须改上游函数体才能实现"
的需求，都说明它其实是引擎能力，不属于我们的产品面 —— 这条判据能筛掉大部分看似该做的功能。

三条原则由此收敛成一条执行规则：

> 新能力先表达成接口，再用旧接口组合实现。只有「接口表达不了」的引擎行为才允许改上游，
> 且必须进 `.apiduo/merge-budget.txt`。

**三个决定（本文的全部结论）：**

| # | 决定 | 效果 |
|---|---|---|
| 1 | 新接口收敛到四个前缀 + **单点注册**；存量路由不迁移 | 以后加接口零新增挂接点；`router/api-router.go` 的 10 块不再增长 |
| 2 | 组合三选一：HTTP 回环 / 进程内调用 / 同包新文件。**产生上游请求的一律回环** | 计费、选路、重试、日志只有一份实现 |
| 3 | 预算从「四总量」升级到「加权 + 删除行趋零 + 热文件块数」 | 冷热块不再等价；语义冲突的唯一来源被单独计量 |

**最该做的三件事（P0，约 1 天）：**

1. 修掉当前两处未标记代码（`users-columns.tsx` 44 行、`types.ts` 4 行），`markercheck` 现在就是红的。
2. `router/apiduo_routes.go` 建注册表，`api-router.go` 的 10 块里新接口改走它。
3. `markercheck` 加 `-heat`：按上游改动频率给每个文件分档，输出加权风险与热文件块数（只报数，不判定）。

## 1. 第一性原理：这个 fork 凭什么成立

### 1.1 反事实测试

删掉 apiduo，只剩 new-api。用户损失什么？

如果答案是「控制台不好看」，那这个 fork 不该存在 —— 上游每两周发一个版本，界面迟早追上，
而维护税是永久的。如果答案是「Agent 接不进来」，那 fork 成立，因为上游的路线图上没有这件事。

上游做的是：**人类在控制台配渠道，程序用 OpenAI SDK 调一个「已知名字」的模型。**
它不做的是：**Agent 在运行时发现能力边界、协商参数合法性、处理异步任务、判断该不该重试。**

差别不在「谁在调用」，而在**调用方是否已经知道答案**：SDK 假设你知道模型名、参数、端点；
Agent 要求这些在运行时才确定。四件事的共性是同一个：**它们都是契约问题，不是转发问题。**

### 1.2 成本的形态决定了成本的出口

合并成本函数（`merge-cost-forecast.md` §2）里，唯一不可测的是 `C_drift`（静默漂移），
唯一指数增长的是「函数体内的挂接块」。两者都指向同一个结论：

**改动位置比改动行数重要一个数量级。** 上游文件里插 200 行顶层代码，不如在一个热函数里插 5 行。

于是「把能力做成接口」和「不改上游」是同一件事的两种说法：接口的实现天然写在新文件里，
新文件不在上游的 diff 范围内。

### 1.3 于是得到一条判据

> **如果一个需求无法表达成「一条新的接口 + 对旧接口的组合」，那它就不是我们的需求，
> 而是引擎的需求。引擎的需求只有三条路：不做、等上游、进预算。**

这条判据的价值是**筛掉需求**，不是解释工作量。举例（实测数据见 §6.1）：

| 需求 | 能表达成接口吗 | 结论 |
|---|---|---|
| MCP 工具：图片/视频生成 | 能（`/mcp` + 回环 `/v1`） | 做，零挂接点 |
| Agent 签名换 key | 能（`/api/agent/*`） | 做，零挂接点 |
| 多 key 粘性策略 | 能（常量放新文件 + 1 个守卫） | 做，3 块 |
| 图像 edits 折叠成 generations | **不能**（改 `adaptor.go` 的函数体） | 引擎需求 → 进预算，11 块 |
| 在渠道表单加一个「协议」下拉 | 能（注册表插槽） | 做，但必须注册表化，不能逐块插 |

## 2. 分层与归属

```
L2  Agent 接口层    mcp/ · router/apiduo_routes.go · controller/apiduo_*.go · /api/agent/*
     ↕ 只能向下
L1  组合层          pkg/apiduo/{trace,discount} · service/filerelay/
     ↕ 只能向下
L0  上游引擎        relay/ · model/ · service/(上游) · setting/ · relaykit/ · tokenkit/
     ↑ 只允许在标记块内反向调用一次
```

| 目录 | 归属 | 改动规则 | 现状 |
|---|---|---|---|
| `relay/` `model/` `middleware/` `controller/`(非 apiduo) | L0 | 只读；例外进预算，删除行必须为 0 | 199 块 / 67 文件（存量） |
| `router/` | L0 + 挂接 | 每功能 ≤1 块 | 25 块（`api-router.go` 10、`main.go` 5、`relay-router.go` 4） |
| `relaykit/` `tokenkit/` | L0 独立模块 | 同上 | `channel_settings.go` 6 块 |
| `mcp/` | L2 | 自由 | 42 文件 / 11.5k 行，1 个挂接点 |
| `pkg/apiduo/` | L1 | 自由；可 import L0 导出符号 | 31 文件 / 7.3k 行 |
| `controller/apiduo_*.go` `middleware/apiduo_*.go` | L2 | 自由（同包新文件） | 35 个文件（含测试） |
| `web/src/features/*` | 混合 | 上游目录只允许注册表插槽 | 234 块 / 79 文件 |
| `web/src/features/apiduo-*/` | L2 | 自由 | — |

三条硬规则（前两条沿用 `module-isolation-plan.md` §4，第三条新增）：

1. **不建独立 go module**。目标只是文件隔离，别引入 `replace` + 版本管理。`relaykit` 独立
   是因为它要给外部 import，我们没有这个需求。
2. **L2 不得 import `relay/` 内部包，也不得 import `router/`**。需要引擎能力就调 L0 的导出
   函数或走 HTTP —— 前者是编译期契约，后者是运行期契约，都强于「读内部变量」。
3. **同一个上游文件里的 apiduo 块 > 3 时，不允许再加块。** 新增必须先注册表化或走注册表插槽。
   现存超限的文件（`channel-mutate-drawer.tsx` 23 块、`advanced-custom-editor-dialog.tsx` 17 块）
   是历史累积，不追溯；但它们是「停止增长」的起点，不是「可以继续」的先例。

### 2.1 新功能的标准骨架

照这个建，天然零挂接点：

```
mcp/                          L2 协议面（仅当要暴露给 Agent）
controller/apiduo_xxx.go      L2 薄 handler：解析 → 调 L1 → 写响应
pkg/apiduo/xxx/               L1 逻辑与测试
router/apiduo_routes.go       L2 注册一行
web/src/features/apiduo-xxx/  L2 前端
```

**四个位置之外不该出现这个功能的名字。** 如果出现了，要么它越层了，要么它本来就是引擎需求 ——
两种情况都该在写代码之前停下来说明。

## 3. 接口契约

### 3.1 四个前缀

| 前缀 | 语义 | 鉴权 | 现状 |
|---|---|---|---|
| `/v1/*` | **旧接口**：OpenAI/方舟兼容的转发入口 | TokenAuth | 上游，只读 |
| `/api/*`（其余） | 上游管理面 | Session/PAT | 上游 + 10 块挂接 |
| `/api/agent/*` | Agent 自注册与凭证 | 签名 / TokenAuth | 新增，2+3 路由 |
| `/api/apiduo/*` | apiduo 自己的管理面 | Session | 部分（trace 在用） |
| `/mcp` | MCP 协议端点 | TokenAuthReadOnly | 新增，1 个入口 |

**规则：新接口一律落在后三个前缀之一。** 理由是可验证：`grep -c 'apiduo\|agent' router/`
能数出我们加了什么，而上游重构 `apiRouter` 时不会撞路径。

**不迁移存量。** `/api/data/sk`、`/api/growth/*`、`/api/appearance` 这些已经在用，迁移要改前端、
改外部脚本、可能断掉已发出去的 key，收益只是"整齐"。**整齐不是收益。**
从下一个新接口开始生效即可 —— 这本身就是「新功能新接口、旧功能旧接口」的自洽应用。

### 3.2 单点注册

`router/api-router.go` 现在 10 块，每加一个功能组加一块。改成：

```go
// router/apiduo_routes.go —— 新文件，上游不认识
package router

type apiduoModule interface{ Register(*gin.RouterGroup) }

var apiduoModules []apiduoModule

func registerApiduoRoutes(g *gin.RouterGroup) {
    for _, m := range apiduoModules { m.Register(g) }
}
```

`api-router.go` 里只留一块：

```go
// APIDUO:routes:BEGIN
registerApiduoRoutes(apiRouter)
// APIDUO:routes:END
```

**收益**：以后新增 10 个接口组，`api-router.go` 仍是 1 块。这一处改造是净下降（10 → 1），
且不改任何既有路由行为。

**代价**：模块必须有确定顺序（中间件顺序敏感），所以 `apiduoModules` 要显式切片初始化而不是
`init()` 注册 —— 顺序写在代码里，不靠 import 顺序。

### 3.3 Agent 接口的六条硬约束

一条接口算不算「Agent 面」，按这六条验。少任何一条，都需要人在中间看一眼 —— 那它就退化成
「给人用的 API」，只是调用方从浏览器换成了脚本。

| # | 约束 | 反例 | 现状 |
|---|---|---|---|
| 1 | **能力可发现**：能查到 kind、参数枚举、上限、一行价格 | 只能读文档 | `models.list` ✓ |
| 2 | **约束可执行**：本地拦截优先于上游报错；未声明 ≠ 0 | 把 `nil` 当 0，锁死图生图 | 三态约定 ✓ |
| 3 | **异步有任务语义**：返回 handle，可查、可取消、状态可枚举 | 只能盲轮询 HTTP 200 | `task.get` 过渡中 |
| 4 | **错误可编程**：`code / retryable / retry_action` | 只回一句中文 | `protocol_error.go` ✓ |
| 5 | **计费可解释**：一行可读文本，不折算成精确数字 | 假精确的 `$0.0231` | `cost` 字段 ✓ |
| 6 | **幂等**：重试不重复计费 | 重发即再扣一次 | `idempotency.go` ✓ |

前五条都已经在 `mcp/` 里落地，说明这套判据不是纸面标准。新增 Agent 接口时逐条对照；
任何一条做不到，应该在设计文档里写明为什么，而不是默认跳过。

## 4. 组合：三选一

这是原则二的直译：**新功能写新接口（适配），旧功能经旧接口组合（不重写）。**

具体有三种实现方式，边界不同，不能混用：

| 方式 | 边界 | 单位成本 | 适用 | 已有实例 |
|---|---|---|---|---|
| **HTTP 回环** | 进程内 HTTP 到自己 | 序列化 + 鉴权透传 + 错误翻译 | **任何会产生上游请求的能力** | `mcp/protocol_upstream.go` 打 `/v1/*` |
| **进程内调用** | Go 函数 | 上游签名变则编译失败（好事） | 只读派生、聚合、查询 | `controller/apiduo_growth.go` 调 `model` |
| **同包新文件** | 包内符号 | 零挂接点 | 只加常量/类型/方法，不改行为 | `constant/apiduo_multi_key_mode.go` |

### 4.1 判据（决策树）

```
这个能力会产生上游请求（花钱）吗？
├─ 会 → HTTP 回环。没有例外。
│        计费、额度、选路、重试、日志、审计只在 relay 里有一份实现。
└─ 不会 → 只读派生/聚合吗？
          ├─ 是 → 进程内调用 L0 的导出函数
          └─ 否 → 只是加枚举/字段/类型吗？
                  ├─ 是 → 同包新文件
                  └─ 否 → 这是「改旧行为」，进预算，且必须是最小切入点
```

**「会产生上游请求的一律回环」是硬规则，不是偏好。** 一旦允许某个新接口在进程内自己扣额度，
就会出现两份计费逻辑；两份逻辑漂移的那天，账对不上，而且找不到是哪一份错的。
MCP 现在的形态是这条规则的样板：它自己不扣费，只把请求翻译好交给 `/v1`。

### 4.2 回环的三条纪律

回环不是免费的，它有三个已知代价，各自有纪律：

1. **身份必须透传，不能提权。** 回环请求带发起者的 key，不带服务身份。`mcp` 用
   `injectBearer` + `captureCaller` 做的就是这个 —— 少了它，审计里所有 MCP 调用都是同一个"服务"，
   出了事追不到人。
2. **错误必须翻译。** 旧接口的错误是给人看的响应体，新接口要的是 `code / retryable /
   retry_action`。`mcp/protocol_error.go` 已经在做。**不允许直接把上游报文塞进新接口的 error**，
   否则 Agent 无法判断该不该重试。
3. **不得复制业务规则。** 判据：把 `/v1` 的实现删掉，新接口应该只剩 HTTP 调用，而不是要重写
   一套逻辑。如果做不到，说明这个能力被放错了层。

## 5. 成本模型：从总量到加权

### 5.1 现有机制的问题

`.apiduo/merge-budget.txt` 记四个总量（files / blocks / added / deleted），只降不升。
这套机制已经抓到三次真实上涨（见预算文件注释），有效。但它有一个盲区：

**冷热不分。** 往 `web/src/features/dashboard/index.tsx`（上游 180 天改 1 次）插 76 行，
和往 `channel-mutate-drawer.tsx`（180 天改 9 次）插 23 块，在预算上是同一件事。
实际风险差一个数量级 —— 前者可能一年不冲突，后者每季度都要重新看。

### 5.2 升级：三个新指标

不改判定逻辑（避免为了指标而失败），只加观测：

| 指标 | 定义 | 用途 |
|---|---|---|
| `weighted` | `Σ blocks × w(heat)`，`w` = 1/2/4/8 对应 H0..H3 | 单一数字表达"合并面有多贵" |
| `hot_blocks` | H2+H3 文件里的块数 | 单调下降的硬指标 |
| `deleted` | 删除的上游行 | 语义冲突的**唯一**来源，目标趋零 |

热度分档按 `git log --since=180.days upstream/main -- <file>` 的提交数：≤2 = H0（冷），
3-5 = H1，6-10 = H2，>10 = H3（每两周至少动一次）。阈值按实测分布定，不是取整：
本仓当前最热的上游文件是 9 次/180 天，若按「≤3 为冷」分档，「热文件」会永远是空集。
**热度必须由工具算，不能抄文档里的旧数字** —— 见附录。

### 5.3 删除行趋零

实测：前端删除 156 行（占 70%），后端 66 行。删除行意味着「我们改了上游写的东西」，
是 `C_sem`（语义冲突）的主要来源；纯插入在任何情况下都能一眼判断归属。

**口径（2026-11-16 已修）**：`deleted` 现在只统计「作者是上游」的被删行 —— 对每条被删行做
`git blame --abbrev=40`，再查 `git rev-list upstream/main` 的集合。旧口径数的是「base 里存在、
现在不存在」的所有行，等价重构会让它虚涨：把标记块里的代码搬进新文件时，被搬走的自有行也算进去。

修正后两个数字差一个数量级：**全仓真实删除面 40 行，旧口径报 242（虚高 6 倍）**。
典型例子是 `channel-mutate-drawer` 抽组件后旧口径 9 → 33，新口径 **0**；
`relay_task.go` 的 3 行删除里只有 2 行是上游的（第 107 行是我方后来插进去的）。

两个边界要记住：当前仓库的 `upstream/main` 是浅引用（253 个提交），2026-09-21 之前的行会归到
边界提交 —— 那仍是上游提交，判断成立；upstream 引用不可用时退回旧口径并**高估**，不会低报。

顺带把检查器从 21 秒降到 4 秒：`ls-tree` 一次判全部文件是否存在（原来 800 次 `cat-file`），
`git diff` 一次取全部差异（原来 156 次）。一个跑得久的闸门会被跳过，跳过的闸门等于没有。

已有的成功案例（`module-isolation-plan.md` §7.2）：把「改写赋值行」改成「保留上游行 + 后一行
镜像」，删除行 1 → 0。这个手法应该成为默认写法，而不是优化技巧：

> **同一处逻辑，优先「追加覆盖结果」而不是「改写原行」。** 只有当追加无法表达时才改写，
> 并在提交信息里写清为什么。

## 6. 实测：钱花在哪

### 6.1 分布（`go run ./tools/markercheck -cost`，2026-11-16）

| 维度 | 文件 | 块 | 新增行 | 删除行 |
|---|---|---|---|---|
| 前端 `web/` | 79 | **234** | 2513 | **156** |
| 后端 | 67 | 199 | 1652 | 66 |
| **合计** | **146** | **433** | **4165** | **222** |

预算基线是 142 / 426 / 4062 / 221，**当前实测已超线**：+4 文件 / +7 块 / +103 行 / +1 删除，
另有 48 行未标记。这不是机制失效，是机制在正常工作 —— 它抓住了未认账的改动。
（快照时间 2026-11-16 上午。当日 12:00 后工作区有并发进行的 UAPI 端点路由改造
（`pkg/endpoint/`、`middleware/distributor.go`），当前 `-cost` 会略高于上表 ——
那是另一批改动，不在本文范围内。）

**结论一：前端是主战场。** 54% 的块、60% 的新增行、**70% 的删除行**在前端。
（下表删除行是旧口径；按作者归因后全仓真实上游删除只有 40 行，见 §5.3。）
后端块数接近，删除行却不到前端的一半（66 vs 156）—— 因为「追加优先」在后端执行过一轮，
前端一次都没做过。

**结论二：块数高度集中。**

| 文件 | 块 | 上游 180d | 性质 |
|---|---|---|---|
| `web/src/features/channels/.../channel-mutate-drawer.tsx` | **23** | 9 | 11 个「按渠道类型显示面板」 |
| `web/src/features/channels/.../advanced-custom-editor-dialog.tsx` | **17** | 1 | 协议矩阵 + 5 个功能面板 |
| `web/src/features/channels/lib/channel-form.ts` | **17** | 8 | 表单状态映射 |
| `web/src/features/channels/types.ts` | **10** | — | 类型扩展 |

## 7. 对抗审查：不做什么

### 7.1 修正：不预做 gate 总线

`module-isolation-plan.md` §3.2 提议做一个请求门禁总线，把后端 64 块压到 12 块。那个判断基于
当时 64 块的数据。现在后端 199 块里，**请求路径上的横切逻辑只有 7 块**
（`middleware/distributor.go` 3、`relay/relay_task.go` 2、`relay/common/relay_info.go` 1、
`service/relay_error.go` 1）。

为一个 7 块的场景建总线（接口 + 注册表 + 上下文结构 + 全部功能重写注册），是净亏：
新增一个抽象层，每个功能都要写 `Match/Handle`，而收益要等到 25 块以上才出现。

**结论：不预做。触发条件是「请求路径类挂接点 > 25 块」**（现在 7 块的 3.5 倍），在那之前继续用
同包新文件 + 1 块插入。

### 7.2 明确不选的四种策略

| 策略 | 为什么不选 |
|---|---|
| **vendor 上游 / 快照合并** | 失去上游 git 历史与 cherry-pick 能力；一次全量替换，冲突从"块级"变成"目录级" |
| **patch 队列（quilt 式）** | 每轮全量重放，一处上下文变动导致整条队列序号偏移，比 merge 更难维护 |
| **rebase-only** | 共享分支不能 rebase；且 rebase 会把冲突解在错误的作者名下，追溯失效 |
| **feature flag 框架** | 上游没有，引入等于新增一层高危挂接面；现有 `env` 开关（如 `shadow`/`enforce`）已够用 |

### 7.3 不做的事

- **不追「零冲突」**。零冲突的代价是把功能全塞进新文件导致重复实现（复制 480 行组件比改 2 行
  贵得多，见预算文件 2026-11-13 的注释）。目标是「冲突十分钟能解」，不是「没有冲突」。
- **不做全量前缀迁移**（§3.1）。
- **不把协议矩阵放后端**（`merge-cost-forecast.md` §5.2 已论证，结论不变）。
- **不做成本提示类协议项**（`annotations` / `input_required`），2026-11-15 已定。
- **不为整齐而批量重写** `!== ROLE.SUPER_ADMIN` 这类写法（`CONVENTIONS.md` 已定）。
