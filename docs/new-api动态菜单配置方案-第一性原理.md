# new-api 动态应用/菜单配置功能 — 第一性原理解决方案

> 目标：在 new-api 管理端增加新功能，通过表单形式动态配置"新应用或子页面"，可出现在左侧边栏（推荐）或顶部导航，配置即生效。

---

## 一、第一性原理推导

### 1.1 回到本质：这个功能到底在解决什么

剥离所有现有实现，问题可以还原为三个不可再分的事实：

**事实 1：导航是"索引"，不是"功能"**
导航本身不产生价值，它的唯一作用是**把用户带到某个目标**。因此一个导航项的全部本质属性只有三个：

- 叫什么（标识）
- 放到哪（位置）
- 点了去哪（动作）

任何其他字段（图标、分组、排序、权限）都是这三个属性的修饰，可有可无，有了体验更好。

**事实 2："动态"的本质是"数据与代码分离"**
硬编码菜单 = 导航定义写在程序里；动态菜单 = 导航定义存在数据里。
所以做这个功能的**唯一技术动作**就是：把一份原本编译期固定的声明，挪到运行期可读写的存储中。除此之外没有新东西。

**事实 3：配置的权威必须唯一**
一个入口要么由系统定义，要么由用户定义。如果两处都能定义同一路径，就会出现"我改了但没生效"——因为改的不是实际生效的那份。这是此类功能 90% 的 bug 来源。

### 1.2 由事实推导出的硬性约束

| 事实 | 推出的约束 |
|---|---|
| 事实 1 | 数据模型最小集 = {名称, 位置, 动作}，先让这三元组跑通，其他字段都是增量 |
| 事实 2 | 前端导航必须从**同一份数据源**渲染，系统内置项和自定义项走同一条渲染管线 |
| 事实 3 | 每条导航只能有一个 owner（system / custom），渲染时做**一次合并**，不允许运行时多处拼合 |

---

## 二、最小可行系统（MVP）

由上面推导，最小系统只需 4 个组件：

**1. 一份数据（表）**

```
{ name, placement(侧/顶), action(内嵌URL / 外链URL / 站内路径) }
```

加上运维必需的 `sort`、`status`。这就是第一版全部字段。

**2. 一个写入口（管理表单）**

增删改查 + 排序 + 启停。形态参考 new-api 现有"菜单设置"页（列表 + 就地编辑表单），不需要重新设计。

**3. 一个读出口（接口）**

前端启动时拉一次导航数据。**关键决策：系统内置项不硬编码在前端组件里，而是作为 owner=system 的记录同样存/发出来**，这样前端永远只渲染一份数据，事实 2、3 同时满足。

**4. 一个渲染器**

- 位置决定渲染到哪（侧边栏区块 / 顶部条）
- action 的协议头决定行为：
  - `http(s)://` → 新窗口或 iframe（由 display_type 再分）
  - `/xxx` → 站内路由

---

## 三、数据模型（完整版）

一张 `nav_apps` 表即可：

| 字段 | 说明 |
|---|---|
| id / sort | 主键与排序权重 |
| name | 展示名称（多语言可存 JSON 或走 i18n key） |
| icon | 图标：支持 emoji / iconfont 类名 / 图片 URL |
| path | 路径或 URL（http 开头视为外链） |
| display_type | **内嵌 iframe / 新标签页打开 / 站内路由** |
| category | 分组：如"聊天工具"、"实用工具"，对应侧边栏的分组折叠 |
| placement | 位置：**侧边栏** or **顶部导航**（支持同时选） |
| content | 内嵌时的 iframe 地址或 HTML 内容 |
| visibility | 可见范围：游客 / 登录用户 / 指定分组（复用 new-api 用户分组体系） |
| status | 启用/停用开关 |
| is_system | 是否系统内置项（防止误删 主页/控制台/定价 等） |
| owner | system / custom —— 保证配置权威唯一 |

简单场景下分组可以直接做成字段枚举，不需要单独的 `nav_categories` 表。

### 逐字段论证（每项都要回答"它满足哪条用户诉求"）

第一性原理的精髓是**不为不存在的需求设计**：

- **分组 category** → 解决"条目多了找不着"（超过 ~7 个就必须分组，这是认知负荷极限）
- **图标 icon** → 解决"纯文字扫视慢"，可选
- **visibility（游客/登录/分组）** → 解决"不同用户看到不同导航"，与 new-api 已有的用户分组体系对齐，不要另造权限模型
- **is_system** → 解决事实 3：保护系统项不被删导致管理页失联
- **多语言** → 可以后置，第一版直接存展示名

## 四、管理端交互（表单形态）

沿用现有"菜单设置"页形态，做三个改进：

1. **列表即编辑**：保留拖拽排序列表，点选某项，下方表单就地编辑，避免弹窗套弹窗
2. **按位置分两个 Tab**：「侧边栏应用」「顶部菜单」，配置心智更清晰
3. **添加菜单时的类型分步**：
   - 选显示类型（内嵌/外链/路由）→ 表单动态切换字段：内嵌才出现 content 编辑器，外链才出现"是否新窗口"
   - 外链自动校验 http(s) 前缀，站内路由校验存在性
   - 表单内提示："内嵌需目标站点允许被 iframe 加载（X-Frame-Options）"

**配置即生效**：保存即写库 + 失效前端缓存，不需要重启。前端导航数据走接口（或并入已有的 option/config 接口），加轻缓存（内存 + 变更时失效），避免每次请求都打库。

---

## 五、用户端渲染（形态决策）

**导航的容量由空间决定：**

- 顶部条：宽度有限，超过 5~6 项必然溢出 → 只放高频入口
- 侧边栏：纵向可滚动、可折叠，容量大一个数量级 → 承接动态应用列表

**结论：动态应用默认进侧边栏分组区块（分组折叠 + 外链图标形态），顶部只作为可选 placement。** 因为无法控制用户加多少应用，必须把默认承载容器选成容量大的那个。

渲染规则：

- **placement=侧边栏**：插入到侧边栏顶部（主导航之上），按 category 分组成可折叠区块，每项右侧渲染外链小图标
- **placement=顶部**：追加到现有顶部菜单末尾
- **display_type=内嵌**：站内注册动态路由 `/app/:id`，页面内放 iframe 加载 content
- **display_type=外链**：点击直接新窗口打开，不建路由
- **visibility 过滤**：渲染前按当前用户角色/分组过滤，不可见的项直接不下发

---

## 六、权限与边界

- 仅 **root 管理员** 可访问「菜单设置」（位于系统设置区，权限天然收敛）
- 系统内置项（is_system=1）：可改名称/排序/停用，**不可删除、不可改路径**，防止把入口全删了导致无法回退管理页
- 删除自定义项二次确认；列表留一个"恢复默认"按钮重置为出厂导航

---

## 七、落地步骤（每步均可独立验证）

| 步骤 | 内容 | 说明 |
|---|---|---|
| 1 | **导航数据接口化** | 把硬编码菜单改为接口下发，系统内置项也入库。这是地基，必须先做 |
| 2 | 管理表单 CRUD | 配置能力：增删改查 + 排序 + 启停 |
| 3 | iframe/外链容器页 | 动作能力：动态路由 `/app/:id` + iframe 容器 |
| 4 | 分组 + 权限过滤 | 规模化的修饰项 |
| 5 | 缓存与变更失效 | 性能修饰项，最后做 |

> **架构风险提示**：如果跳过第 1 步直接做表单，会得到两套导航逻辑（硬编码 + 动态），永远无法干净合并——这是本项目唯一真正的架构风险点。

---

## 八、一句话总结

这个功能 = 把导航从"代码里的常量"变成"库里的记录"，然后用同一份数据驱动管理表单和用户界面；先让三元组 {名称, 位置, 动作} 跑通，其余字段全部是应对具体诉求的增量，且每个增量都要能说清它在解决什么问题。
