为什么是鱼骨，而不是甘特图

这份原型的核心判断：鱼骨图在这件事上成立，但只在特定前提成立。

1. 鱼骨图原本不是画时间的

石川图的结构是「结果 ← 多类原因」，主脊从结果倒推，骨头是原因分类（人 / 机 / 料 / 法 / 环）。 它没有刻度，分支位置是示意，不是比例。

把时间放上主脊，等于换了一个约定：骨头的锚点位置同时表示「什么时候」。 这个改写只在一种情况下成立 —— 各阶段是离散的、数量有限的（4 到 6 个节点）。 如果时间节点是连续的，或者需要精确到小时的等比例刻度，它立刻失效，那时候应该用甘特图或时间轴。

判断标准。问一句：某个节点比其他节点晚了两天，图上要不要体现这个差距？ 要 → 甘特图。不要，只想表达先后 → 鱼骨图。

2. 上下两扇解决的是发布公告最难写的事

发布公告的读者分两类：内部想知道「我们做了什么」，外部想知道「我会不会受影响」。 常规写法是把这两件事混在一段列表里，读者要自己筛。

鱼骨图的上下分扇天然把这两类分开：

  • 上扇 = 动作：切分支、灰度、全量 —— 内部视角
  • 下扇 = 影响：谁能看见、要不要改代码、有没有回退按钮 —— 外部视角

这不是为了好看，是为了让外部读者只看下半张图。

3. 破坏性变更必须单独出图例

所有骨头一个颜色，等于声明「这些事同等重要」。实际不是： 3 项破坏性变更和 1 项 bugfix 放同一张图里，读者会按顺序读完，然后漏掉那 3 项。

所以破坏性的骨用红色，并在图头用一枚 含 1 项破坏性变更 的标签前置声明。 标签比颜色更可靠 —— 灰度打印或色盲读者也能分辨。

4. 时间滑块的作用被低估了

静态鱼骨图只能表达「有这几个阶段」。加上滑块后，同一个图形可以回答三个问题：

  • 现在走到哪了（当前阶段高亮，未到达的骨变淡）
  • 这个阶段之前发生过什么
  • 下一阶段要发生什么

公告的访问高峰在发布前后 24 小时，那时读者最需要的就是「现在到哪了」。

落地建议。鱼骨图由结构化数据渲染，不要让人在后台手绘： { version, phases:[{t, at, actions[], impacts[], breaking[]}] }。 图、清单、时间窗、订阅邮件四处共用这一份数据，避免图改了文字没改。

5. 不这么做的时候

  • 只有 1–2 个变更项：不要画图，三行列表更清楚。
  • 纯修复版本（patch）：没有时间窗，直接列 bug 编号。
  • 需要精确时刻表（比如对齐某个外部截止时间）：甘特图或带刻度的横轴。
  • 节点超过 7 个：主脊会挤，改成纵向时间轴。

6. 与前一版公告设计的关系

这份是「公告的一种内容形态」，不是新的存储模型。它复用上一轮的 announcements 表，只是把 content 换成了结构化的发布数据：

上一轮字段发布公告里的含义
titlev0.9.4 发布：端点能力表独立
level含破坏性变更 → warning
starts_at全量完成时刻，公告即刻可见
ends_at观察期结束，到时自动从面板移除
placementsdashboard + popover，不进横幅
新增 release{version, phases[], breaking[]} 子结构

也就是说：鱼骨只是渲染器，不是新的对象类型。公告仍然只有一张表， 发布公告是其中 kind = release 的一种。
