# 额度闸门 · 防超刷方案（v0.3）

> 状态：设计稿，未落代码。配套可交互原型：`design/user-rate-limit.html`
> 目标读者：后端 / 产品 / 运营
> **唯一目标：让单账号的最大可损失金额归零。** 不做速率公平分配，不做大户提速，不做档位体系。

---

## 1. 结论先行

1. 防超刷不需要"限速分级"。把预扣改成**覆盖单请求成本上界**，再让结算**不允许透支**，单账号损失上界就从 `K × (c − p)` 变成 `0`，与并发数、码龄、充值额都无关。
2. 现在之所以需要并发闸，是因为预扣只算输入（`promptTokens × 1`），输出零预扣（`completionRatio` 完全没进预扣）。补齐这一项后，**预扣额本身就构成并发闸**：每个在途请求占用 `p`，可用并发天然等于 `⌊Q ÷ p⌋`，不需要另建 Redis 并发计数器。
3. 当前最大的洞不是"低余额账号"，而是**信任旁路**：余额 > $10 的用户完全不预扣（`TrustQuotaUSD` 默认 10），`p = 0`，`K` 无结构约束。这个门的判据必须从"用户余额"改成"单请求额度"。

---

## 2. 判据

超刷 = 用极小的自有资金换走远超支付能力的服务量。唯一判据：

```
单账号最大损失 L < 账号获取成本（邮箱/手机号/邀请码 + 风控成本）
```

`L` 的展开式只有三个变量：

```
L ≈ K × (c̄ − p̄)      K = 在途并发，c̄ = 单请求实际成本，p̄ = 单请求预扣
```

于是只有三个旋钮：**抬 p、压 K、结算拒绝**。三者中 `p̄ ≥ c̄` 是唯一能把 `L` 打到 0 的，且没有运营成本；压 `K` 有用户可见代价，只应作为前者的兜底。

## 3. 代码事实：洞在哪一环

| # | 位置 | 事实 | 影响 |
|---|---|---|---|
| H1 | `service/billing_session.go:329-352`、`setting/operation_setting/quota_setting.go:20` | `TrustQuotaUSD` 默认 **10**：`relayInfo.UserQuota > 10 USD` 且令牌充足时 `effectiveQuota = 0`，**完全不预扣**。判定用的是请求开始时的快照，不随在途请求递减 | `p̄ = 0`，`K` 无上限。余额越大越危险，与"低额度"无关 |
| H2 | `relay/helper/price.go:110`、`:410` | 倍率模式预扣 = `promptTokens × PreConsumeMultiplier`（默认 1）；tiered_expr 模式硬编码 `C: 0` | **输出侧零预扣**。200 输入 token + 8K 输出的请求，预扣 ≈ ¥0.004，实际成本 ¥0.9 |
| H3 | `service/quota.go:462-470` → `model/user.go:1387` | 差额补扣 `DecreaseUserQuota` 无余额条件，也没有任何负额度下限 | 余额可被扣成任意负值，`L` 只受 `K` 约束 |
| H4 | `middleware/` | 只有 RPM 窗口计数（`model-rate-limit.go`，默认 1000 成功请求/分钟），**没有 per-user 并发限制** | `K` 的实际唯一约束是上游渠道限流 |

已确认不需要改的部分：

- 预扣本身是原子的：`TryReserveUserQuota` 走 `UPDATE ... WHERE quota >= ?` 或 Redis Lua（`model/quota_reserve.go:143-198`），不存在"并发读到同一份余额全部放行"的 TOCTOU；Redis 异常时降级到 DB 条件更新，**不会 fail-open**。
- 按次计费模型（`usePrice`）预扣 = 全额单价 × n（`relay/helper/price.go` 的 `ApplyOtherRatiosToFloat` 分支），本来就是对的。
- 异步任务走 `ForcePreConsume`，跳过信任旁路，本来就是对的。
- 新用户赠送 / 邀请返利默认都是 0（`common/constants.go:141-143`），默认配置下不存在小号刷赠额。

## 4. 方案：三段式

### 4.1 预扣覆盖单请求成本上界

```
p = ⌈prompt_tokens × input_mult × in_price⌉
  + ⌈min(max_tokens, cap_out(model)) × out_price⌉
```

- `out_price = in_price × completionRatio`，`in_price` 由模型倍率 × 分组倍率得到；实现上就是现有的 `modelRatio × groupRatio`，输出项乘 `completionRatio`。
- `cap_out(model)` 取该模型**真实最大输出**（不是 P95），配置化，允许按模型覆盖。
- 把上游请求的 `max_tokens` clamp 到 `cap_out`，否则 `p` 不是上界。
- tiered_expr 模式把 `C` 从 `0` 换成 `min(max_tokens, cap_out)` 代入表达式取上界。

这样 `c ≤ p` 恒成立，结算差额只剩"退款"一个方向。

### 4.2 预扣即并发闸

```
可用并发 K = ⌊Q ÷ p⌋        Q = users.quota（已扣除在途预扣）
```

不需要额外计数器：每个在途请求已经原子地占住 `p`，第 `K+1` 个请求的 `TryReserveUserQuota` 自然失败。Redis 挂了走 DB 条件更新，约束依然成立。

只有当 `p = 0` 时该式退化，见 4.5。

### 4.3 结算不允许透支（floor = 0）

```
差额 d = c − p
d ≤ 0  → 退还 −d（现状已支持）
d > 0  → 只扣到余额为 0，剩余记「坏账」，立即停用账号并进复核队列
```

`floor = 0` 的语义是：**平台不为任何账号垫资**。`d > 0` 在 4.1 生效后只可能来自上游计价偏差（reasoning token 超预期、倍率热更、缓存未命中），属于异常而非常态，出现即报警。

实现要点：扣款语句改为带条件的 clamp（`WHERE quota >= d`，失败则读旧值后置 0 并记录 `lost = d − oldQ`），不能用当前的 `DecreaseUserQuota` 直减。

### 4.4 免预扣语义修正：从"看余额"改成"看单请求"

现状：余额 > $10 就免预扣 —— 判据错了，余额大恰恰意味着单次爆发的绝对损失大。

改为：**`p < PRE_CONSUME_SKIP_QUOTA`（建议 ¥0.02）时免预扣**。

- 微小请求免预扣，省一次事务，差额上限就是 ¥0.02，无套利价值。
- 大请求必预扣，与用户余额无关。
- `TrustQuotaUSD` 默认值从 10 改为 0（关闭），避免旧语义残留。

### 4.5 唯一需要非金额闸的地方：p = 0

免费模型（`modelRatio = 0`）或 `groupRatio = 0` 时 `p = 0`，金额闸完全失效，仍可无限并发打日志与上游。

处置：对 `p = 0` 的请求启用一层独立的 per-user 并发上限（Redis `INCR` + TTL，`defer DECR`），默认 4，可配置。这是整个方案里唯一需要新增计数器的场景，范围明确、可失败降级。

## 6. v0.2 中被砍掉的部分

| 被砍 | 原因 |
|---|---|
| T0–T5 档位表、贡献值 `S = R + min(R, C)` | 只服务于"公平分配 + 大户提速"。防超刷下 `p` 已把并发锚定在余额上，档位是重复约束 |
| 注册时长封顶 | 同上。新号的损失上界已是 0，无需按码龄压 |
| 保证金表（¥0.5 / ¥2 / ¥20） | 被 `p` 取代。保证金是 `p` 的粗糙近似，维护两套口径必然打架 |
| 7 日消耗聚合 / runway | v0.2 已删，v0.3 确认不需要 |
| 429 `gate=exposure/tier/age` 三分类 | 只剩下"余额不足"一种，语义收敛为 403 + 精确数字 |

保留自 v0.2 的判断：**控制变量是并发而不是 RPM**、**方案必须是可关闭的叠加层**、**Redis 异常不能 fail-open**。

## 8. 边界与风险

| # | 风险 | 处置 |
|---|---|---|
| 1 | 预扣变大导致 403 变多，正常用户被误伤 | `cap_out` 取模型真实上限而非固定值；403 文案给精确可行动项（"降 max_tokens 到 4096"或"充值 ¥X"） |
| 2 | 长流式请求全程占用 `p`，用户并发骤降 | 这是预期行为。用户端必须显示"在途占用 / 可用余额"，否则会被当成 bug |
| 3 | `cap_out` 配小 → 上游实际输出被截断 | clamp 只改 `max_tokens`；若上游无视上限仍输出更多，差额走 floor=0 + 坏账，并要求供应商侧核账 |
| 4 | 停用账号误伤大额正常用户 | 坏账触发只停"新请求"，在途请求跑完；提供运营白名单与一键恢复 |
| 5 | 订阅 / 套餐用户 | 预扣走订阅池，同样 clamp；订阅池不足返回 403，不得回落到钱包透支 |
| 6 | 退款 / 拒付 | 与预扣无关（预扣不看档位），只需保证退款后余额 < `p` 的请求被自然拒绝 |
| 7 | 免费模型被刷 | 4.5 的并发闸；`p = 0` 的请求同时计入 RPM 统计 |
| 8 | 倍率热更导致 `c > p` | 每请求快照倍率（现有 `PriceData` 已冻结），热更只影响后续请求 |
| 9 | 大量小账号分摊 | 单账号损失为 0 后，攻击者成本 = 账号获取成本，转由注册侧风控处理，不属于本方案 |
| 10 | 上游实际计费口径与本地估算不一致 | `c/p` 比值 P99 监控，超阈值告警；这是唯一会持续产生坏账的来源 |

---

## 9. 灰度与验收

1. `shadow`：只计算 `p` 与"若启用会 403 多少请求"，不改行为，跑 7 天。
2. 指标达标再 `enforce`：
   - `c/p > 1` 的请求占比 < 0.1%；
   - 因 `p` 变大新增的 403 中，`max_tokens > cap_out` 的占比（说明 cap 配小了）；
   - 坏账金额 / GMV < 0.05%。
3. 回滚：`OUTPUT_PRE_CONSUME_CAP` 置空即回到 v0.2 行为（只算输入），无需发版。

## 10. 待确认

1. `cap_out` 按模型逐个配置，还是给一个全局默认（如 8192）+ 例外表？前者准，后者省事。
2. `max_tokens` 超 `cap_out` 时是**截断**（clamp）还是**直接 400**？截断对用户友好，400 对账务更干净。
3. 坏账触发停用，是否要给"单次 ≤ ¥1"的豁免（避免正常用户一次异常就封号）？
4. 订阅制用户的 `p` 是否也按钱包同口径（全额预扣），还是给订阅池单独的透支容忍度？
