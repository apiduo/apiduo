口径

合并两个看板的前提是两边的数字能对上。以下五件事决定了这个页面为什么长这样。

合并的单位是动作，不是图表

增长看板回答「哪个客户要走了」，错误看板回答「哪里坏了」。两者服务同一个决策：今天先做哪件事。所以合并后的首页是一条队列，不是两组图表。图表留在「系统异常」页，供需要深挖时使用。

失败数的口径必须统一

logs 里 type=5 是尝试级的：重试循环里每次 attempt 失败都写一条。而 quota_data.count 是成功请求数。当前 growth 的 ScanFailures 用 COUNT(*)，把尝试数当成了请求数：

-- 现在（尝试级，虚高 1.8–2.7 倍）
COUNT(*) FROM logs WHERE type = 5

-- 应为（请求级）
COUNT(DISTINCT CASE WHEN request_id <> '' THEN request_id END)
+ SUM(CASE WHEN request_id = '' THEN 1 ELSE 0 END)

后果是 incident_rate_pct 的阈值比预期更早触发：一个请求失败三次，分子算 3，分母只算 0 次成功。比率会明显偏高，告警因此提前。

「有请求但消耗为 0」是最重要的一条

这条判据比失败率更有效：客户被故障打死时消耗为 0，只看消耗会把他判成「沉默」，而沉默的处置是「等」——恰好在最该救的时候等。这个逻辑现有实现已经有了，合并时保留原样。

事故型客户不能按分层筛掉

分层的作用是控制触达成本，但事故型客户往往量级不大、分层不高。如果队列先按分层过滤，最先被漏掉的正是这批人。所以队列默认不按分层过滤，只提供「仅付费客户」这一个可选项。

影响面要用请求级去重

「影响 20 个用户」来自 logs.username 去重，是下界：没有失败的用户不会出现，同一用户多 key 只算一个。它不能和「注册用户数」做除法。
