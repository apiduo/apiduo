    三个入口的职责边界

    同一份数据，不同紧迫度
    全站横幅只给 紧急。全局最多 1 条，可关闭但 24 小时内不再弹。占用横幅时必须挤掉前一条，不允许并行。
    铃铛通知最近 20 条进行中的公告。未读计数。打开不等于是已读，点进详情才算。
    控制台面板置顶区 + 最近 5 条。底部固定「查看历史公告」，过期的在这里可查，不再占主列表。
    登录页只给维护类。未登录可见，因此不得包含用户余额、内部渠道名等个体信息。

    已读判定

    服务端为准
    1
    已读 = 详情弹窗打开且停留 ≥ 1 秒。仅仅让列表进入视口不算。
    2
    确认 = 显式点「我已阅读」。只有勾了「要求确认」的公告才有这一步。
    3
    状态写 announcement_reads，跨设备一致。localStorage 只做乐观更新，失败回落。
    4
    公告内容被编辑 → version +1 → 已读记录按 (announcement_id, version) 存，改过的公告重新变未读。
    5
    未登录用户不记录已读，只在本地记忆 24 小时。

    用户可用动作

    知道了关闭详情，标记已读
    今日不再提示仅横幅。按自然日，第二天恢复
    查看历史公告面板底部入口，按时间倒序，含已过期
    标记全部已读铃铛页脚。不包含「要求确认」的公告
    结论：现状的问题不在展示层，在数据结构。 一条公告压成了「content + publishDate + type + extra」，四要素里缺三个 —— 受众、失效时间、送达回执。 改卡片样式不会让它变好，只会在一个没有状态的对象上继续堆样式。

    同一条公告，今天走的路径 vs 优化后

    现状：四个断点

    写全表内存编辑 → 一次 JSON 覆盖写 断：并发即丢
    发publishDate 只影响排序 断：定时不存在
    达推送全站，无受众 断：不该看的人看到了
    读打开铃铛即全部已读 断：读数不可信
    审无版本、无操作人 断：改错了查不到
    →

    优化后：五个闭环

    写单条草稿 + 发布前 9 项检查
    发状态由窗口派生，定时 = 未来窗口
    达受众过滤 + 展示位选择
    读进详情才算已读，跨设备一致
    审version + 操作人 + 变更差异
    为什么先修数据结构而不是先修界面。第 1、2、7、10 条都是数据模型问题， 在第 6 条（全量覆盖写）之上任何界面改进都会被下一次覆盖抹掉。界面是结果，不是起点。

    1. 字段模型

    字段类型约束与语义与现状的差异
    iduint64主键，只增不复用现状 id 由前端 max+1 生成，删一条再建会重号
    titlestring必填，1–60 字，纯文本新增
    contenttext1–2000 字，Markdown 子集上限从 500 放宽，白名单渲染
    extrastring0–200 字，弹窗底部灰字上限从 100 放宽
    levelenuminfo · success · warning · critical5 档收成 4 档
    starts_atdatetime必填从 publishDate 拆出
    ends_atdatetime?null = 长期有效新增
    audiencejson{"kind":"all"|"group"|"role"|"paid","values":[]}新增
    placementsjson[]banner · dashboard · popover · login新增
    pinnedbool面板顶部固定，同级别最多 2 条新增
    cta_label / cta_urlstring成对出现或都为空；URL 限 http(s) 与站内相对路径新增
    require_ackbool仅 critical 可置 true新增
    stateenumdraft · published · revoked · archived（人工闸门）新增
    versionuint32每次内容变更 +1，用于乐观锁与已读失效新增
    created_by / updated_byuint用户 id新增
    派生状态不落库。scheduled / active / expired 是 state = published && now vs [starts_at, ends_at) 的结果，每次读取时算。 落库要定时任务扫表改状态，任务一停状态就错 —— 用时间函数没有这个问题。

    2. 状态机

    草稿draft
    发布 →写 published
    定时now < starts_at
    到点 →无需动作
    进行中窗口内
    到点 →无需动作
    已过期now ≥ ends_at
    30 天后 →定时任务
    已归档archived
    下线任意时刻 → state = revoked，立刻从所有展示位消失，记录保留。用于「发错了」。
    删除只允许删草稿。已发布的不能删，只能下线或归档 —— 否则用户侧的历史会断。
    编辑进行中可改，改完 version +1，已读记录失效；但 critical 且已进过横幅的，改标题需二次确认。
    横幅互斥发布 banner + critical 时若已有占用，要么拒绝，要么在确认框里显示被挤掉的标题与剩余时间。

    4. 迁移路径

    阶段内容要点兼容处理
    P0 建表 + 字段 + 单条读写 + 受众过滤 一次性把 console_setting.announcements 的数据搬进新表： publishDate → starts_at，ends_at = null， title 取正文首句前 60 字，type 按映射表降级到 4 档。 announcements_enabled 保留为全局总闸。 旧 option 只读不写，保留一个版本周期
    P1 状态派生 + 状态机 + 工作台界面 过期自动移出主列表；revoked 立即下线；横幅互斥校验在发布接口里做，不在前端做。 旧字段继续返回，前端按新结构优先
    P2 已读落库 + 确认流 + 统计 announcement_reads(announcement_id, version, user_id, read_at, acked_at)， 唯一键前三列。localStorage 降级为乐观缓存，请求失败时回退本地、不报错。 旧 localStorage 数据一次性上报迁移（可选）
    P3 /api/notice 下线 转成 level=critical, placements=[banner] 的系统公告；保留 302 到 status 接口一个周期。 双写一版，观察后再移除

    5. 明确不做

    富文本编辑器不做。Markdown 子集 + 白名单渲染已够表达， 引入富文本会把 XSS 面从「渲染」扩大到「编辑与粘贴」。
    多语言公告不做。现阶段运营只有中文读者； 要做就做 content_i18n 一张附表，而不是在正文里堆多语言段落。
    定时撤回不做。ends_at 已经覆盖 「到点自动消失」；「到点自动删除」没有真实需求，且会破坏历史。
    A/B 测试不做。公告总量是每月个位数，样本量撑不起分组实验。
    邮件/短信外发不做。站内触达先跑通；外发涉及退订合规， 应独立立项，不要塞进公告表。
    已读强制拦截不做。除「要求确认」的紧急公告外， 任何遮挡式弹窗都会把用户推离主流程。
    取舍原则。每加一个字段，都要能回答「没有它会产生什么后果」。 标题解决辨认，窗口解决过期，受众解决误达，version 解决覆盖，已读落库解决读数不可信。 回答不了的字段（排序权重、阅读时长、曝光位次）一律不进表。
