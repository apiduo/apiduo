产品原型 · apiduo 控制台侧边栏

WorkBuddy 深链该落在侧边栏的哪儿

结论：深链不进目录，进动作区。侧边栏底部放一个常驻入口，点进去是一层 drill-in 的 「客户端工作台」，深链有多少条都收在里面；目录区最多保留三条用户自己钉的常用项。 这样未来从 5 条长到 50 条，侧边栏不变形。

2026-11-20 · 待评审 示例 scheme workbuddy://（需与客户端注册表对齐） 复用既有 drill-in 视图，不新增弹窗容器
01

为什么不能「在导航里加一行」

侧边栏的每一行都在回答同一个问题：我会去哪一页。深链回答的是另一个问题：我要离开网页。 三个本质差异决定了它不能和页面条目同构：

1没有页面

点完 Web 控制台还在原地，不发生任何导航。它因此不能有 active 态、不能有面包屑、不能被记成当前页。

→ 混进目录会出现两行同时高亮

2会失败

未安装客户端、系统没注册 scheme、浏览器静默拦截。普通链接最差是 404，深链最差是点了完全没反应。

→ 失败必须有人接住，不能交给浏览器

3带上下文

唤起客户端时通常要带上你正在看的东西——当前 API Key、当前模型、当前任务。同一个动作，参数不同就是不同入口。

→ 数量随资源维度线性膨胀

03

选定形态：一个入口，一层视图，一张接住失败的卡

方案 A 的形状是三步，每一步都对应上面的一条本质差异。复用既有的 drill-in 视图，不新建弹窗—— 侧边栏换视图时折叠态、移动端抽屉、返回箭头都是现成的。

步骤界面解决的问题
① 入口 侧边栏底部常驻一行
W · WorkBuddy · 12 个入口		 数量再多也只有一行，目录区永远是页面导航。折叠态退化为一个方块图标，仍可点。
② 收拢 drill-in 视图
← 返回 / 搜索 / 按用途分组		 承载 10–50 条不失控。搜索是主要发现方式，分组只做粗筛。头部不写标题，与既有视图一致。
③ 交接 右下角 handoff 卡片
唤起中 → 没反应？→ 三个出口		 浏览器无法汇报深链成败。中介卡的价值不是检测，是把静默失败变成有下一步。

注意②里的「携带」标记：带上下文的深链（当前工作区、当前 API Key）在右上角显示一枚赭红 chip。 同一个 scheme 复制多份会造成"看起来一样、点了不一样"的困惑，chip 是目前最便宜的解释手段。

04

状态矩阵

深链的复杂度几乎全在异常分支。以下六种状态必须在设计阶段就定好，不能留到实现时临时决定。

状态入口表现点击后
已安装底部入口常态；面板显示 已安装handoff 卡片 → 系统接管 → 卡片自动消失
未安装副标题改为「安装客户端」，状态点变赭红不发起深链，直接给下载入口（置灰是反模式）
点击无响应无变化2.5s 后卡片转为「没有收到响应？」，给重试 / 复制 / 下载
无权限条目不渲染（复用 min_role）—
折叠态只剩 W 方块，右上角绿点表示可用点击展开为临时面板或进入视图
移动端抽屉底部同一位置，滚动区外唤起本机 App；未安装走应用商店
05

数据与治理

条目字段（在既有 NavApp 上扩展，不新建表）

  • slug稳定标识，创建后不可改
  • hrefworkbuddy://…，仅客户端 scheme
  • group常用 / 工作流 / 开发者
  • context需要注入的变量：key、model、task
  • min_role复用现有角色常量
  • pinned用户自己钉，不是管理员配
  • source内置（随版本）vs 自定义

三条治理规则

  • 一内置条目随版本发布，管理员只能停用不能改 href，避免升级后地址失效
  • 二自定义条目必须填 scheme 白名单，只允许 workbuddy://，不允许任意协议
  • 三目录区最多 3 条 pinned，超出提示去面板里管理，否则扩张会从"用户偏好"重新长回来
06

对抗审查：这套方案哪里会垮

Q1

底部是低频区，用户可能永远看不见

成立。缓解手段是首次进入时给一次性提示，并把未安装态改成「安装客户端」而不是隐藏入口。 但必须承认：如果产品目标是把客户端当主入口，底部就不够——那就该升级成独立的顶层分组，代价是目录语义被稀释。 这是产品定位问题，不是布局问题。

Q2

为什么不用 Cmd+K 命令面板，那才是"很多入口"的标准答案

命令面板解决的是"我知道叫什么、要找它"，前提是你已经知道有这个东西。 深链入口需要可发现，不能只活在快捷键里。结论：面板里也支持 Cmd+K 作为加速器，但它不是唯一入口。

Q3

handoff 卡片检测不到失败，是不是自欺欺人

检测确实做不到——Web 无法得知 OS 是否接管了 scheme。卡片的价值不是检测，是提供退出路径： 复制链接、下载客户端、重试。没有它，用户面对的是一片空白，只能怀疑自己点错了。 另外这个卡片必须在当前页面内，不能是新标签页，因为深链会夺走焦点。

Q4

十二个入口已经需要搜索了，五十个怎么办

五十个时搜索成为主要路径，分组退化为筛选器。真正的风险不是数量，是命名： 「打开工作区」和「打开项目」这种近似条目会让搜索失效。治理规则里应加一条—— 同一分组内名称不得前缀相同。

Q5

带上下文的深链会不会把 URL 撑爆、把 Key 泄露到系统日志

会。API Key 不得进 query string——它会被系统深链日志、剪贴板管理器、浏览器历史各记一份。 正确做法是只传标识（key id），由客户端回调网关换取；或走一次性 token。这条是硬约束，不是优化项。

明确不做

  • ×不在目录区平铺深链（超过 3 条就失控）
  • ×不做悬浮球（遮挡内容，且与侧边栏职责重复）
  • ×不为深链新造弹窗容器（复用 drill-in 视图）
  • ×不在未安装时把入口置灰（改成安装动作）
  • ×不给深链条目选中态（它没有页面）
  • ×不把 API Key 放进深链参数
