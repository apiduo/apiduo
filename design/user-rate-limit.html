① 预扣必须覆盖单请求成本上界

差额只剩"退款"一个方向，透支在数学上不成立
预扣
p = ⌈prompt × input_mult × in_price⌉ + ⌈min(max_tokens, cap_out) × out_price⌉
并发
K = ⌊Q ÷ p⌋　　预扣即闸门，无需额外计数器
结算
d = c − p　d>0 只扣到余额 0，剩余记坏账并停用
现在的实现：倍率模式预扣 = promptTokens × 1（relay/helper/price.go:110），tiered_expr 模式 C: 0（:410）。 输出侧零预扣，所以 c 的上界与 p 无关，差额随在途请求数线性放大。

    429 · 频率闸（与余额无关）

    只对 p = 0 的免费模型与 RPM 兜底生效
    HTTP/1.1 429 Too Many Requests
Retry-After: 2
X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 0
X-RateLimit-Policy: scope=model; window=60s

{
  "error": {
    "type": "rate_limit_error",
    "code": "model_request_rate_limit",
    "message": "该模型每分钟最多 1000 次成功请求，请在 2 秒后重试。"
  }
}
    429 只表达"等一会再来"；403 只表达"你不该发这个请求"。两者混用会让客户端重试逻辑全部失效。

    客户端看到的弹窗

    余额不足，请求未发出

    本次请求需要预留 ¥0.90，当前余额 ¥0.41。请求没有到达上游，不产生任何费用。

    把 max_tokens 改为 3584 可立即发出；或充值 ¥0.49。

    降级与兜底

    防刷目标下，"放行"不是安全默认值
    故障行为
    Redis 不可用走 DB 条件更新，约束保持；不 fail-open
    余额读取失败拒绝大额请求，放行 p < ¥0.02 的请求
    cap 配置缺失取全局默认 8192，禁止退化为 0
    倍率热更每请求冻结快照，只影响后续请求
    实际成本 > p扣到 0 为止，记坏账，停用账号，报警
