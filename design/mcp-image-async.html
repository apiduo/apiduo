MCP 图片异步 方案原型 2026-11-17

一张图，两种交付：把异步端点接进同一个 image.generate

POST /async/v1/images/generations 返回 202 和 task_id，轮询到 200 才拿到 URL。接入 MCP 的方式不是加一个工具，而是让 transport 补上异步半边，并回答一个更要紧的问题： 完成态没有 status 字段时，怎么判断任务结束了。

时间尺度对比

现有 MCP 的图片调用把上游生成的时长绑在一条 MCP 请求上，客户端超时上限 8 分钟。 代码注释记录了一次真实事故：qwen n=4 用 5 分钟以上，300s 超时触发，计费 20000、产物 URL 全丢。 异步入口是这件事的结构性解法，不是可选优化。

两条链路，同一套工具

点击任一步看该步的返回

同步

execution.task = sync
  1. 0.0 s agent 调 image.generate（prompt + size）
  2. 0.1 s MCP 自调 POST /v1/images/generations
  3. 0.1–349 s 连接挂着等上游出图
  4. 结束 200 data[url] completed

异步

execution.task = async
  1. 0.0 s agent 调同一个 image.generate，参数不变
  2. 0.05 s MCP 自调 POST /async/v1/images/generations
  3. 0.2 s 202 {task_id} working
  4. +10 s 202 status:"in_progress"progress:"30%" 可有可无
  5. +30 s 200 data[url] completed
请求体 { model, prompt, image?, n, size, quality } 两边逐字段一致 · buildPayload 与参数校验零分支
image.generate → 同步返回

      第二行曾经是 v1 方案的第一优先级：成功视图只回 data，
      没有 status，MCP 会永远判 working。
      正确的修法是让生产端补齐 —— 网关改了 4 行（be0c1cfc0），
      MCP 侧一行都不用写。消费端加兜底（TerminalOnData）
      要 15 行、一个测试，还要长期解释「为什么只有图片特殊」，修生产方永远更便宜。

          P0
          image 没有 Query
          task.get 直接报「协议 image 不支持任务查询」

          P0
          提交端点写死同步
          异步模型打到同步路径：4xx，或同步等 8 分钟
          加 AsyncGenerate，由 m.Async 选路
        

        

          P2
          只有 m.Async 才签句柄
          声明 sync、上游却回 task_id：钱花了，用户看到「上游未返回图片数据」。需与句柄 Mode 同一提交
          拿到 task_id 就签，形态写进句柄
