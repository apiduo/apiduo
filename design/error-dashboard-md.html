错误层级归因

先定位坏在哪一层，再谈具体渠道
归因口径：把 error_code 前缀映射到失败发生的位置。渠道层占比高说明是供应商或密钥问题，上游层占比高说明是对端返回异常，客户端层高则说明是自己用户传错了参数——三者的处置动作完全不同。

重试效果

第 0 层不是"重试次数为 0 的成功"，而是 DecideRelayRetry 判定不可重试、直接返回的错误——参数非法、额度不足、权限拒绝都属于这一类。它们从没进过重试流程，混进"重试成功率"会把分母做脏。

换个维度就是换个切片轴，点任意行下钻到错误流

时间 错误码 消息 模型 渠道 用户 状态 耗时 request_id
没有匹配的错误记录
为什么这里还有「重试链」？一次客户端请求可能打 3 个渠道，每次失败都写一条错误日志，request_id 相同。点开任意一行可以看到完整尝试链——这是判断「渠道坏了」还是「整个模型都坏了」的唯一依据。
口径提醒：本页的失败率是 尝试口径（失败尝试 ÷ 该渠道尝试总数），不是用户可感知的请求失败率。一个渠道失败率高但被重试兜住了，用户其实无感；反过来，渠道失败率低但它是唯一可用渠道，影响反而大。perf_metrics 没有 channel 维度，这里无法给出请求口径。

这张时间线暴露的是监控缺口：密钥从失效到被自动禁用隔了约 2 小时，期间完全靠重试硬扛——用户侧看起来「只是偶尔慢」，运维侧却在持续产生错误日志。错误看板的价值就是把这段窗口从「事后翻日志」提前到「5 分钟内可见」。
能力缺口：DisableChannel 目前只写系统日志并发通知，没有把「谁在什么时候被禁用、原因、被谁恢复」落成结构化记录。上面只有最后一条能直接从 channels.status 读到，其余节点是根据错误时间推断的示意。若要真正的时间线，需新增 channel_events 表（渠道 ID / 事件类型 / 原因 / 错误码 / 触发错误日志 ID / 操作者 / 时间）。

指标口径表

每个数字都必须能追到一张表和一种算法
指标 定义 数据源 粒度
请求失败率 1 - success_count / request_count，一次请求一个样本，重试成功算成功 perf_metrics 小时 / model+group
尝试失败数 每条 type=5 日志 = 一次上游尝试失败 logs 每条尝试
失败请求数 COUNT(DISTINCT request_id)，去重后才是客户端看到的失败次数 logs 每个 request
层级归因 error_code 前缀映射：channel: → 渠道层；bad_response*/empty_response/do_request_failed → 上游层；invalid_request/bad_request_body/model_not_found → 客户端层；insufficient_user_quota/access_denied → 额度层；其余 → 本地系统 logs.other 每条尝试
渠道尝试失败率 该渠道失败尝试 ÷ 该渠道总尝试（分母 = 成功消费日志 + 错误日志，按 channel_id 聚合） logs 渠道
重试阶梯 按 request_id 聚合：同一 request 的 type=5 条数 = 失败尝试数；该 request 是否出现 type=2 决定最终成败。层内拆分是估算，但 Σ失败尝试 与 Σ最终失败 必须与日志精确相等 logs 每 request
维度分布 按 channel_id / model_name / username / group / error_code 分别 GROUP BY，各维度求和恒等于区间失败尝试总数 logs 单维度
恶化信号 最近 30 分钟错误率 ≥ 7 天同时段基线 × 3 且绝对次数 ≥ 10，两个条件同时满足才报，避免小样本噪音 logs 聚合 渠道 × 错误码

MVP 后端接口清单

只读，五个接口足够支撑本原型全部视图
接口 用途 实现要点
GET /api/error/summary KPI + 双口径时间序列 perf_metrics 按桶求和取失败率；logs 按桶 count 取尝试数。两路各查一次，在 handler 合流
GET /api/error/breakdown 按错误码 / 渠道 / 模型 / 用户 / 分组分布 dim 必须是白名单枚举（code/channel/model/user/group），不要接受任意列名拼接
GET /api/error/events 错误流分页 复用 GetAllLogs 的过滤条件 + channel/error_code 条件；CH 上走 LIMIT
GET /api/error/request/:rid 单请求全链路（重试链） 按 request_id 查同表所有 type in (2,5) 行，按 id 升序即尝试顺序
GET /api/error/retry-ladder 重试 N 次后的成败分布 一条 GROUP BY request_id 的子查询先算出每次请求的失败次数与最终结果，再按失败次数分桶
GET /api/error/channels 渠道健康排行 分母要和错误分母同源，否则跨渠道不可比

落地顺序与边界

  1. 先做只读四视图：总览、错误流、渠道健康、口径。不碰写入，不改表结构，纯查询层。
  2. JSON 抽取要双实现：error_code 藏在 logs.other 里。CH 用 JSONExtractString(other,'error_code')，MySQL 用 JSON_UNQUOTE(JSON_EXTRACT(other,'$.error_code'))。两套都要有测试，否则换库就静默出错。
  3. 聚合必须走预聚合：线上 logs 已 8 万+行/天且 TTL 180 天，24h 视图每次全表 JSON 抽取撑不住。要么扩 perf_metrics 加 channel_id 与 error_code 维度，要么新建 error_rollup_10m。
  4. 维度一次查全：四个维度用 GROUPING SETS 一条 SQL 出全，避免五个接口各查一次导致总数对不上，也省掉四次往返。
  5. 暂不做：处置按钮、告警规则、认领状态。这三项都要新表 + 权限模型，先把"看得见"做对。
  6. 明确不做：不重复实现渠道自动禁用判断。现有 ShouldDisableChannel 已经覆盖，看板只呈现结果。
